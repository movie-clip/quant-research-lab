# US-27.9: Low-severity tail — fabricated 0.0 points, stdev conventions, DR/return-basis consistency

**Epic:** Epic 27 — Financial Calculation Correctness
**PRD:** [`epic-27-financial-calculation-correctness.md`](../prd/epic-27-financial-calculation-correctness.md)
**Status:** Done
**Last updated:** 2026-07-05

## Story

As a **portfolio researcher**, I want the remaining audited consistency gaps
closed — no plausible-looking fabricated zeros in the performance series, a
written stdev convention per surface, and a self-consistent Diversification
Ratio on a verified return basis — so every number left standing after
Epic 27 is either correct or explicitly documented.

## Context (audit findings F11, F12, F13)

**F11 — fabricated 0.0 performance points.**
`analytics/performance.py` `build_true_performance_series` initializes
`portfolio_return_pct = 0.0` per point and only overwrites it when the basis
contract is `verified_total_return` and the daily return is computable. Two
fabrication paths: (a) unverified basis → an entire series of hard `0.0`s
(reads as "0% return", not "withheld"); (b) a mid-series zero-previous-value
day → a single bogus 0.0 point while `cumulative_growth` carries on. Fix:
`portfolio_return_pct` becomes nullable (schema + TS type + consumers), null
on both paths; the withheld-basis path should suppress explicitly, not
zero-fill.

**F12 — two stdev conventions coexist undocumented.** `analytics/risk.py`
uses sample (N−1) stats for vol/TE/β/ρ; `analytics/correlation.py` and
`analytics/distribution.py` use population (N). Ratios cancel the convention;
stdev-level outputs differ slightly across tabs for the same window. Resolve
by **documenting** the per-surface convention in the methodology (a
standardization would churn every golden for negligible value — decide and
record; if standardizing anyway, do it here with one deliberate golden
regeneration).

**F13 — Diversification Ratio self-consistency + return basis.**
(a) `intra_correlation_engine.py` computes σᵢ over each holding's own
non-null dates but σ_p over complete-case dates only; with ragged coverage
the documented DR ≥ 1 guarantee can break. Fix: compute σᵢ over the same
complete-case date set as σ_p (methodology already says the DR inputs must be
self-consistent).
(b) The correlation engines consume `row["price"]` directly, never
`select_history_price_series`. Yahoo-sourced rows set `price = adjClose`; the
FMP light endpoint's basis must be **verified empirically** (does `price`
re-adjust for dividends/splits? the US-21.4 goldens churn suggests it does,
but nothing asserts it). Outcome: either switch these engines to the
selected-series helper, or document the verified basis + add a
`detect_history_return_basis`-driven note on the correlation/intra responses.
Never leave the basis unstated.

Implementer must read:
- `analytics/performance.py` + `schemas/reconciliation.py`
  `PerformancePoint` + frontend consumers of `portfolio_return_pct`.
- Methodology §Volatility and Relative Risk, §Value-at-Risk (population
  choice), §Intra-Portfolio Correlation (DR edge cases).
- `services/intra_correlation_engine.py`, `services/correlation_engine.py`,
  `analytics/risk.py` `select_history_price_series`, and the FMP client's
  light-endpoint response (empirical check with a dividend-paying symbol
  across an ex-date).
