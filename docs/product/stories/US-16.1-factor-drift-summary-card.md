# US-16.1: Factor Drift Summary card

**Epic:** Epic 16 — Factor Drift Visualization
**PRD:** [`epic-16-factor-drift-visualization.md`](../prd/epic-16-factor-drift-visualization.md)
**Status:** Done
**Last updated:** 2026-06-04

## Story

As a **portfolio researcher**, I want a Factor Drift Summary card on the
Exposure tab that ranks how much each factor loading has moved over a selected
window, so that I can see at a glance which exposures are drifting — and in
which direction — without trying to read the change off a 16-line trend chart.

## Context

The rolling factor model already computes a full per-factor loading time
series, surfaced today only as the multi-line `RollingFactorLoadingsCard`
trend chart on the Dashboard. That chart shows the *levels* but makes the
*change* hard to rank or quantify. This story adds a **frontend-only**
`FactorDriftSummaryCard` to the Exposure tab that reduces each factor's series
to a single delta — latest loading minus the reference loading at the start of
the trimmed window — and renders the factors ranked by absolute drift as a
horizontal divergent bar list.

This story does **no** backend work. The data already lives in
`ExposureAnalysis.statistical_factor_model.rolling_loadings_{20,60,252}d`,
which the Exposure tab's `result` prop already carries. The card derives the
deltas client-side — a presentation-layer rebasing of engine-computed
loadings, the same class of client-side arithmetic the existing
`RollingFactorLoadingsCard` already performs (chart-domain, coverage). It never
fits a regression.

## Acceptance criteria

- [x] AC1 — A `FactorDriftSummaryCard` is visible in the Exposure tab when a
  portfolio is loaded and the selected window has enough rolling-loading
  observations. It renders inside a `CardShell` (`role="region"` with an
  `aria-labelledby` title) using the Epic 12 design system — no raw hex / px in
  inline styles (the `designSystem.audit.test.ts` contract holds).
- [x] AC2 — For each factor with a non-null latest and non-null reference
  loading, the card shows a row with: factor label, reference loading, latest
  loading, and the drift delta (latest − reference) formatted to 2 decimals
  with an explicit sign (e.g. `+0.42`, `−0.18`).
- [x] AC3 — Rows are ranked by absolute drift descending (largest mover first);
  ties broken by factor label ascending. The number of rows is capped at the
  same default factor set the trend chart shows (`DEFAULT_VISIBLE_FACTORS`) so
  the two cards stay visually consistent.
- [x] AC4 — Each row renders a horizontal divergent magnitude bar centered on a
  zero baseline: bars extend right for positive drift, left for negative,
  with length proportional to absolute drift relative to the largest absolute
  drift in the visible set. Direction is encoded by **both** color *and* side
  of the baseline (not color alone), and the numeric signed delta is always
  present — so the signal survives for color-blind users.
- [x] AC5 — A window selector (20d / 60d / 252d, default 60) is visible; changing
  it recomputes the deltas and re-ranks the rows from the matching
  `rolling_loadings_<window>` series. The selector uses the shared
  `WindowSelector` primitive with a `:focus-visible` outline and an
  `aria-label` per button.
- [x] AC6 — A `Synthetic` `TrustBadge` is shown on the card header. Hovering it
  shows: `"Factor loadings are reconstructed from current holdings × historical factor-proxy prices. Drift is the change in loading over the selected window."`
  (The badge primitive supplies the visible "Synthetic" label; the tooltip text
  itself omits the word so the design-system single-source-of-truth audit stays green.)
- [x] AC7 — When the selected window has insufficient history (its
  `rolling_loadings_<window>` series is empty after leading-null trimming, or
  the factor model status is `insufficient_history`), the card renders an
  `EmptyState` reading `"Not enough history for {window}d factor drift."` plus
  the available observation count. It is never blank, never zeroed, never
  fabricated.
- [x] AC8 — A factor whose reference *or* latest loading is null in the selected
  window is excluded from the ranked rows entirely (no fabricated 0 delta). If
  every visible factor is excluded, the card falls back to the AC7 EmptyState.
- [x] AC9 — A short caption states the comparison being made, e.g.
  `"Latest vs start of window · {N} observations · {startDate} → {endDate}"`,
  derived from the trimmed series coverage (reuse the coverage helper shape).
- [x] AC10 — `npx tsc --noEmit` is clean; `npx vitest run` passes including the
  new `FactorDriftSummaryCard.test.tsx`; the design-system audit stays green;
  existing `RollingFactorLoadingsCard.test.tsx` and `ExposurePanel` tests stay green.

## Out of scope

- No backend engine / route / schema — data already exists in `ExposureAnalysis`.
- No re-fit of the factor model and no client-side regression of any kind.
- No relocation or restyle of the existing Dashboard `RollingFactorLoadingsCard`.
- No statistical-significance / confidence bands on the drift delta.
- No user-selectable custom reference date — the reference is the first

- No factor-group filter (Market/Style/Sectors/Macro) in v1 — the card uses the
  same default factor set as the trend chart; group filtering can be a follow-up.

## Notes / decisions

- **Delta definition**: `drift_k = β_k(t_latest) − β_k(t_reference)` where both
  loadings come from the same `rolling_loadings_<window>` series and
  `t_reference` is the first date of the series after leading-null trimming.
  This is a descriptive difference of two engine-computed loadings, not a new
  estimate — consistent with the methodology-traceability guardrail (the
  loadings trace to §Statistical Factor Model; the drift subsection documents
  the difference).
- **Frontend-thin justification**: per CLAUDE.md the frontend must not compute
  betas/correlations/returns. It does **not** here — the betas are computed by
  the engine. Taking a difference of two already-computed loadings is a
  presentation rebasing, the same class as the existing card's domain/coverage
  computation. The methodology subsection makes the formula explicit so the UI
  value still traces to a documented definition.
- **Academic precedent** (for the methodology subsection): time-varying /
  conditional factor exposures are well established — Ferson & Schadt (1996),
  "Measuring Fund Strategy and Performance in Changing Economic Conditions,"
  *Journal of Finance* 51(2) (conditional, time-varying betas); Jagannathan &
  Wang (1996), "The Conditional CAPM and the Cross-Section of Expected Returns,"
  *Journal of Finance* 51(1). Rolling-window beta estimation as a drift proxy
  follows the standard rolling-regression convention (cf. Fama & MacBeth 1973).
  The drift statistic itself (`Δβ`) is a plain first difference, no citation
  beyond the rolling-beta literature required.
- **Color map reuse**: reuse `FACTOR_LINE_COLORS` so a factor's color is
  consistent between the Dashboard trend chart and this card. Where the divergent
  bar needs a sign color, use the existing value-positive / value-negative
  design tokens (as the drawdown/attribution cards do), not the per-factor color,
  so direction reads consistently across rows.
- **No fetch**: the card is purely derived from the `result` prop the Exposure
  tab already holds — no adapter call, so there is no loading/error state of its
  own (those belong to the tab-level fetch). Only the EmptyState path applies.
