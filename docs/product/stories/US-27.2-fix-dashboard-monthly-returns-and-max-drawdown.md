# US-27.2: Fix dashboard monthly-return chaining + max-drawdown basis

**Epic:** Epic 27 — Financial Calculation Correctness
**PRD:** [`epic-27-financial-calculation-correctness.md`](../prd/epic-27-financial-calculation-correctness.md)
**Status:** Done
**Last updated:** 2026-07-05

## Story

As a **portfolio researcher**, I want the Dashboard's monthly returns to
compound back to the period's time-weighted return, and its max drawdown to
measure investment loss rather than cash-flow noise, so the Dashboard numbers
are internally consistent and cash-flow-neutral like the rest of the product.

## Context (audit findings F3 + F2, both in `services/dashboard_history_engine.py`)

**F3 — monthly returns drop every month-boundary return.**
`_compute_contribution_adjusted_monthly_returns` groups states by `YYYY-MM`
and compounds *within* each group with `previous_state = None` at the top of
every month. The daily return from the last trading day of month M to the
first trading day of month M+1 is therefore counted in **no** month:
Π(1 + monthly) ≠ period TWR, and every month omits its first trading day's
return. Correct behaviour: the first day of month M+1 compounds against the
prior month's last state (carry `previous_state` across the group boundary;
a month's return spans "last state of prior month → last state of this
month").

**F2 — max drawdown computed on raw portfolio value.**
`_compute_max_drawdown` walks `performance_series` tracking a peak of
`point.portfolio_value` — which includes external cash flows. A deposit lifts
the value and masks a real drawdown; a withdrawal fabricates one. The
methodology's stated basis is the compounded return index
(`drawdown_basis="compounded_return_index"`, §Wealth Index and Drawdown), and
the diagnostics path already implements it correctly (`_build_wealth_index`
over cash-flow-neutral TWR returns in `risk.py`). The dashboard path must use
the same wealth-index basis (reuse `_build_wealth_index` +
`_build_drawdown_from_return_index`, or the series' cumulative
`portfolio_return_pct` chain — not raw value).

Implementer must read:
- `services/dashboard_history_engine.py` — both functions + where
  `max_drawdown_pct` / `monthly_returns` flow into `range_metrics`.
- `analytics/risk.py` `_build_wealth_index` / `_build_drawdown_from_return_index`
  (the correct existing basis to reuse).
- `docs/contracts/dashboard-fields.md` — `monthly_returns`,
  `monthly_returns_reliable`, `max_drawdown_pct` rows (note: `max_drawdown_pct`
  sits behind the investor-economics withholding policy — the fix changes the
  computed value, not the withholding gate).

## Acceptance criteria

- [x] AC1 — Monthly returns chain: for a fixture spanning ≥ 3 months with no
  external flows, Π(1 + monthly_return/100) equals the period compounded TWR
  within 1e-9 (property test).
- [x] AC2 — With external flows, each monthly return is built from the same
  cash-flow-neutral daily formula as the TWR chain (flows subtracted before
  dividing by the prior value), including the month-boundary day.
- [x] AC3 — `_compute_max_drawdown` uses the compounded return index: a fixture
  with a mid-series deposit and a genuine price drawdown reports the price
  drawdown (today it is masked); a fixture with a withdrawal and flat prices
  reports ~0 drawdown (today it fabricates one).
- [x] AC4 — `monthly_returns_reliable` semantics unchanged (negative-value /
  extreme-move suppression still applies on top of the corrected values).
- [x] AC5 — The withholding policy around `max_drawdown_pct` is untouched
  (withheld stays withheld); only the computed value changes where surfaced.
- [x] AC6 — Goldens (`dashboardGoldens.ts`) regenerated deliberately; the diff
  is explained per-field in the slice log. Methodology + `dashboard-fields.md`
