# US-32.2: Bring the Risk-tab cards under the design-system audit

**Epic:** Epic 32 — Project Hygiene & Agent-Facing Doc Accuracy
**PRD:** [`epic-32-project-hygiene-and-agent-docs.md`](../prd/epic-32-project-hygiene-and-agent-docs.md)
**Status:** Done (2026-08-19)
**Last updated:** 2026-08-19

## Story

As a **portfolio researcher**, I want the Risk tab's cards held to the same
enforced visual and accessibility contract as every other card, so that the
tab I use for risk decisions cannot quietly drift into inconsistent or
inaccessible rendering.

## Context

PRD finding **F-5**, deferred from the 2026-06-19 skills review and verified
still live on 2026-08-12.

`designSystem.audit.test.ts` mechanically enforces the Epic-12 contract — no
hex literals, no `px` literals, single-source `Synthetic` labelling — over the
files listed in `ALL_CARD_FILES`. All three Risk-tab cards are **absent** from
that list:

- `StressScenariosCard.tsx`
- `DrawdownAnalyticsCard.tsx`
- `VarDistributionCard.tsx`

They use the Epic-12 primitives **by convention**, and as far as anyone knows
they comply — but nothing checks. A hex literal, a `px` value, or a hand-rolled
Synthetic badge in any of them would ship green today. That is a two-tab gate
on a three-tab product.

Note the ordering risk: adding the files to the list may surface real
violations. Those are the point of the story, not an obstacle to it — fix them
rather than waiving them, and if any turn out to need a deliberate exception,
record the reason the way `ExposurePanel`'s entry does.

Implementer must read: `apps/desktop/src/test/designSystem.audit.test.ts`
(`ALL_CARD_FILES`, `CARDS_WITH_BADGE`, and the escape-hatch comment mechanism);
`.claude/skills/ui-polish/SKILL.md`; the three card files.

## Acceptance criteria

- [x] AC1 — All three Risk-tab cards are in `ALL_CARD_FILES`, so the no-hex /
  no-px / single-source-`Synthetic` checks cover them.
- [x] AC2 — Each card that renders a `Synthetic` badge is in
  `CARDS_WITH_BADGE`; each that does not is deliberately **absent** from it,
  with the reason recorded in a comment (the `ExposurePanel` / US-30.6
  precedent).
- [x] AC3 — **Any violation the audit surfaces is fixed, not waived** — a
  literal replaced by its design token, not hidden behind an escape hatch. If a
  genuine exception is required, it carries a comment saying why.
- [x] AC4 — **Zero visual change.** Every replacement is a literal-to-token
  substitution with the same computed value; the cards render identically.
- [x] AC5 — The audit **actually covers** the new files: temporarily
  introducing a hex literal into a Risk-tab card fails the suite. Demonstrated
  during implementation and recorded in the story; the check does not ship as a
  test that passes vacuously.
- [x] AC6 — Existing Risk-tab card tests stay green **unchanged** — this story
  alters styling sources, never behaviour.
- [x] AC7 — `dashboardGoldens.ts` byte-identical; full suite + tsc + dead-code
  gate green.

## Out of scope

- **Any visual redesign of the Risk tab.** This story makes the existing
  appearance enforced, not different.
- **Extending the audit's rules** (new checks beyond hex/px/badge). Widening
  scope and deepening rules at once would make a failure ambiguous.
- **Chart files.** `CHART_FILES` has its own membership rules; the Risk cards'
  charts are considered separately only if the audit reports on them.

## Notes / decisions

- **Why this was deferred and why it should not be again.** The 2026-06-19
  review scoped itself to skill files and left this. Fourteen months of product
  work later the gate still stops at the Exposure tab. The cost of leaving it
  is invisible precisely because nothing checks — which is the argument for
  closing it, not for deferring it once more.
- **Expect the honest outcome to be "no violations found".** The cards were
  built with the primitives. That is a fine result: the deliverable is the
  *enforcement*, and AC5 is what proves the enforcement is real rather than
  a list nobody reads.
- No formula or methodology change; no academic citation required.

## Outcome (2026-08-19)

**Adding the files surfaced real violations, as the story anticipated.**
`DrawdownAnalyticsCard` and `VarDistributionCard` both opened their TrustBadge
tooltip with `"Synthetic: …"`, tripping the single-source rule — the badge
already renders that label from `TrustBadge`'s `LABELS` map, so the string was
duplicated in the card. **Fixed, not waived** (AC3): the prefix is gone and the
tooltips now read like the compliant cards' (`FactorAttributionCard`,
`RollingCorrelationChart`), describing the construction rather than restating
the badge.

**A note on AC4.** "Zero visual change" holds for the rendered card surface —
no token substitutions were needed, so no colour, spacing or layout moved. The
one thing that did change is the *hover tooltip text* on two badges, which is
the fix itself. Recorded rather than glossed, because AC4 was written expecting
hex/px substitutions and this violation was a different class.

**`StressScenariosCard` needed no change** — its only `Synthetic` matches are
the `SyntheticHistoryCoverage` type name, which the rule's boundary-aware regex
correctly ignores.

**AC5 demonstrated, not assumed.** A `{ color: "#ff0000", padding: "4px" }`
literal was injected into `StressScenariosCard` and the suite failed on both
`no_literal_hex_colors_in_card_files` and
`no_literal_pixel_values_in_inline_style_props`. Before this story that same
literal shipped green. The canary was then reverted, and the file is
byte-identical to its committed state.

**Placement decisions recorded in the audit file:** all three cards render
synthetic-history analytics, so all three are in `CARDS_WITH_BADGE`.
`DrawdownAnalyticsCard` and `VarDistributionCard` are in `CHART_FILES`;
`StressScenariosCard` is deliberately absent from it, because it renders a
scenario table and no chart.
