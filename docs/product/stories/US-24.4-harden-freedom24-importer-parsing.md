# US-24.4: Harden the Freedom24 importer parsing + extract its hardcodes

**Epic:** Epic 24 — Codebase Improvement
**PRD:** [`epic-24-codebase-improvement.md`](../prd/epic-24-codebase-improvement.md)
**Status:** Done
**Last updated:** 2026-06-24

## Story

As a **portfolio researcher**, I want the Freedom24 statement importer to fail
**safe** when a PDF's layout drifts — skipping an unparseable record and
surfacing the gap through reconciliation instead of crashing the whole import or
silently mis-parsing — and its inline format hardcodes named in one place, so
that importing a slightly-different Freedom24 statement degrades gracefully and
the parser is auditable.

## Context

`app/importers/freedom24.py` parses the statement PDF by walking **fixed line
offsets** (`lines[index + N]`, `step = 8/9`, magic page indices `page_texts[3]`,
`[6]`, `[9]`…). Two problems (Epic 24 register row US-24.4):

1. **Fragile, unguarded positional parsing.** Each record calls
   `_normalize_number(lines[index + N])`, which raises `ValueError` on a
   non-numeric line. A single layout drift therefore **crashes the entire
   import** (or mis-parses) — there is no per-record guard.
2. **Inline format hardcodes** repeated across the parsers: the currency
   whitelist `{"USD", "EUR", "GBP"}`, the `.replace(".US", "")` symbol-suffix
   strip, the default `currency = "USD"`, and the magic page indices. Plus three
   genuinely-**dead** parsed-but-dropped offset-walk locals (`isin` in
   `_parse_positions`, `realized_pnl`, `account` — `# noqa`'d in US-23.3).

**Correction to the register:** the "Freedom24 ISIN data gap" is **not real** —
`_parse_instruments` already parses ISIN and sets `isin=` on every
`ImportedInstrument` (so Freedom24 ISINs already reach the model and the US-19.2
identity checks). The line-138 `isin` in `_parse_positions` is just dead
offset-walk code (positions don't model ISIN). This story corrects that register
row rather than "flowing" an ISIN that already flows.

This is **behaviour-preserving for valid statements** — the existing
`test_import_freedom24_statement_returns_expected_snapshot` (FF2026.pdf) pins the
exact parsed positions / cash / NAV / ledger and must stay green byte-for-byte;
the hardening only changes behaviour for **malformed** input (crash → safe skip).

Implementer must read:
- `app/importers/freedom24.py` — the five positional parsers + `_normalize_number`.
- `app/tests/test_importer.py` `test_import_freedom24_statement_returns_expected_snapshot`
  — the FF2026.pdf golden-master guard.
- `docs/finance/financial-methodology.md` §Import admission rule — a dropped
  record must surface via reconciliation, never be fabricated.

## Acceptance criteria

- [x] AC1 — **Fail-safe positional parsing:** each Freedom24 record parse
  (`_parse_positions`, `_parse_transactions`, `_parse_cash_balances`,
  `_parse_cash_movements`, `_parse_instruments`) guards its fixed-offset reads so
  a malformed/non-numeric record is **skipped and parsing continues**, instead of
  raising and aborting the whole import. A truncated or garbled page yields a
  **partial** snapshot (or empty list), never an exception.
- [x] AC2 — **Behaviour-neutral for valid statements:** the FF2026.pdf snapshot
  test is unchanged and green byte-for-byte (same single VTI position, same cash
  balances, NAVs, and 8 ledger entries) — the guards add resilience without
  changing any value parsed from a well-formed statement.
- [x] AC3 — **No fabrication on a dropped record:** a skipped record is simply
  absent from the snapshot (positions / ledger / instruments), never replaced by
  a zero/placeholder; the existing import-admission reconciliation
  (`build_reconciliation_summary`) is what surfaces the resulting totals gap
  (the dropped value shows up as a reconciliation difference, not a silent zero).
- [x] AC4 — **Hardcodes named once:** the currency whitelist, the `.US`
  symbol-suffix token, the default position currency, and the Freedom24 page
  indices are module-level named constants (e.g. `_KNOWN_CURRENCIES`,
  `_US_SUFFIX`, `_DEFAULT_POSITION_CURRENCY`, `_PAGE_*`); the three dead
  parsed-but-dropped locals (`isin`/`realized_pnl`/`account`) are removed (their
  offset structure is preserved by comments, not dead bindings). `ruff`/`vulture`
  stay clean (US-23.8 gate).
- [x] AC5 — The ISIN flow is **pinned**: the FF2026 test asserts the VTI
  instrument's `isin` equals its statement value (proving the already-working
  ISIN flow is not regressed by the hardcode extraction).

## Out of scope

- **Modeling `realized_pnl`** — `ImportedLedgerEntry` has no realized-P&L field;
  adding one is a schema change with downstream contract impact, deferred (the
  Freedom24 value stays parsed-but-unused, now documented as a known deferral, not
  silently `# noqa`'d).
- **A full parser rewrite** (e.g. table-structure detection instead of fixed
  offsets) — out of scope; this story adds *guards* around the existing offset
  logic, it does not replace it.
- **The IB / ESPP importers** — they have lower-volume positional parsing; the
  same fail-safe pattern can extend to them in a follow-up. This story is Freedom24
  (the dominant offender). Recorded in the register.

## Notes / decisions

- **Skip-and-continue is the correct fail mode, not skip-and-fabricate.** A record
  that can't be parsed can't be fabricated either; the current behaviour (crash)
  is strictly worse than a partial import. The import-admission reconciliation
  already compares parsed totals vs the statement's reported totals, so a dropped
  record surfaces as a reconciliation difference — the trust-semantics-correct way
  to expose a gap (no fabrication, no silent zero).
- **Behaviour-neutral proof = the FF2026 fixture test.** Because a real Freedom24
  statement is pinned to exact values, the hardcode extraction and the guards are
  provably non-altering for valid input; only malformed input changes (crash →
  skip), which the new degradation test covers.
- No new formula; no methodology change (only an importer-resilience note).
