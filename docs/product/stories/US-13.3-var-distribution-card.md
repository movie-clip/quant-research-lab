# US-13.3: VaR & Distribution card

**Epic:** 13 — Risk Analytics Tab
**PRD:** [`epic-13-risk-analytics-tab.md`](../prd/epic-13-risk-analytics-tab.md)
**Status:** Done
**Last updated:** 2026-06-01

## Story

As a **portfolio researcher**, I want a VaR & Distribution card on the Risk
tab that shows me the daily return distribution histogram plus a table of
percentiles, historical Value-at-Risk (95% / 99%), Conditional VaR (95%
Expected Shortfall), and the distribution's shape (mean / std / skew /
excess kurtosis) — so that I can pre-decide a risk budget anchored in the
actual statistical tail of my portfolio's returns rather than reasoning
abstractly about volatility or single-point drawdowns.

## Context

US-13.1 (Done) and US-13.2 (Done) shipped the first two cards of the Risk
tab (Stress Scenarios + Drawdown Analytics). This story adds the **third and
final** card to the same `RiskPanel.tsx` `.risk-shell-stack`, completing
the v1 Risk tab surface.

This is the most methodologically novel of the three cards: a brand-new
analytics module computing historical VaR, CVaR, percentiles, distribution
moments (mean / std / skewness / excess kurtosis), and a 30-bin histogram.
The methodology is already in place — §Value-at-Risk and Distribution
(line 667 of `docs/finance/financial-methodology.md`) was appended during
the Epic 13 foundation pass with full formulas, edge cases, and the
required academic citations (Jorion 2007; Acerbi & Tasche 2002;
Embrechts, McNeil & Frey 2015).

## Acceptance criteria

- [x] AC1 — `services/quant-engine/app/analytics/distribution.py`
  exposes five pure functions: `compute_percentiles(returns)`,
  `compute_var(returns, confidence)`, `compute_cvar(returns,
  confidence)`, `compute_distribution_shape(returns)`,
  `compute_histogram(returns, num_bins=30)`. No I/O, no
  `MarketDataService` import.
- [x] AC2 — All distribution math is **pure Python** (the
  `statistics` standard-library module plus manual quantile /
  moment / histogram formulas). No `numpy` or `scipy` imports — the
  project deps do not include them, and the pure-Python factor model
  is the established precedent.
- [x] AC3 — Percentile computation uses NIST linear-interpolation
  method (equivalent to numpy.quantile default; equivalent to
  `statistics.quantiles(returns, n=100, method='inclusive')` indexing
  for the 5 / 10 / 50 / 90 / 95 percentiles). All five percentiles
  return None when `len(returns) < 20`.
- [x] AC4 — `compute_var(returns, confidence)` returns
  `-percentile(returns, 1 - confidence) * 100` (positive number =
  loss in percent). Returns None when `len(returns) < 20`. NEVER
  clipped to a positive number — when the window contains no loss
  days at the requested confidence, the function returns a NEGATIVE
  number ("the tail day was still positive"), surfaced as-is to the
  UI. Methodology Contract rule.
- [x] AC5 — `compute_cvar(returns, confidence)` returns
  `-mean({r : r ≤ percentile(returns, 1 - confidence)}) * 100`
  (positive number = loss in percent). Returns None when
  `len(returns) < 20` OR when the tail (returns ≤ the quantile)
  contains fewer than 2 elements.
- [x] AC6 — `compute_distribution_shape(returns)` returns a dict with
  keys `mean_pct`, `std_pct`, `skewness`, `kurtosis_excess`. mean_pct
  and std_pct are in percent (multiplied by 100). std uses population
  N denominator (consistent with the correlation engine). Skew is
  Fisher-Pearson (`m3 / m2^(3/2)` where `m_k = mean((r - mean)^k)`).
  Kurtosis is EXCESS (`m4 / m2^2 - 3`, Fisher convention). When
  `len(returns) < 20`: all four fields None. When std = 0
  (constant series): mean_pct and std_pct are computed normally,
  skewness and kurtosis_excess return None.
- [x] AC7 — `compute_histogram(returns, num_bins=30)` returns a list
  of `HistogramBin` with 30 bins by default, range = [min(r),
  max(r)] (auto-fit; no symmetric padding; no outlier trimming).
  Each bin's `center` is the bin midpoint (decimal return, NOT
  percent). The total of `bin.count` across all bins equals
  `len(returns)`. Returns empty list when `len(returns) < 20`.
- [x] AC8 — `services/quant-engine/app/schemas/distribution.py`
  defines: `DistributionEngineRequest(PortfolioEngineRequest)` with
  `window_trading_days: Literal[60, 252, 504] = 252` (no None/"max"
  — VaR is window-pinned for interpretability); `HistogramBin {
  center: float; count: int }`; `DistributionEngineResponse {
  window_trading_days: int; return_count: int; var_95: float | None;
  var_99: float | None; cvar_95: float | None; percentile_5: float |
  None; percentile_10: float | None; percentile_50: float | None;
  percentile_90: float | None; percentile_95: float | None;
  mean_pct: float | None; std_pct: float | None; skewness: float |
  None; kurtosis_excess: float | None; histogram_bins:
  list[HistogramBin]; trust: Literal['synthetic', 'unavailable'] }`.
- [x] AC9 — `POST /engines/distribution/run` is registered in
  `app/api/main.py` (after `drawdown.router`) and routed to
  `app/api/routes/distribution.py` (mirror of `drawdown.py`).
  Returns `DistributionEngineResponse` with HTTP 200; malformed
  payloads (e.g. `window_trading_days: 1000` not in the Literal
  set) return HTTP 422; internal failures raise HTTP 400 with
  exception detail.
- [x] AC10 — `services/quant-engine/app/services/distribution_engine.py`
  exposes `run_distribution_engine(request) ->
  DistributionEngineResponse`. Reuses
  `_build_synthetic_snapshot_history_states` (from
  `diagnostics_engine.py`); computes daily returns from each
  state's `total_market_value` (same pattern as
  `drawdown_engine._compute_daily_returns` — duplicated, not
  shared, since the two engines' error handling differs); fetches
  market data with `_lookback_calendar_days(window) = ceil(window
  * 1.6) + 30` (duplicated mirror of attribution_engine, same
  pattern drawdown_engine uses). Then delegates to the
  analytics-module functions.
- [x] AC11 — Engine fail-closed behaviour: response `trust =
  'unavailable'` AND `return_count = 0` AND every scalar field
  None AND `histogram_bins = []`, in any of these conditions:
  (a) request has no positions; (b) `benchmark_rows` empty;
  (c) `len(daily_returns) < 20`. Never fabricates a zero VaR or
  a synthetic histogram.
- [x] AC12 — Engine sanity invariant: `cvar_95 >= var_95` (CVaR ≥
  VaR by construction, coherent risk measure). If the engine ever
  computes a pair where this is violated, it MUST raise (which
  becomes HTTP 400 at the route boundary) — never emit
  inconsistent data. Methodology Contract rule.

  Embrechts, McNeil & Frey 2015 — Quantitative Risk Management
  Ch. 2.4). No methodology ticket needed in this story.
- **Pure Python only.** The project deps (`requirements.txt`)
  do not include numpy or scipy; the existing factor model is
  pure-Python linear algebra. The distribution module follows
  suit. Implementer should use `statistics.mean`,
  `statistics.pvariance` (population variance, consistent with
  the correlation engine), and hand-rolled formulas for
  quantile (NIST linear interpolation), skewness
  (`m3 / m2^(3/2)`), and excess kurtosis (`m4 / m2^2 - 3`).
- **CVaR ≥ VaR invariant is non-negotiable.** Acerbi & Tasche
  proved CVaR is a coherent risk measure with the sub-additivity
  property that VaR lacks; `CVaR < VaR` would be a code bug,
  not a data issue. The engine raises rather than emits
  inconsistent data — methodology Contract rule.
- **Negative VaR is meaningful, not a bug.** When the lookback
  window contains no loss days at the requested confidence
  (e.g. portfolio went straight up for 252 days, VaR_95 looks
  at the 13th-most-negative return which is still positive),
  the function returns a NEGATIVE number ("the tail day was
  still positive"). The UI styles this cell muted (vs the
  red coloring used for real losses) so the researcher
  understands the signal — methodology Contract rule.
- **Window selector intentionally has no "Max" option.** Unlike
  the Drawdown card (which benefits from arbitrarily long
  history for episode identification), VaR / CVaR are
  interpretable only relative to a fixed lookback. 60d / 252d /
  504d cover short-term / 1-year / 2-year horizons. Adding
  more requires explicit product justification.
- **Histogram bin range and count are fixed.** 30 bins,
  `[min(r), max(r)]` auto-fit. Symmetric padding would
  understate the tail; outlier trimming would hide the most
  important data points. UI consumers must accept the
  engine-decided binning verbatim.
- **Self-fetching component pattern** (RiskPanel doesn't own
  the card's state) matches Drawdown card pattern from
  US-13.2; concurrent fetches from stress + drawdown +
  distribution on snapshot change are all fine — the URL-routed
  `makeRoutedFetch` test helper in `RiskPanel.test.tsx`
  handles all three concurrently.
