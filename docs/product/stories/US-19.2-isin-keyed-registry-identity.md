# US-19.2: ISIN-keyed registry identity

**Epic:** Epic 19 — Instrument Identity Integrity
**PRD:** [`epic-19-instrument-identity-integrity.md`](../prd/epic-19-instrument-identity-integrity.md)
**Status:** Done
**Last updated:** 2026-06-11

## Story

As a **portfolio researcher**, I want each holding's broker-statement ISIN
validated against an authoritative expected ISIN stored in the instrument
registry, so that a ticker→fund mislabel (the `DFND` case) is caught by a
**definitive global identifier**, not only by the conservative
description-token heuristic — and a wrong identity can never silently survive
an import when the statement itself carries the proof.

## Context

US-19.1 shipped the description-consistency detector
(`app/services/instrument_identity.py`): it flags a holding when the broker
description and registry fund name share **zero** significant tokens. That is
deliberately conservative — it misses mislabels that share words (e.g. two
different "Defense UCITS ETF" products). The statement, however, already
carries each holding's **ISIN** (both the Interactive Brokers and Freedom24
parsers populate `ImportedInstrument.isin`), and the ISIN is the definitive
identifier: same ISIN = same fund, different ISIN = different fund, no
heuristics. The registry has no ISIN data today.

This story (1) adds an optional `isin` to registry instrument definitions,
seeded with **authoritative values sourced from the real committed statements**
(IB2026/FF2026 — e.g. `DFND → IE000U9ODG19` iShares Global Aerospace & Defence,
distinct from `DFNS → IE000YYE6WK5` VanEck Defense: the exact near-miss pair the
heuristic could confuse); (2) extends the identity detector with an ISIN
comparison that fires on a definitive mismatch; and (3) surfaces it through the
**same two channels** as US-19.1 — a new Import Admission check and the
Exposure Data Sources panel's identity warnings. Flag only — never
auto-corrects (PRD non-goal). Evidence-gated: if either side lacks an ISIN
(registry not yet seeded, or statement didn't carry one), the check **skips
that holding** — absent evidence is withheld, never treated as a failure or a
pass-by-fabrication.

Implementer must read:
- `app/services/instrument_identity.py` — the US-19.1 detector this extends.
- `app/instruments/registry.py` — `_instrument(...)` constructor +
  `INSTRUMENT_DEFINITIONS` (where `isin` is added).
- `app/services/import_admission.py` —
  `_build_instrument_description_consistency_check` (the pattern for the new
  ISIN check) + `build_import_admission_summary`.
- `app/schemas/provenance.py` — `InstrumentIdentityMismatch` (schema change
  first, per convention) + `docs/contracts/provenance-fields.md` +
  `apps/desktop/src/features/portfolio/types.ts` (mirror).
- `apps/desktop/src/features/portfolio/DataSourcesPanel.tsx` — the identity
  warning render (small extension for the ISIN kind).

## Acceptance criteria

- [x] AC1 — `InstrumentIdentityMismatch` carries the evidence class: a `kind`
  field (`"description"` | `"isin"`; existing description mismatches keep
  working with `kind="description"`), and for ISIN mismatches the
  `statement_isin` and `expected_isin` values are present so the researcher can
  verify the claim directly. TS type and `provenance-fields.md` mirror the
  schema in the same pass.
- [x] AC2 — Registry instrument definitions accept an optional `isin`; the
  symbols present in the committed real statements are seeded with their
  statement-sourced ISINs (the 16 registry-known UCITS/identity-sensitive
  lines: `DFND`, `DEFS`, `IDFN`, `VUAA`, `SXRV`, `ICOM`, `VDST`, `SGLD`,
  `ISLN`, `SEMI`, `IUIT`, `IAUP`, `COPX`, `BTEC`, `IUFS`, `IUHC` — `DFNS` is
  not a registry entry, so it has nothing to seed). A guard test
  proves every seeded ISIN equals the ISIN the committed statements actually
  carry for that symbol (the registry can never drift from the source evidence).
- [x] AC3 — A holding whose statement ISIN differs from the registry's expected
  ISIN (after uppercase/whitespace normalization) is flagged as an
  `kind="isin"` identity mismatch — including when the description heuristic
  would pass (shared tokens). The simulated `DFND`-mislabeled-as-VanEck case is
  caught by ISIN evidence.
- [x] AC4 — Evidence-gating is explicit: no ISIN mismatch is raised when the
  registry entry has no seeded ISIN, when the statement instrument carries no
  ISIN, or when the symbol is not registry-known — absent evidence is never
  fabricated into a pass or a failure (trust guardrail).
- [x] AC5 — The Import Admission Review gains a
  `instrument_isin_registry_consistency` check: `pass` when every comparable
  holding's ISINs agree; `warn` (trust impact `degraded`) naming the mismatched
  symbols when any disagree — same severity model as the US-19.1 description
  check (flag, never block/auto-correct).
- [x] AC6 — The Exposure **Data Sources panel** renders ISIN mismatches in the
  existing identity-warnings block, showing the symbol and both ISINs
  (statement vs expected), visually consistent with the US-19.1 description
  warnings; no warning row appears when there are none.
- [x] AC7 — Re-importing the real committed statements produces **zero** ISIN
  mismatches (the registry seeds come from those statements — proves no false
  positives), and the full backend + frontend suites stay green.

## Out of scope

- **Auto-correction / registry rewrite on mismatch** — flag only (PRD non-goal;
  correcting a mapping stays a human/code change).
- **External ISIN lookup** (FMP/Yahoo don't return ISINs for EU UCITS funds) —
  evidence is the statement only.
- **Blocking/withholding the import on an ISIN mismatch** — the admission
  decision model stays warn/degraded like US-19.1; escalating a definitive
  mismatch to `withheld` is a product decision deliberately deferred.
- **Seeding ISINs for symbols absent from the committed statements** — no
  authoritative source; unseeded entries are simply skipped (AC4).
- **Using ISIN for symbol resolution / price fetching** (Epic 18 owns
  resolution; identity and resolution stay separate concerns).

## Notes / decisions

- **Why ISIN evidence is definitive while description is heuristic:** ISIN
  (ISO 6166) is the globally unique security identifier printed on the
  statement by the broker; equality/inequality is exact. The description
  comparison must tolerate formatting noise and so can only flag *disjoint*
  identities. The two checks are complementary: ISIN catches everything where
  both sides have evidence; description covers unseeded registry entries.
- **Why seeds come from the statements (not typed by hand from fund
  factsheets):** the statement is the broker truth-class source this product
  already trusts for identity; test (8) pins registry⇄statement agreement so a
  typo'd seed cannot pass. The DFND/DFNS pair in the real IB statement
  (`IE000U9ODG19` iShares vs `IE000YYE6WK5` VanEck) is the live validation case.
- **Default `kind="description"`** keeps the schema change backwards-compatible
  for any persisted/older payloads and the existing frontend rendering.
- No financial formula; no academic citation; methodology untouched (identity
  integrity is a truth-class concern, documented in the architecture doc's
  identity section, not the finance methodology).
