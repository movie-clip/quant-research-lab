# US-31.4: Stop the bare-symbol fallback substituting a different security for SEMI

**Epic:** Epic 31 — Ledger Replay Correctness
**PRD:** [`epic-31-ledger-replay-correctness.md`](../prd/epic-31-ledger-replay-correctness.md)
**Status:** Done
**Last updated:** 2026-07-25

## Story

As a **portfolio researcher** holding the iShares MSCI Global Semiconductors
UCITS ETF (`SEMI`, LSE, GBP), I want its price history to come from that fund
or from nothing — never from a different US-listed security that happens to
share the ticker — so that my portfolio's value, correlations, and factor
loadings are measured against the fund I actually hold.

## Context

PRD finding **F-5 (High)**, verified 2026-07-24. `SEMI`'s resolution rule
(`app/core/symbols.py:44`) lists `("SEMI.L", "SEMI")`. `SEMI.L` — the held LSE
UCITS line — is unavailable on the current FMP plan (402), so resolution falls
through to the **bare `SEMI`**, which on FMP is a **different security**
(confirmed: `last_fetch_meta.resolved_symbol == "SEMI"`, 2026-06-30 quote
**40.58** vs the held line's **17.998 GBP**, a 2.2547× ratio). On the committed
IB2026 portfolio this overstates a 4.4%-of-NAV holding by **+$2,506.93** — the
single largest term in the replay's terminal market-value drift.

This is the **same wrong-fund collision class** already fixed twice: `DFND`
(US-18.3 — never map to the VanEck lines) and `CIBR`
(`app/core/symbols.py:49-54` — the bare `CIBR` is the US-listed sister fund, so
it was demoted to a labeled proxy with **no** bare history/quote/holdings
candidate). `SEMI` is the one unguarded survivor. The fix mirrors `CIBR`
exactly: remove the bare `"SEMI"` from the quote/history/holdings candidates so
`SEMI.L` is the only real-data candidate.

**Verified post-fix behaviour** (checked against the live providers while
authoring): with the bare candidate gone, FMP 402s on `SEMI.L` and the
existing yfinance secondary-provider fallback (`market_data.py:335-345`, added
in US-18.1, which only runs on the **real-symbol** candidates and never on
proxies) returns the **correct** `SEMI.L` line — **17.998 GBP** on 2026-06-30,
matching the statement close to the cent. So after this story the holding is
valued from the right fund; it is merely carried in **GBP unconverted**, which
is finding **F-4**'s concern and is deliberately left to **US-31.5**. If
`SEMI.L` were unavailable from **both** providers, the holding would carry no
price and be disclosed via US-31.2's `unpriced_replay_symbols` — an honest
"unavailable", never the wrong fund.

The frozen golden fixture is keyed by requested symbol and still holds the
**wrong** `SEMI` series (40.58), because `resolve_symbol_candidates` only
governs the **live** path — so this story requires a deliberate re-capture
(`export_dashboard_goldens --capture`) after the rule change.

## Notes / decisions

- **No new formula, no schema change, so no methodology/contract edit** beyond
  marking F-5 resolved and noting the guard in the FMP skill's UCITS table.
  The story corrects which *security* a price series comes from; it changes no
  formula.
- **Why remove the bare candidate rather than add `SEMI.L` to overrides:** the
  rule already leads with `SEMI.L`; the defect is purely the *fallthrough* to
  bare `SEMI`. Removing it is the minimal, precedent-matching change (CIBR did
  exactly this) and keeps the yfinance secondary provider — which fetches the
  correct `SEMI.L` GBP line — as the effective source.
- **Why not add bare `SEMI` as a proxy** (as CIBR did with bare `CIBR`): CIBR's
  US sister fund is a *known, deliberate* cybersecurity proxy. Bare `SEMI` on
  FMP is an **unidentified** different security (the audit established only that
  it is *not* the held fund, ratio 2.2547). SEMI already has two verified
  semiconductor proxies (`SOXX`, `SMH`); introducing an unidentified security
  as a third proxy would reintroduce a wrong-fund risk in proxy position.
  Leave the proxies as-is.
- **The stale-cache gotcha (for T-31.4.2):** requesting `SEMI.L` against a
  polluted local FMP cache can return the *previously cached bare-SEMI* rows via
  the FMP client's stale-cache fallback (observed during authoring). This is a
  local-cache artifact from prior capture runs, not production logic — clear
  the `SEMI`/`SEMI.L` cache entries before `--capture`, and confirm the
  captured `SEMI` series shows the GBP ~17–18 range, not ~40, before committing
  the fixture.
- **Reproduction evidence** lives in `test_ledger_replay_audit.py`'s
  `test_f5_*` pin (added by the F-4/F-5 audit) and the PRD F-5 row.
