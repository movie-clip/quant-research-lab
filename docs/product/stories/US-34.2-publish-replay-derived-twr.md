# US-34.2: Publish the replay's time-weighted return under an explicit `replay_derived` trust state

**Epic:** Epic 34 — An Answerable Dashboard: Reachable Trust States
**PRD:** [`epic-34-answerable-dashboard-and-reachable-trust.md`](../prd/epic-34-answerable-dashboard-and-reachable-trust.md)
**Status:** Done (2026-08-13)
**Last updated:** 2026-08-13

## Story

As a **portfolio researcher**, I want the Dashboard to show the time-weighted
return the engine already computes, labelled with the basis it was computed on,
so that I can judge my performance instead of reading five columns of `null`.

## Context

PRD findings **F-1** and **F-1a**. The Dashboard's headline metrics are `null`
in all five ranges on every run because three hardcoded gates in
`dashboard_history_engine.py` — `portfolio_path="unavailable"` (:165),
`_allow_dashboard_drawdown_outputs → False` (:208),
`investor_economics available=False` (:218) — and a proof-admission gate whose
five hard disqualifiers are structural properties of replaying a broker
statement (`inferred_opening_holdings`, `inferred_opening_quantities`,
`terminal_force_reconciliation_present`, `forward_filled_prices`,
`mixed_basis_valuation`).

The effect runs deeper than the summary scalars:
`build_true_performance_series` computes `portfolio_return_pct` only when the
basis is `verified_total_return` (`performance.py:245`), so **all 148 points of
the cumulative return series are null**, and the chart plots portfolio *value*
against benchmark *price*.

**The proof gate is not wrong; it answers a different question.** It certifies a
GIPS-style *verified total return*, which a reconstructed replay genuinely
cannot claim. This story does not weaken it by a single condition. It adds a
rung **below** it: a return computed from the imported replay, published with a
basis that says exactly that, so failing the strict gate stops meaning "no
answer".

Implementer must read:
- PRD F-1/F-1a — including the three-hardcoded-gates block.
- `app/analytics/performance.py` → `build_true_performance_series` and
  `_time_weighted_daily_return` (which already withholds unpublishable days —
  US-31.3/US-33.2 — and must keep doing so).
- `docs/finance/financial-methodology.md` §Portfolio Return Methodology.
- `docs/contracts/dashboard-fields.md` → `return_basis_contract.portfolio_path`.

## Acceptance criteria

- [x] AC1 — **The portfolio return basis is classified, not asserted.** The
  hardcoded `portfolio_path="unavailable"` is replaced by a function of the run:
  `verified_total_return` when the proof admission grants an exact slice,
  `replay_derived` when the imported replay produced daily states, and
  `unavailable` when it produced none. On the committed IB2026 statement it is
  **`replay_derived`**.

- [x] AC2 — **The cumulative return series is computed on the new basis.**
  `build_true_performance_series` populates `portfolio_return_pct` for
  `replay_derived` exactly as it does for `verified_total_return` — same chain,
  same withholding. On IB2026, **141 of 148** points carry a return; the 7 gaps
  are exactly US-31.3's reconciled terminal day and US-33.2's six unbacked-cash
  days.

- [x] AC3 — **Withholding is unchanged.** `_time_weighted_daily_return` still
  returns `None` for any day where `return_is_publishable` is false, so the
  reconciled terminal day and the six unbacked-cash days remain absent from the
  chain on the new basis. A test asserts those exact dates are still missing.

- [x] AC4 — **Every range publishes a time-weighted return**, and the `All`
  window's figure is explainable against the statement's own **4.765666%** —
  the two are computed on different bases (the replay's chained daily TWR vs the
  broker's own calculation) and are pinned with the measured difference stated,
  not silently assumed equal.

- [x] AC5 — **The number carries its trust, visibly.** Each range's summary
  reports the basis its TWR was computed on, and the Dashboard renders a
  `replay_derived` return with a visible marker distinguishing it from a
  verified one. A researcher can never mistake this figure for a verified total
  return.

- [x] AC6 — **The strict gate is untouched and still refuses.** On IB2026
  `investor_economics_status` stays `withheld`,
  `portfolio_proof.verified_total_return_emitted` stays `False`, and
  `portfolio_path` is **not** `verified_total_return`. A test asserts all three
  — this story must be incapable of promoting the imported path to verified.

- [x] AC7 — **Max drawdown is deliberately NOT unlocked here.**
  `_allow_dashboard_drawdown_outputs` stays `False`, and a test pins that
  `max_drawdown_pct` is still `null`.

  > **Scope narrowed during implementation.** The AC originally unlocked the
  > drawdown alongside the return. Its stub takes two parameters it never reads
  > — `benchmark_rows` and `symbol_price_histories` — which say the intended
  > gate was about whether the **price inputs are adjusted**, not about whether
  > the replay is publishable. A drawdown chained from unadjusted closes is a
  > *price* drawdown and overstates the loss on dividend-paying holdings. That
  > is a methodology question this story did not research, so it moves to its
  > own story rather than riding along on a rung it does not belong to.

- [x] AC8 — **Nothing else unlocks.** `benchmark_return_pct` and
  `excess_return_pct` stay `null` on this statement: they depend on the
  benchmark's own basis, which is US-34.5's story. A test pins that they are
  still withheld, so this story cannot be read as a general unlocking.

- [x] AC9 — **A snapshot with no replay states still reports `unavailable`**
  and publishes nothing — the classification is a real signal, and the
  fail-closed path is intact.

## Findings surfaced while implementing

Publishing the numbers exposed three defects that being `null` had hidden. All
three are recorded rather than quietly fixed, because each is evidence about how
the gate was masking problems.

1. **Every window reported the same return.** `portfolio_return_pct` is
   cumulative from the series start, so slicing it and reading the last point
   gave since-inception for 1M, 3M, YTD, 1Y and All alike (2.43% across the
   board). Fixed by re-basing on the window's own first point.

2. **Windowed ranges were anchored at the series start.**
   `_slice_performance_series` took `next(state for state in daily_states ...)`
   — the *first* qualifying state in the whole series, not the last one before
   the window. The 1M slice plotted a 21-day tail against a seven-month-old
   anchor. Fixed by searching in reverse; this also moved `start_value` and
   `money_weighted_return_pct` for windowed ranges, which is why the FF2026
   truth test needed re-pinning.

3. **The money-weighted return contains the reconciliation adjustment**
   (recorded as **Epic 34 F-7**, story US-34.6). On FF2026, TWR is 0.12% and
   MWR is 3.75% with zero flows; the whole gap is the reconciled terminal day.
   TWR withholds it; MWR reads `end_value`, which *is* the reconciled value.
   The identity `0.12 + 3.63 = 3.75` is now pinned. Not fixed here — it is a
   separate path with its own guardrail question.

## Notes / decisions

- **No new formula.** The chained cash-flow-neutral daily TWR is already
  specified in `financial-methodology.md` §Portfolio Return Methodology and
  already implemented; this story changes *when it is published*, not how it is
  computed. The methodology entry gains the publication rung, not a formula.
- **Naming.** `replay_derived` names the **basis** (where the number came
  from), and the trust ladder word for it is `degraded` — it is a real
  measurement on reconstructed inputs. Both are surfaced: the basis on
  `return_basis_contract`, the trust on the rendered metric. Reusing
  `unverified_adjusted_proxy` would be wrong: nothing here is a proxy.
- **Why the `All` TWR will not equal the statement's 4.765666%.** The broker
  computes its own TWR over the full statement period from 2026-01-01; the
  replay chains daily returns from 2026-01-08 (its first valuable date) and
  withholds 7 days. AC4 requires the difference to be *stated and pinned*, not
  assumed away — if it is large, that is a finding for the epic, not a number to
  massage.
