## Story

As a **portfolio researcher relying on the Exposure tab's sector breakdown**,
I want the sector-taxonomy lookup, the market-data cache-status diagnostics,
and the test suite behind them to hold up under drift and reuse, so that a
future FMP formatting change doesn't silently reclassify my holdings as
Unclassified, a diagnostic engineers rely on to reason about cache behaviour
isn't lying, and the next sector-classification test doesn't have to
reinvent — or subtly diverge from — the same fake three times over.

## Context

Three findings, each already independently diagnosed with file:line evidence
by earlier lanes in the US-37.1 run. Read each source in full before drafting
any implementation:

1. **Taxonomy-matching robustness gap** —
   `10-quant-audit.md` (`2026-08-21-dynamic-sector-classification` run)
   § Findings, FINDING 2 (MINOR). `SECTOR_TAXONOMY_MAP.get(profile["sector"])`
   in `services/quant-engine/app/instruments/equity_sector_resolution.py:74`
   is a raw, case-sensitive `dict.get()` with no normalization of the FMP
   `sector` string — unlike the ISIN side of the same resolver, which
   normalizes via `normalize_isin` (upper + strip). Verified: sector values
   `"technology"`, `"TECHNOLOGY"`, `" Technology"`, `"Technology "` all four
   fall through to `(None, "unavailable")` today instead of resolving to
   `"Technology"`. Fails safe today (degrades to Unclassified, never
   fabricates) — the risk is a *silent* future regression: an FMP-side
   casing/whitespace change would move previously-classified equities into
   Unclassified with no test catching it and no error surfaced.

2. **Pre-existing cache-metadata bug** — `02-quant-research.md` § risks.
   `MarketDataService.get_company_profile`'s
   `last_fetch_meta[...]["cached"]` (`services/quant-engine/app/services/market_data.py:474`)
   is hardcoded `True` on every successful call, regardless of whether the
   FMP profile response actually came from the on-disk cache or required a
   live fetch. Pre-existing (not introduced by US-37.1), noticed but not
   investigated by the research brief. `get_company_profile` itself has no
   direct unit-test coverage today (every existing test mocks the whole
   `MarketDataService`), so this has never been pinned either way.

3. **Test-fixture duplication** — `09-test.md` § risks. The FMP-profile
   fake/stub pattern (`_FakeMarketData` in `test_instrument_enrichment.py`
   and `test_equity_sector_resolution.py`; `_SpyMarketData` in
   `test_instrument_registry.py`) is now hand-duplicated across all three
   files, each a small, near-identical re-implementation (configurable
   per-symbol response, optional raise-on-symbol, call recording) with no
   shared scaffolding in `app/tests/fixtures.py` — the project's own
   designated home for exactly this kind of shared test builder (US-21.2).

**Explicitly out of scope** (do not touch, per the human's scoping decision):
ETF look-through / constituent classification (F-B: `analytics/risk.py`'s
`build_lookthrough_sector_exposure` / `_infer_sector_from_sources`), and both
epic-24 tech-debt-register rows — `instruments/registry.py:45-48,180-261`
(the keyword sector classifier) and `analytics/risk.py:1485-1499,1537-1549`
(the hardcoded proxy-ticker sector inference). None of this story's ACs or
tickets reach any of those three.

Implementer must also read: `docs/product/stories/US-37.1-dynamic-equity-sector-classification.md`
(the story this follows up on — same resolver, same test suite) and
`services/quant-engine/app/instruments/equity_sector_resolution.py` in full
(small file, the whole resolution function is in view at once).

## Acceptance criteria

- [x] AC1 — In `resolve_equity_sector`
  (`services/quant-engine/app/instruments/equity_sector_resolution.py`), an
  FMP `sector` string that differs from a `SECTOR_TAXONOMY_MAP` key only by
  leading/trailing whitespace, or only by letter case, resolves to the same
  mapped sector the exact-match key would — it is never treated as an
  unmapped sector and never falls through to `unavailable` on that basis
  alone.
- [x] AC2 — A `sector` string genuinely absent from the taxonomy map (not a
  casing/whitespace variant of a known key) still falls through to
  `unavailable` exactly as it does today — the normalization in AC1 narrows
  what counts as "unmapped," it does not widen what counts as "mapped."
- [x] AC3 — `MarketDataService.get_company_profile`'s cache-status
  diagnostic — the `"cached"` value under `last_fetch_meta[symbol]`, readable
  via `get_last_fetch_meta` — reports `True` only for a call whose FMP
  profile response was actually served from the cache, and `False` for a
  call that required a live fetch.
- [x] AC4 — Calling `get_company_profile` twice for the same symbol within
  the cache's TTL reports the first call's `cached` value as `False` (or
  whatever the true miss/hit state of that specific call was) and the second
  call's as `True`, distinguishing the two rather than reporting the same
  hardcoded value for both.
- [x] AC5 — `test_instrument_enrichment.py`, `test_equity_sector_resolution.py`,
  and `test_instrument_registry.py` each import their FMP-profile
  fake/stub for `MarketDataService.get_company_profile` from one shared
  implementation in `app/tests/fixtures.py`, rather than each defining its
  own local class. The shared implementation supports, at minimum, the union
  of what the three current local fakes need: a configurable per-symbol
  response (a profile dict or `None`), an optional set of symbols that raise
  instead of returning, and a record of every symbol looked up — so no
  existing test's setup has to change shape to adopt it, only its import.

## Test plan

Backend (pytest):

- `test_equity_sector_resolution.py` — a dedicated regression test (or a
  parametrized set) pinning at least one casing-variant case (e.g. FMP
  returning `"TECHNOLOGY"` or `" Technology"`) resolving to the same mapped
  sector as the exact-case key, per AC1. Include a case confirming a
  genuinely unmapped sector string still falls through to `unavailable`
  (AC2), so the normalization is proven not to have widened the map.
- `test_market_data.py` — new coverage of `MarketDataService.get_company_profile`
  itself (this method has none today; existing profile-touching tests all
  mock the whole service, not the client/cache layer beneath it). Covers a
  cache-miss call reporting `cached: False` and a subsequent cache-hit call
  for the same symbol reporting `cached: True` (AC3, AC4). Whatever
  mechanism the fix uses to learn the cache's hit/miss status is this
  ticket's implementation choice — the test should assert the *reported*
  value, not a particular internal call sequence.
- `fixtures.py` gains the shared FMP-profile fake (AC5); `test_instrument_enrichment.py`,
  `test_equity_sector_resolution.py`, and `test_instrument_registry.py` are
  updated to import it instead of defining `_FakeMarketData` / `_SpyMarketData`
  locally. Every existing test in all three files must stay green with no
  behavioural change — this is a refactor of test scaffolding, not a change
  to what is tested.

Regression / guardrail:

- No existing test asserts the current (wrong) hardcoded `cached: True` for
  the `"profile"` `last_fetch_meta` entry specifically, so AC3/AC4 carry no
  known conflicting-assertion risk — confirmed by search before drafting
  this story, worth re-confirming at implementation time.
- `python scripts/run_all_tests.py` green, including the dead-code gate (a
  fixture consolidation that leaves an unused local class behind would trip
  vulture/knip).

## Notes / decisions

- **Why normalization covers case as well as whitespace.** The work order
  left this to this draft's judgment. FINDING 2's own reproduction tested
  four variants — `"technology"`, `"TECHNOLOGY"`, `" Technology"`,
  `"Technology "` — spanning both axes, and explicitly framed the risk as
  "a future FMP formatting change (provider-side casing/whitespace drift)."
  All eleven `SECTOR_TAXONOMY_MAP` values are consistently Title Case today
  (confirmed live against 15+ distinct FMP tickers across both the research
  brief and the audit), so a case-insensitive comparison costs nothing
  against current data and directly defends against the drift the finding
  names. Whitespace-only stripping would leave the casing half of the
  reproduced finding unaddressed.
- **Why the cache-flag fix is scoped to `get_company_profile` only.** The
  same hardcoded-`True` shape exists in four other `MarketDataService`
  methods (see Out of scope). The source finding (`02-quant-research.md`
  § risks) named only `get_company_profile`, noticed incidentally while
  researching a different question, not investigated as a systemic pattern.
  Widening the fix to all five call sites was not diagnosed by any source
  document this draft was given, so it stays out — flagged in `risks` for a
  human to decide whether it is worth its own follow-up.
- **Two backend tickets, not one.** T-37.2.1 and T-37.2.2 touch unrelated
  files and functions with no shared code or ordering dependency; splitting
  them lets either land independently and keeps each PR's diff legible
  against a single finding.
- **No design/tech-lead pass ticketed.** All three findings are
  narrow, single-function fixes with no schema change and no new field —
  the express-lane criteria this project's `project.md` § "The express lane"
  describes (defect in shipped behaviour, fix inside one lane, no schema
  touched) appear to fit T-37.2.1 and T-37.2.2. That routing call belongs to
  whoever dispatches these tickets, not this draft — noted here so it isn't
  missed.
