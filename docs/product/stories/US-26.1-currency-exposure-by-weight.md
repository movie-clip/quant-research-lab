# US-26.1: Currency exposure by weight (snapshot)

**Epic:** Epic 26 — Currency Exposure & Risk
**PRD:** [`epic-26-currency-exposure-and-risk.md`](../prd/epic-26-currency-exposure-and-risk.md)
**Status:** Done
**Last updated:** 2026-08-11

## Story

As a **portfolio researcher**, I want to see what fraction of my portfolio is
denominated in each currency, and how much of it is not in my base currency, so
that I can see the currency risk I am already carrying — today the product
imports `currency` on every position and shows it nowhere.

## Context

Epic 26's MVP story, and the epic's only ready one (US-26.2 is explicitly
not-ready pending a research brief and empirical verification of
`get_fx_history`).

`ImportedPosition.currency` and `ImportedStatement.base_currency` are captured
on every import and aggregated by nothing. On the committed IB2026 portfolio
that hides real exposure: 16 USD positions, 3 EUR, 1 GBP. A researcher holding
UCITS ETFs traded in EUR/GBP cannot answer "how much of my portfolio is not in
USD?" from any tab.

This is **snapshot analytics** — current holdings only, no historical prices,
no market-data call. Same truth class as sector exposure.

### Corrections to the research brief's formula

*(Two were identified while writing this story; a third emerged during
implementation — see AC3 and Notes.)*

The methodology's §Currency Exposure block was written 2026-07-04. All three
problems below are fixed in this story, and the methodology corrected.

**Correction 1 — the denominator must be base-currency converted.** The brief
specifies raw `market_value` in both numerator and denominator. That is exactly
the **F-7 defect** US-30.5a fixed as Critical: raw-summing values across
currencies mixes units. On IB2026 the raw sum is **$58,588.76** against the
FX-converted **$61,238.53**, which reproduces the statement's own `stock_total`
to the cent — the statement is the arbiter. Shipping the brief's formula
verbatim would reintroduce a fixed Critical bug **on the very card whose
subject is currency**, where it would be most misleading.

The correct construction converts each position to the base currency **first**,
then groups by the currency the position is *denominated in*:

```text
currency_weight_c = Σ_i base_value_i   (holdings i with currency_i = c)
                    ──────────────────────────────────────────────────
                    Σ_j base_value_j   (all holdings j)
```

Group by original currency; measure in one unit. `analytics/currency.py`
already provides `position_base_market_values` and its FX disclosure — reuse
them rather than re-deriving conversion (the US-31.2 "one shared chain" lesson).

**Correction 2 — the null-currency rule is self-contradictory.** The brief says
a null-currency position is *"excluded from both numerator and denominator"*
**and** *"surfaced as an 'unclassified' residual weight so the total still
reconciles to 100%"*. Those cannot both hold: excluded from the denominator,
the classified weights already sum to 100% and the residual is a share of
nothing.

**Correction 3 (found during implementation) — the bucket is unreachable, and
the real fabrication is upstream.** `ImportedPosition.currency` is
`str = Field(min_length=3, max_length=3)`, so a snapshot carrying a
currency-less position cannot be constructed at all — Pydantic rejects it.
Building an `unclassified` bucket would be dead code behind a UI state that can
never render.

The fabrication the brief was reaching for is real, but it happens **before**
this analytic: `portfolio_snapshot_builder.py:43` coerces
`currency=item.currency or request.base_currency or 'USD'`, so a request-path
position that stated no currency arrives already labelled. This module cannot
see that and must not pretend to. Logged as **US-26.3 (Med)**; a schema test
pins the constraint so relaxing it forces the question to be answered rather
than silently mislabelling value.

Implementer must read: `docs/finance/financial-methodology.md` §Currency
Exposure (and its "Base-currency weighting rule" under §Risk Contribution and
Concentration); `app/analytics/currency.py`;
`app/schemas/exposure.py` (`ExposureResult`, the `fx_*_currencies` tiers);
`docs/contracts/exposure-fields.md`; `.claude/skills/ui-polish/SKILL.md`.

## Acceptance criteria

- [x] AC1 — The Exposure tab shows a **Currency Exposure** card listing each
  currency the portfolio holds with its weight, sorted by weight descending,
  plus an explicit **non-base-currency** total.
- [x] AC2 — Every weight is computed on **base-currency-converted** market
  values in both numerator and denominator (Correction 1). The card's
  denominator equals the same `total_base_market_value` the rest of the
  Exposure tab uses — the two can never disagree.
- [x] AC3 — ~~A position with **no currency** is counted in the denominator and
  reported in an explicit `unclassified` bucket.~~ **Superseded during
  implementation (Correction 3).** `ImportedPosition.currency` is
  `str = Field(min_length=3, max_length=3)` — a currency-less position cannot
  exist in a snapshot, so the bucket is unreachable and building it would be
  dead code with a UI state that can never render. The fabrication the brief
  anticipated is real but happens **upstream**, in the request-path snapshot
  builder (`currency or base_currency or 'USD'`), where this analytic cannot
  see it. Logged as **US-26.3**; a schema test pins the constraint so relaxing
  it forces the question to be answered rather than silently mislabelling
  value.
- [x] AC4 — When `base_currency` is null the per-currency weights still render
  but the non-base total is **null** ("—"), never `0` — there is no baseline to
  compare against, and zero would read as "no currency risk".
- [x] AC5 — **FX degradation is visible on the card itself.** A currency
  converted at the statement's static period-end rate, and a currency carried
  **unconverted** because no rate exists, are surfaced (reusing the existing
  `fx_static_rate_currencies` / `fx_fallback_currencies` tiers). An unconverted
  currency's own weight is the least trustworthy number on this card, so it is
  never presented as if fully converted.
- [x] AC6 — The card renders a **`Synthetic`-free** presentation: this is
  snapshot analytics over broker-truth composition, not synthetic history, so
  it carries no `Synthetic` TrustBadge (the US-30.6 precedent for the
  Concentration Pack).
- [x] AC7 — **No new market-data dependency.** The analytics function takes
  only the snapshot; no `MarketDataService` call is added anywhere on this path
  (the PRD's stated success signal, verifiable by inspection and pinned by a
  test).
- [x] AC8 — A portfolio with only base-currency positions shows a single 100%
  row and a non-base total of exactly 0% — the card is correct in the trivial
  case, not just the interesting one.
- [x] AC9 — On the committed IB2026 statement the card reproduces the expected
  split, pinned exactly: the three EUR and one GBP holdings against 16 USD, on
  the $61,238.53 converted denominator.
- [x] AC10 — `dashboardGoldens.ts` is byte-identical (this adds an Exposure
  surface; it changes no dashboard-history output).

  consumes it.

## Notes / decisions

- **Why a new module rather than `risk.py`.** The methodology already directs
  this to its own file, and `risk.py` is the project's most overloaded module.
  Currency exposure shares its conversion inputs with the other weight surfaces
  but is a distinct concern.
- **The card's most important honesty property** is AC5. A currency carried
  *unconverted* contributes a raw foreign number to a base-currency
  denominator, so its own weight is the least reliable figure on a card whose
  entire subject is currency. That must be visible, not buried in a tooltip —
  it is the same class of degradation US-27.8 and US-30.2 established
  disclosure tiers for.
- **Both formula corrections are recorded in the story rather than silently
  applied**, per the project's practice of correcting a brief in the open.
  Correction 1 in particular is the difference between a card that agrees with
  the rest of the Exposure tab and one that quietly contradicts it by 4.33%.
- **Academic precedent** (for the methodology section — this is a composition
  measure, not a new estimator):
  - Solnik, B. (1974). "An equilibrium model of the international capital
    market." *Journal of Economic Theory*, 8(4), 500–524 — currency as a
    distinct exposure in an international portfolio.
  - Perold, A.F. & Schulman, E.C. (1988). "The Free Lunch in Currency Hedging."
    *Financial Analysts Journal*, 44(3), 45–50 — why currency exposure is
    measured and reported separately from asset exposure.
  - CFA Institute (2020). *GIPS for Firms*, §2.A.1 — portfolio values are
    stated in a single base currency, which is why the denominator converts.
