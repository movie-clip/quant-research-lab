# US-36.1: A blocked commit stays blocked, regardless of which tool issued it

**Epic:** Epic 36 — Findings-First Doc & Gate Hygiene
**PRD:** [`epic-36-findings-first-doc-and-gate-hygiene.md`](../prd/epic-36-findings-first-doc-and-gate-hygiene.md)
**Status:** Done (2026-08-20)
**Last updated:** 2026-08-20

## Story

As a **researcher relying on this project's own integrity claims**, I want the
test-freshness commit gate to hold no matter which tool issues `git commit`, so
that a stale, unverified tree can never be committed silently by tool choice
alone.

## Context

Finding **F-R1** (`docs/product/review-2026-08-20-findings.md`). The
`PreToolUse` hook that blocks `git commit` until `.claude/.last-test-pass` is
fresher than every changed non-`.md` file was wired with `"matcher": "Bash"`
only (`.claude/settings.json:19-29`, calling `scripts/hooks/pre_commit_gate.py`).
This environment also exposes a PowerShell tool that can run `git commit`
directly — a commit issued through PowerShell never triggered the hook, so the
freshness gate could be bypassed by tool choice alone, with no
`--no-verify`-style signal that it happened.

This was worse than a plain gap: both `CLAUDE.md` (repo root) and
`<agenticRoot>/projects/portfolio/project.md` asserted, in the "Mechanical
gates" section, that a real git-level hook already closed this gap, "fixed
2026-08-20." Confirmed false by two independent lanes (`Glob`/repo-wide
`Grep`): neither `scripts/githooks/pre-commit` nor
`scripts/hooks/git_pre_commit.py` existed anywhere in the repo before this
story. See the Epic 36 PRD's "meta-finding" section for how both files were
corrected twice in the course of this run — once as an interim "gap is open"
statement, once as the final accurate description once this story's fix
landed.

## Design decision (tech lead, `05-technical-plan.md`)

**Build the real git-level hook**, not a mirrored PowerShell matcher on the
existing Claude Code `PreToolUse` hook. Rationale: a `PreToolUse`-matcher fix
only ever covers tools the harness explicitly enumerates *today* — add a third
tool tomorrow (a raw terminal passthrough, a different IDE integration) and
the identical gap reopens silently, the same failure class this epic exists to
close. A git-level hook fires on `git commit` regardless of the invoking
process, satisfying AC1's "regardless of which tool issued it" as a universal
property rather than an enumerated list. It also matches what `CLAUDE.md` and
`project.md` already (falsely) described — building anything else would have
created a second doc/code inconsistency on top of the one being fixed.

The residual gap this decision creates — `core.hooksPath` is local git config,
not committed, so a fresh clone has it unset until something sets it — is
closed by making `scripts/run_all_tests.py` idempotently set it
(`git config core.hooksPath scripts/githooks`) on every run
(`ensure_git_hooks_wired()`), so any legitimate dev/agent session self-heals
the wiring. The existing Bash-matched `PreToolUse` hook stays as a
faster-feedback duplicate and a safety net for the brief window before the
bootstrap has run in a fresh clone.

## Acceptance criteria

- [x] AC1 — A `git commit` issued through the PowerShell tool, on a tree where
  `.claude/.last-test-pass` is missing or stale relative to a changed
  non-`.md` file, is **blocked** — the commit does not complete.
- [x] AC2 — The block in AC1 produces a message naming why the commit was
  blocked (missing marker vs. stale-relative-to-which-file), matching the
  clarity the existing Bash-issued block already gives.
- [x] AC3 — A `git commit` issued through the Bash tool continues to be
  blocked under the same staleness condition, exactly as it did before —
  `pre_commit_gate.py`'s JSON-stdin parsing, `GIT_COMMIT_RE` sniffing and
  exit-code-2 contract are unchanged; `.claude/settings.json` has zero diff.
- [x] AC4 — A `git commit` issued through either tool **succeeds** when
  `.claude/.last-test-pass` is fresh relative to every changed non-`.md` file.
- [x] AC5 — Markdown-only changes remain exempt from the staleness check,
  regardless of which tool issues the commit — the `.md` exemption lives once
  in the shared `_commit_gate.check()`, not duplicated per entry point.
- [x] AC6 — A regression test exists that fails if the staleness **logic**
  regresses, in the spirit of `test_docs_paths.py`'s precedent.
- [x] AC7 — A regression test drives a **real `git commit`** through a repo
  wired the way this one is, and fails if the gate does not fire. Exercises
  the parts AC6 cannot reach: the `scripts/githooks/pre-commit` wrapper, its
  interpreter discovery, `core.hooksPath` resolution, and git's own decision
  to invoke the file.
- [x] AC8 — A regression test fails if `scripts/githooks/pre-commit` is not
  tracked by git, or is tracked non-executable (mode ≠ `100755`), naming
  `git add --chmod=+x` as the fix.

> **AC6 originally read "a regression test exists that fails if tool-coverage
> regresses again" and was marked satisfied by a test suite that never issued a
> single `git commit`.** Every test invoked the hook scripts directly, so it
> proved the staleness logic could not regress while proving nothing about
> whether the gate was reachable — and F-R1 was never a logic bug. Both gates
> passed it; the reviewer explicitly confirmed the tests exercise "the real
> entry points, not a reimplementation," which was true and insufficient. AC7
> and AC8 are the missing halves, added 2026-08-20 after the gap was found in
> post-close review. See "Outcome" for why this is recorded rather than
> quietly corrected.

## Test plan

Backend (pytest):

- `services/quant-engine/app/tests/test_commit_gate.py` (**14 tests** — 10
  original + 4 added post-close for AC7/AC8, see "Outcome" for why). Builds a
  throwaway git repo per test (`tmp_path`-based `hook_repo` fixture) carrying a
  live copy of the three real hook files at the matching relative depth, then
  invokes the **actual enforcement points** — `scripts/hooks/git_pre_commit.py`
  directly (proxy for a PowerShell-issued commit, since git itself calls this
  exact script via `core.hooksPath` regardless of invoking tool) and
  `scripts/hooks/pre_commit_gate.py` with a crafted stdin JSON payload (proxy
  for the Bash path) — not a reimplementation of either script's logic.
- Covers (original 10): missing-marker blocks (both entry points, AC1/AC2),
  stale-file blocks naming the offending filename (both, AC1/AC2), fresh-tree
  allows (both, AC4), `.md`-only-change allows (both, AC5), a Bash-path
  command-sniffing guard (a non-`git commit` command must not trigger the
  check even with no marker present, guarding AC3's unchanged contract), and
  `ensure_git_hooks_wired()` idempotency (calling it twice does not raise and
  leaves `core.hooksPath` correctly set).
- Covers (4 new, AC7/AC8): a `wired_repo` fixture that copies the real
  `scripts/githooks/pre-commit` wrapper byte-for-byte and sets
  `core.hooksPath` to it, then drives an actual `subprocess.run(["git",
  "commit", ...])` — three tests assert a real, git-issued commit is blocked
  when the marker is missing, blocked when it's stale, and allowed when the
  tree is fresh (AC7); one test reads the git index directly
  (`git ls-files --stage`) and asserts `scripts/githooks/pre-commit` is
  tracked at mode `100755`, with both failure messages naming
  `git add --chmod=+x` as the fix (AC8).

Regression / guardrail:

- `python scripts/run_all_tests.py` green (802 backend, 331 frontend, tsc
  clean, dead-code gate strict-clean, at integration-gate time).
- Bash-path behaviour not weakened while fixing the PowerShell path: verified
  by diff (`pre_commit_gate.py`'s refactor removed only the duplicated
  staleness logic, preserved message text verbatim) and by the dedicated
  Bash-path test cases above.

## Outcome (2026-08-20)

Shipped exactly per the design decision above — the git-level hook, not a
matcher mirror. Verified by both gates directly against the working tree, not
by trusting lane reports: `git ls-files --stage scripts/githooks/pre-commit`
shows index mode `100755` (the executable bit survived staging, via the
`--chmod=+x` workaround — a plain `git add` on this Windows checkout
(`core.filemode=false`) would have silently recorded it as `100644`); `git
config --get core.hooksPath` on the gated checkout returns `scripts/githooks`;
`.claude/settings.json` has zero diff, confirming AC3 held at the wiring
level, not just the message-text level.

**Two SHOULD_FIX items carried forward, not blocking:** `_commit_gate.py`'s
`changed_files()` rename-entry parsing (`git status --porcelain=v1 -z`'s
two-field `R` entries) has no dedicated regression test — a `git mv`-then-edit
path through the shared gate logic is currently uncovered. See
`docs/product/epic-roadmap.md` → "Open items" for this and the other
close-out carries from the integration gate.

### Post-close follow-up (2026-08-20) — AC6 was under-specified; T-36.1.4 closes the gap

A later review of this story's own close-out found that **AC6 as originally
written proved the wrong property.** It read "a regression test exists that
fails if tool-coverage regresses again" and was marked satisfied by a test
suite where every one of the original 10 tests invoked the hook scripts
directly (`git_pre_commit.py`, `pre_commit_gate.py`) — never through an actual
`git commit`. That suite genuinely proves the staleness **logic** cannot
regress; it proves nothing about whether the gate is **reachable** — whether
`core.hooksPath` is actually wired, whether the wrapper's interpreter
discovery actually resolves a working Python on a real checkout, whether git
itself actually invokes the file. F-R1, the finding this whole story exists to
close, was never a logic bug — it was exactly this reachability gap, on a
different axis (tool coverage instead of interpreter/wiring). Both the
original integration gate and the original reviewer pass genuinely confirmed
what they checked ("the real entry points, not a reimplementation") — that
was true, and it was the wrong thing to check to close AC6's own stated
promise.

**AC6 was corrected in place** (see the explanatory callout above "## Test
plan") to read "fails if the staleness logic regresses" — narrowing it to what
the original 10 tests actually prove — and **AC7 and AC8 were added** as the
missing reachability half: AC7 drives a real `git commit` subprocess through a
repo wired the way this one is, exercising the wrapper, its interpreter
discovery, `core.hooksPath` resolution, and git's own decision to invoke the
file, none of which AC6's direct-invocation tests can reach. AC8 fails if
`scripts/githooks/pre-commit` is not tracked by git or is tracked
non-executable, closing the specific Windows `core.filemode=false` footgun
this story's own T-36.1.1 had to work around by hand.

**T-36.1.4** implemented the fix this gap-closing found was actually needed
beyond the 4 new tests themselves: the wrapper's interpreter discovery now
fails closed (a clear two-line stderr message naming both tried interpreters,
exit 1) instead of a theoretical silent no-op if neither `python` nor
`python3` resolves, and `ensure_git_hooks_wired()` now checks the hook file
exists before pointing `core.hooksPath` at it, warning instead of wiring a
gate that could never fire.

**Both gates re-ran and passed** against the corrected AC set:
tech-lead INTEGRATION (`01-integration.md` in this follow-up's run,
`2026-08-20-us36.1-followup`) — PASS, 14/14 `test_commit_gate.py` tests, full
`run_all_tests.py` green, plus an independent scratch-repro (outside the
tracked checkout) of the interpreter-discovery failure mode confirming the
wrapper fails closed for real, not just in the test's own assertion. Reviewer
acceptance (`02-review.md`, same run) — PASS, AC6/AC7/AC8 independently
re-verified against the repo rather than trusted from the integration report.
