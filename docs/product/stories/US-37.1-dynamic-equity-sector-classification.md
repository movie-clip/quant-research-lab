## Open decisions

The quant research brief (`02-quant-research.md`) resolved the producer's six
scoping questions but explicitly left four items to the schema owner / tech
lead. These are carried forward unresolved and **block ticketing** — the
design pass (`tech-lead` DESIGN) must settle them before implementation
starts:

1. **Naming of the classification-provenance field/enum.** The research brief
   proposes a candidate name/shape (`classification_source`, enum
   `static | fmp_verified | unavailable`) but is explicit this is a
   non-binding candidate, not a locked contract, and flags that the word
   `verified` specifically must not be reused for this tier (it already has a
   narrower, distinct meaning elsewhere in this codebase —
   `verified_total_return`). See research brief § Trust-class analysis.
2. **Exact nullability wiring of `sector`.** `Instrument.sector` is already
   typed `str | None` but the equity branch never actually returns `None`
   today — it always returns `"Other"`. The research brief recommends the
   field start actually using its existing nullability rather than continuing
   to stand in a string for absence, but leaves the mechanics (how the
   `None` is carried through `analytics/overview.py`'s sector aggregation,
   which currently keys a dict by `sector` and expects a string — see Notes
   below) to the schema owner. See research brief § Trust-class analysis,
   § No-coverage handling.
3. **Whether the ISIN-mismatch ("wrong security") case needs its own exposed
   state, or collapses into the same `unavailable`/unclassified outcome as
   genuine no-coverage.** The research brief notes the mismatch case is
   subtly closer to `withheld` than `unavailable` under this project's own
   trust ladder ("the resolver *does* receive a sector string from FMP, and
   specifically distrusts it") but that nothing downstream currently consumes
   a `withheld` sector, so collapsing may be acceptable. Flagged as a
   deliberate choice to make, not an accidental collapse. See research brief
   § Trust-class analysis.
4. **Caching/persistence mechanism shape.** The research brief recommends, as
   a **"should" not a hard block**, that `get_company_profile()` calls made
   for sector resolution stop sharing the 300-second live-quote cache TTL —
   either widen that TTL for this call, or (the more robust option it names)
   persist the resolved classification as its own record (symbol, mapped
   sector, source tier, resolved-at, ISIN-match evidence) independent of the
   ephemeral HTTP cache. The exact shape is explicitly left to the tech lead.
   See research brief § Caching recommendation.

## Story

As a **portfolio researcher**, I want any equity I hold that isn't in the
curated instrument registry to receive a real, identity-confirmed sector
classification from market data instead of a hardcoded `"Other"`, so that the
Exposure tab's sector breakdown reflects what I actually hold rather than an
artifact of which ~90 tickers happen to be hand-curated.

## Context

`InstrumentRegistry.classify_imported_instrument`'s equity branch
(`services/quant-engine/app/instruments/registry.py:256-265`) unconditionally
returns `sector="Other"` for any equity not in the static
`INSTRUMENT_DEFINITIONS` dict — no keyword inference, no market-data call,
nothing. This is confirmed live against the bound statement
(`docs/IB2026.csv`): four real, currently-held equities — INTU (Intuit), PANW
(Palo Alto Networks), VICI (Vici Properties), SPCX (Space Exploration
Technologies Corp.) — all land in `"Other"` today, and all four resolve
cleanly via FMP's company-profile endpoint with an ISIN that matches the
statement's own `Security ID` byte-for-byte (research brief § Live
verification).

`MarketDataService.get_company_profile()`
(`services/quant-engine/app/services/market_data.py:459`) is already wired,
already cached, and already called at import time for a narrower case
(US-14.3, Freedom24-only) — this story extends its use to the equity
classification path, gated by identity evidence rather than trusted bare.

**Why the identity gate is load-bearing, not optional.** A bare-ticker FMP
lookup has silently resolved to the wrong security three times before in this
exact codebase (`app/core/symbols.py`'s `DFND`/`SEMI`/`CIBR` comments), and
the research brief reproduced a fourth live collision (`DFNS`) during this
research pass. The mitigating pattern already exists —
`services/quant-engine/app/services/instrument_identity.py`'s evidence-gated
ISIN comparison (US-19.1/US-19.2) — currently used only to check a statement's
ISIN against the *registry's* recorded ISIN. This story requires reusing that
same pattern against the *FMP profile's* ISIN, not building a second,
divergent check (research brief § Identity risk — a "one code path"
correctness requirement).

**Why US-14.3's "don't bypass the registry" decision doesn't transfer.**
US-14.3 scoped narrowly (Freedom24 only, feeding the *existing* keyword
classifier) and its own stated justification was "no regression" against a
classifier that was already doing an OK job. That reasoning does not apply
here: the equity branch has zero classification today, for any importer — "no
regression" is not a meaningful bar when there is nothing to regress from. See
research brief § Does the US-14.3 precedent transfer?

**A second call site must change for this to actually reach the UI.**
`analytics/overview.py:50` — `sector = instrument.sector if instrument and
instrument.sector else instrument_registry.get_sector(position.symbol)` —
currently treats a falsy/`None` sector as "try the static registry again,
then fall back to `'Other'`". If `classify_imported_instrument`'s equity
branch starts returning `None` instead of `"Other"`, this line's own
`get_sector()` fallback will silently re-coerce it back to `"Other"` unless it
is also corrected. Implementer must read this file (lines 46-67) alongside
`registry.py`.

Implementer must also read: `docs/product/stories/US-14.3-freedom24-fmp-enrichment.md`
(prior art + why it was scoped narrowly); `services/quant-engine/app/services/instrument_enrichment.py`
(the existing fail-safe `except Exception` pattern to mirror);
`docs/contracts/exposure-fields.md` (`top_sectors` / `sector_hhi` rows — the
"computed over the full sector allocation set" invariant already documented
there); `02-quant-research.md` in full, especially § Recommended resolution
logic (the exact classification order, written as pseudocode with every edge
case named) and § Sector taxonomy normalization (the live-verified FMP↔project
sector-string mapping table).

## Acceptance criteria

- [x] AC1 — For an equity symbol present in the static `INSTRUMENT_DEFINITIONS`
  registry, sector classification is unchanged and no
  `MarketDataService.get_company_profile()` call is made
  (`instruments/registry.py`).
- [x] AC2 — For an equity symbol not in the static registry, sector
  classification is attempted via `MarketDataService.get_company_profile()`,
  reusing its existing symbol-candidate resolution rather than a second,
  independent lookup (research brief § Recommended resolution logic).
- [x] AC3 — An FMP-sourced sector is used only when the statement's ISIN and
  the FMP profile's ISIN are both present and match, using the same
  evidence-gated ISIN-comparison approach already implemented for
  registry-known holdings in `instrument_identity.py` (US-19.1/US-19.2),
  applied against the FMP profile's ISIN instead of the registry's (research
  brief § Identity risk).
- [x] AC4 — When the statement's ISIN and the FMP profile's ISIN are both
  present and disagree, the FMP-sourced sector is not used at all — the
  equity gets no classification from this lookup, not a wrong one (the
  "wrong security" case).
- [x] AC5 — When either the statement or the FMP profile lacks an ISIN (no
  identity evidence either way), the FMP-sourced sector is not used — the
  equity falls through to no classification, the conservative default the
  research brief recommends.
- [x] AC6 — An FMP `sector` value that is empty, missing, or not present in
  the project's sector-taxonomy mapping table is treated as no
  classification — it is never passed through to the user as a new, unmapped
  sector value (research brief § Sector taxonomy normalization).
- [x] AC7 — The sector-taxonomy mapping table covers, at minimum, the eleven
  GICS-style sector strings the research brief verified live against FMP,
  including the five confirmed-divergent pairs: Health Care/Healthcare,
  Financials/Financial Services, Consumer Discretionary/Consumer Cyclical,
  Consumer Staples/Consumer Defensive, Materials/Basic Materials.
- [x] AC8 — If the FMP lookup fails for any reason (timeout, error, rate
  limit, no coverage for the symbol), the import completes normally and the
  equity falls through to no classification — an FMP failure never blocks or
  crashes an import.
- [x] AC9 — An equity for which no source (static registry, or
  identity-confirmed FMP) resolves a sector is disclosed on the Exposure tab's
  sector breakdown (top sectors / sector concentration cards) under a
  distinct, named "unclassified" state — never the string `"Other"`, and
  never silently dropped from the sector weight total (guardrail 4; the
  existing "computed over the full sector allocation set" invariant in
  `docs/contracts/exposure-fields.md` holds for the new state too).
- [x] AC10 — Positions whose sector already resolves today via the static
  registry, or via the ETF branch's keyword inference, are unaffected: their
  reported sector is unchanged by this story (equity-branch-only scope; the
  ETF branch and ETF look-through constituent classification — F-B — are
  explicitly out of scope).

## Test plan

Backend (pytest), likely `test_instrument_registry.py` plus a new module for
the resolution logic (final location is the tech lead's / backend-engineer's
call):

- Static-dict fast path unaffected — an equity symbol in
  `INSTRUMENT_DEFINITIONS` never triggers a `get_company_profile` call.
- FMP + ISIN-match success case — an unrecognized equity symbol with a
  statement ISIN that matches the FMP profile's ISIN resolves to the mapped
  taxonomy sector.
- FMP + ISIN-mismatch (wrong-security) case — a statement ISIN that disagrees
  with the FMP profile's ISIN results in no classification, not the FMP
  value.
- FMP-no-coverage case — `get_company_profile` returning `None`/empty results
  in no classification and the import completes.
- FMP-sector-not-in-taxonomy-map case — an FMP sector string absent from the
  mapping table results in no classification, not a raw pass-through.
- No-ISIN-evidence case — either side missing an ISIN results in no
  classification (the conservative default).
- FMP-raises case — an exception from the lookup results in no
  classification and does not propagate.
- **Dedicated taxonomy-mapping regression test** pinning the five known
  FMP/project sector-string divergences (Health Care/Healthcare,
  Financials/Financial Services, Consumer Discretionary/Consumer Cyclical,
  Consumer Staples/Consumer Defensive, Materials/Basic Materials) as a named,
  standalone test — so a future FMP naming drift on any of these fails the
  suite instead of silently fragmenting a sector bucket.
- Aggregation coverage (`analytics/overview.py` or wherever the fix lands) —
  an equity with no resolved sector appears in the sector breakdown under the
  distinct unclassified state, with its weight included in the total (not
  dropped, not folded into any named sector including "Other").
- Regression — static-registry equities and ETF-branch classifications remain
  unchanged (no behavioural change outside the equity, non-static branch).

Frontend (vitest): none anticipated for this story. `ExposurePanel.tsx`'s
top-sectors / sector-concentration rendering is already data-driven off
whatever bucket labels the engine returns (`concentration.top_sectors`,
mapped generically, no special-casing observed for `"Other"` today) — see
Notes / decisions for why this story does not ticket frontend work by
default.

Regression / guardrail:
- No-fabrication regression: an equity with no classification is never
  assigned a sector string standing in for absence.
- `python scripts/run_all_tests.py` green. Goldens diff inspected: if any
  equity in the bound statement's own fixtures reclassifies (the research
  brief's live-verified candidates — INTU/PANW/VICI/SPCX — all resolve to
  Technology/Technology/Real Estate/Industrials respectively), that diff is
  the legitimate flow-through of this fix and should be committed.

## Notes / decisions

- **Why this story does not ticket frontend work.** The Exposure tab's
  sector cards (`apps/desktop/src/features/portfolio/ExposurePanel.tsx`)
  render `concentration.top_sectors` generically — mapping over whatever
  bucket labels the engine returns, with no special-casing found for
  `"Other"` or any other sector string. As drafted, the fix is entirely
  backend: the aggregation layer needs to emit a distinctly-labeled
  unclassified bucket instead of silently reusing `"Other"`, and the existing
  generic rendering picks it up with no frontend code change. **If the design
  pass decides the new state needs its own visual treatment** (e.g. a trust
  badge distinguishing curated/confirmed/unclassified sectors, which the
  research brief raises as a possibility but does not require), a frontend
  ticket should be added at that point — this is a judgment call, not a
  closed question.
- **Why the ISIN-comparison logic is reused, not reimplemented.** The
  research brief is explicit this is a correctness requirement, not a style
  preference: three prior incidents in this exact codebase
  (`app/core/symbols.py`'s `DFND`/`SEMI`/`CIBR` comments) plus a fourth live
  reproduction (`DFNS`) during the research pass all show a bare-ticker
  provider lookup silently resolving to the wrong security. A second,
  divergent identity-check implementation is exactly the class of defect
  this project's quant/tech-debt findings repeatedly flag.
- **Naming caution carried forward.** Do not name the FMP-confirmed
  classification tier `verified` — that word already has a narrower, specific
  meaning elsewhere in this codebase (`verified_total_return`). Reusing it
  for a categorical, non-returns fact risks the truth-class mixing guardrail
  3 forbids. (Also listed under Open decisions #1.)
- **No new methodology formula**, but a new methodology-*doc* gap: sector
  *exposure* (an aggregate over already-classified holdings) is documented
  today (`financial-methodology.md` §Sector exposure vs. factor loading); the
  classification mechanism itself is not. T-37.1.3 closes that gap for the
  first time, not just for this story's change.
- **Epic placement — resolved.** The human confirmed this story gets its own
  new, dedicated single-story epic (Epic 37), not a reopening of the closed
  Epic 24 and not a fold into any other epic. The reasoning that originally
  connected this fix to Epic 24 — F-A directly closes that epic's own
  `docs/tech-debt-register.md` row tagged `epic-24`
  (`instruments/registry.py:45-48,180-261`) — still explains why this work
  exists, but no longer determines which epic number it is filed under.
