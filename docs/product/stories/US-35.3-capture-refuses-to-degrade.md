# US-35.3: Refuse to overwrite the golden capture with a degraded one

**Epic:** Epic 35 — Market-Data Failure Honesty
**PRD:** [`epic-35-market-data-cache-resilience.md`](../prd/epic-35-market-data-cache-resilience.md)
**Status:** Done (2026-08-19)
**Last updated:** 2026-08-19

## Story

As a **developer refreshing the frozen market data**, I want a capture that
collected materially less than the committed one to fail instead of writing, so
that the fixture the entire network-free suite stands on cannot be quietly
replaced with a broken one.

## Context

PRD finding **F-3**, observed live on 2026-08-19.

`capture_golden_market_data` runs the golden generator through a recording proxy,
writes whatever it recorded, and prints the series count. It asserts nothing:

```python
payload = recorder.to_payload()
GOLDEN_MARKET_DATA_PATH.write_text(json.dumps(payload, indent=2, sort_keys=True), …)
print(f"Wrote {GOLDEN_MARKET_DATA_PATH} ({series_count} series)")
```

During US-34.9 it overwrote a **73-series** capture with a **21-series** one and
reported success. The cause was upstream — a broken mapper emptied SPY, the
dashboard run degraded, and far fewer symbols were ever requested — but the
capture had no opinion about it. The damage was caught only because a human
happened to compare the counts, and recovering meant `git checkout` of a file
that had already been written.

`golden_market_data.json` is the foundation of a deliberately network-free
suite: every engine test, every replay pin, and `dashboardGoldens.ts` itself are
derived from it. It is also captured **rarely and manually**, which is exactly
why it should be loud — nobody runs it often enough to have an intuition for
what a healthy run looks like.

Implementer must read: `app/scripts/export_dashboard_goldens.py`
(`capture_golden_market_data`, `RecordingMarketData.to_payload`);
`app/scripts/frozen_market_data.py`; `scripts/refresh_statement.py` (which calls
the capture as its first step); the Epic 35 PRD.

### What "degraded" means here

The comparison must be against the **committed** fixture, which is the only
statement of what a healthy capture looks like. Three properties are worth
checking, and they failed together in the real incident:

| Property | Real incident |
|---|---|
| series count | 73 → **21** |
| total rows | 9,288 → 2,771 |
| the benchmark is present and non-empty | SPY present with **0 rows** |

The third is the sharpest: SPY appeared in the payload, so a naive
"is SPY there?" check would have passed.

## Acceptance criteria

- [x] AC1 — **A materially smaller capture is refused.** If the new capture has
  fewer series than the committed fixture, or fewer total rows, the file is
  **not written** and the command exits non-zero.

- [x] AC2 — **A capture whose benchmark has no rows is refused**, even if the
  symbol is present in the payload — the exact shape of the real incident.

- [x] AC3 — **The message says what changed**, naming the counts before and
  after and the symbols that lost rows, so the operator can tell a broken run
  from a legitimately smaller statement without diffing a 2 MB JSON file.

- [x] AC4 — **A legitimate shrink can still be captured.** Replacing the
  statement with a smaller portfolio is a real workflow, so the refusal is
  overridable by an explicit flag — and the flag's name says what it is
  overriding, rather than being a generic `--force`.

- [x] AC5 — **A first capture works.** With no committed fixture to compare
  against, the capture writes normally instead of failing closed on a missing
  baseline.

- [x] AC6 — **A healthy re-capture is unaffected.** The 2026-08-19 refresh
  (73 series, 9,302 rows, up slightly from 9,288) passes the check — the
  guard must not fire on ordinary drift.

- [x] AC7 — **The check is on the capture, not the suite.** No test-time
  behaviour changes; `dashboardGoldens.ts` byte-identical; full suite + tsc +
  dead-code gate green.

## Test plan

Backend (pytest):

- `test_capture_guard.py` *(new)* — **7 tests**: a capture with fewer series
  than the baseline is refused and nothing is written (AC1); one with equal
  series but materially fewer rows is refused (AC1); one whose benchmark series
  is present-but-empty is refused (**AC2** — the real incident's shape); the
  refusal message names the before/after counts and the emptied symbol (AC3);
  the override flag permits the write and says so (AC4); a missing baseline
  writes normally (AC5); the actual 2026-08-19 shape (73 series, slightly more
  rows) passes (AC6).

The guard is a pure function over `(new_payload, committed_payload)` so every
case is a dict, not a live capture — the suite stays network-free.

Regression / guardrail:

- `dashboardGoldens.ts` byte-identical (AC7).
- `test_golden_market_data_basis.py` green untouched — it pins the *contents* of
  the committed capture; this story pins the *act of replacing* it.
- The capture itself is never invoked by the suite (it is the one live-data
  path), so the guard is tested directly rather than through it.

## Out of scope

- **Validating the capture's *contents*** — that adjusted closes are present, or
  that a symbol resolves to the right listing. `test_golden_market_data_basis.py`
  already pins the contents of whatever is committed; this story is only about
  refusing to *replace* a good fixture with a degraded one.
- **Making the capture retry or self-heal.** If it degraded, the right move is
  to stop and tell the operator, not to try again against an unknown cause.
- **The upstream cause of the US-34.9 incident** — a broken mapper plus
  negative-cached failures. Both are fixed (US-34.9, US-35.1); this story is the
  net underneath.
- **Backing up the previous capture.** Git already is that backup, and
  `git checkout` is how the incident was recovered.

## Notes / decisions

- **No formula, no methodology, no trust-class change**; no academic citation.
- **Why compare against the committed file rather than a hardcoded floor.** A
  threshold like "at least 70 series" is another hand-maintained number that
  drifts with the statement — the same class US-32.1 and US-35.2 both removed.
  The committed fixture is self-updating and is already the definition of a
  healthy capture.
- **Why "materially" fewer rows, not "any" fewer.** A re-capture legitimately
  moves by a few rows: the 2026-08-19 refresh went 9,288 → 9,302 as European
  listings gained a terminal-day quote. The guard must catch 9,288 → 2,771 and
  ignore ±1%.
- **Why the override is named for what it overrides.** A generic `--force` gets
  typed reflexively when a command refuses. The flag should have to be read.

## Outcome (2026-08-19)

**Replayed against the real incident, using the committed fixture**, by
reconstructing the degraded capture (the 20 symbols that survived, SPY present
with zero rows) and running the guard on it:

```
committed: 72 symbols, 9,302 rows
degraded : 20 symbols, 2,774 rows

Guard verdict:
  - Series count fell from 72 to 20. Missing: AAPL, ACN, ACOMO, … (52 symbols)
  - Total rows fell from 9,302 to 2,774 (70.2% lost).
  - The benchmark SPY has no rows (it had 238). Every dashboard figure is
    measured against it.
  - 1 symbol(s) are present but empty: SPY.
```

All four checks fire, and re-capturing the committed fixture unchanged is
accepted with no reasons.

**The present-but-empty benchmark is the check that matters most.** SPY *was* in
the degraded payload — a naive "is the benchmark in the capture?" test passes
that. An empty benchmark is worse than a missing one precisely because the
payload still looks structurally complete.

**The threshold is a share, not a count.** The 2026-08-19 refresh legitimately
moved 9,288 → 9,302 rows as the European listings gained a terminal-day quote.
A guard that fired on healthy drift would be worse than none — it would train
the operator to reach for the override reflexively, which is also why the flag
is `--allow-smaller-capture` rather than `--force`: it has to be read to be
typed.

**The baseline is the committed file, not a hardcoded floor.** "At least 70
series" would be one more hand-maintained number drifting with the statement —
the class US-32.1 and US-35.2 both removed. An unreadable baseline is treated as
*no* baseline rather than as a failure, so a corrupt fixture stays recoverable.
