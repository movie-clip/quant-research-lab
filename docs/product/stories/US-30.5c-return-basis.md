# US-30.5c: Provenance-selected return basis — cash-excluded market-value chain for synthetic series

**Epic:** Epic 30 — Exposure Improvements
**PRD:** [`epic-30-exposure-improvements.md`](../prd/epic-30-exposure-improvements.md)
**Status:** Done
**Last updated:** 2026-07-15

## Story

As a **portfolio researcher**, I want the shared portfolio-return series that
feeds correlation, beta, tracking error and factor attribution to exclude my
static cash balance **when it is reconstructed synthetically from current
holdings** — so a benchmark's rolling correlation to my equity is not diluted
toward zero by a cash cushion those historical dates never actually held —
**without** re-introducing the trade-fabrication bug (F-1) on the imported
ledger-replay path, where excluding cash would turn a BUY into a fake gain.

## Context

PRD finding **F-10 (High)**, decided 2026-07-08 (owner): *exclude cash*.
Scoping this fix surfaced that the naive reading of that decision — "put every
consumer on the market-value chain" — is **unsafe**, and the honest fix is
narrower and provenance-driven. This is the F-3 precedent again: record the
scoping correction in the story, cite the evidence, then fix the real defect.

### Why "market-value chain everywhere" is wrong

The shared series `_portfolio_time_weighted_return_series` (`risk.py:1553`)
computes a **cash-flow-neutral TWR** on `total_portfolio_value`:

    r_t = (PV_t − external_cash_flow_t) / PV_{t−1} − 1

TWR-on-portfolio-value is **trade-safe**: a buy moves cash → stock with the two
legs cancelling in `PV`, so no return is fabricated. A plain market-value chain
(`MV_t / MV_{t−1} − 1`) is **not** trade-safe. Reproduced against the committed
`docs/IB2026.csv` ledger (146 BUY/SELL entries in the statement window): the
worst single-day MV-vs-TWR divergence is **37.23% on 2026-06-19** — a *trading*
day, which the MV chain would publish as a 37% "return". That is exactly the
F-1 fabrication class US-30.1 fixed on the drift engine. So a blanket swap is
rejected.

### The provenance rule (the drift-engine precedent)

US-30.1 established that the correct basis depends on **what the series is built
from** (`drift_engine.py` `use_ledger_basis`). The same rule applies here, and
the diagnostics engine already carries the exact provenance signal
(`DiagnosticsProvenance.historical_basis`) at the one place every return-series
builder is invoked (`build_historical_diagnostics_result`,
`diagnostics_engine.py:328`):

| `historical_basis` | states built by | trades present? | correct basis |
|---|---|---|---|
| `imported_portfolio_history` | `build_daily_portfolio_states` (ledger replay) | **yes** (146 in window) | `portfolio_value` (TWR — unchanged) |
| `market_data_history` | `_build_synthetic_snapshot_history_states` (current holdings × prices) | **no** (cash is a flat carry, `external_cash_flow≡0`) | `market_value` (cash excluded) |

On the synthetic path, cash is `total_cash` carried flat on **every** day
(`diagnostics_engine.py:884`) and `external_cash_flow` is always `0.0`, so TWR
divides equity returns by a constant `MV + cash` denominator — diluting every
return toward zero by the cash weight. There are no trades to protect, so the
market-value chain is both correct **and** safe there. The multi-benchmark
correlation engine (`correlation_engine.py:132`) is **always** synthetic
(`_build_synthetic_snapshot_history_states_with_coverage`) and today reads
`state.total_portfolio_value` directly — the same dilution.

### Design: basis as a safe-by-default, provenance-threaded parameter

`_portfolio_time_weighted_return_series` (and attribution's mirror
`_portfolio_return_series`) gain a `basis: ReturnBasis` parameter that
**defaults to `"portfolio_value"`** (today's TWR). Every existing call site and
every existing test therefore stays **byte-identical** unless a caller
explicitly opts into `"market_value"`. Only two provenance sources opt in:

1. `build_historical_diagnostics_result` derives
   `return_basis = "market_value" if provenance.historical_basis ==
   "market_data_history" else "portfolio_value"` and threads it through the five
   portfolio-return-series builders it fans out to
   (`build_portfolio_risk_summary`, `build_rolling_risk_series`,
   `build_relative_risk_summary`, `build_statistical_factor_model`,
   `build_volatility_regime_payload`). (`build_risk_contribution_breakdown`
   builds **no** portfolio-return series — it derives per-position risk from
   `price_histories` and the already-basis'd factor `model` — so it is *not*
   threaded.)
2. `attribution_engine` (the `/engines/attribution` card) and `stress_engine`
   (the Risk-tab Stress Scenarios card) build their states via
   `_build_synthetic_snapshot_history_states_with_coverage` — they are **always
   synthetic** — so they pass `return_basis="market_value"` into
   `build_factor_attribution` / `build_statistical_factor_model`.
3. `correlation_engine.py` switches its synthetic portfolio price series from
   `total_portfolio_value` to `total_market_value`.

The default is chosen so the change is **auditable by grep**: the only places
that produce a cash-excluded series are the two that pass the literal
`"market_value"`.

### Blast radius (why this is smaller than F-10 first appeared)

Because the default is `portfolio_value`, everything on the **ledger-replay
path stays byte-identical**:

- **Dashboard** — `dashboard_history_engine.py:854` (`_compute_max_drawdown`)
  calls the series with no basis arg → stays TWR → **unchanged**.
- **Imported diagnostics** — the committed IB2026 golden portfolio runs on
  `run_imported_diagnostics_engine` → `imported_portfolio_history` → TWR →
  **unchanged**. So the Exposure tab's rolling correlation/beta and the
  Dashboard Risk Summary for the *imported* portfolio legitimately stay on the
  trade-safe TWR (the honest consequence: cash de-dilution is deferred on the
  ledger path — it needs per-day trade-flow neutralization, out of scope; see
  below).

The **only** behavioural movement is on the **synthetic** surfaces:

- Snapshot-request diagnostics (`snapshot_request` / `market_data_history`).
- The multi-benchmark correlation engine (always synthetic) — its rolling
  correlations/betas across the benchmark universe.

`dashboardGoldens.ts` is generated from the **imported** path, so it is
expected **byte-identical**; the movement is captured by the synthetic-path
correlation/attribution tests and the multi-benchmark correlation golden (if
present). AC8 pins this: any golden diff must be synthetic-family only.

**Corroboration — the Risk-tab VaR and Drawdown engines already do this.**
`distribution_engine._compute_daily_returns` and
`drawdown_engine._compute_daily_returns` already derive their synthetic return
series from `state.total_market_value` (cash-excluded market-value chain). So
the "two bases" F-10 flagged was really an *internal inconsistency*: the
VaR/drawdown synthetic surfaces were on the market-value chain while the
correlation/beta/attribution/factor/stress synthetic surfaces were on the
cash-inclusive TWR. This story removes that split by moving the latter onto the
same market-value chain the former already uses — no change to
distribution/drawdown (they are already correct).

### Out of scope (deferred, recorded)

Truly excluding cash **on the ledger-replay path** (so the imported portfolio's
own rolling correlation de-dilutes too) requires neutralizing intra-day trade
flows in market-value space — `DailyPortfolioState`
(`schemas/reconciliation.py:563`) has no per-day trade-flow field, so the MV
chain cannot distinguish a BUY from a gain there. Adding that field and the
`r_t = (MV_t − trade_flow_t)/MV_{t−1} − 1` estimator is a real engine change
larger than F-10's billing; it is logged to the Epic 24 tech-debt register as a
follow-up, **not** done here. On the ledger path TWR already handles cash
correctly (cash ≈ 3% of NAV, moved only by real flows/trades), so the residual
dilution is small and *correct*, not a fabrication.

## Notes / decisions

- **Why safe-by-default (`portfolio_value`) rather than flipping the default:**
  the trade-fabrication risk lives entirely on the ledger path; a default that
  preserves TWR there means no call site can accidentally fabricate a return by
  forgetting to pass a basis — the failure mode is fail-safe, and the
  cash-excluded path is opt-in and greppable (the F-4 lesson: don't let a
  forgotten wiring change behaviour silently).
- **Why the imported portfolio's rolling correlation does *not* visibly change:**
  it runs on the ledger path, which correctly stays TWR. Fully de-diluting the
  ledger path needs per-day trade-flow neutralization (a new
  `DailyPortfolioState` field) — deliberately deferred (see Out of scope). This
  is the honest, accurate scope of "exclude cash", not the maximal one.
- No new *formula* beyond the market-value chain already documented in
  §Indexed Return Series (US-30.1); this story extends its provenance rule to
  the correlation/attribution series. No new citation required.
