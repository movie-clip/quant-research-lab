# US-14.3: Freedom24 FMP company-profile enrichment for unknown symbols

**Epic:** 14 — Post-Epic-13 Bug Sweep
**PRD:** [`epic-14-post-epic-13-bug-sweep.md`](../prd/epic-14-post-epic-13-bug-sweep.md)
**Status:** Done
**Last updated:** 2026-06-01

## Story

As a **portfolio researcher**, I want unknown tickers I hold via
Freedom24 to be automatically classified by sector + asset-class
using FMP's company profile at import time, so that any new ETF
or stock I add to my portfolio gets the right Exposure-tab sector
without me having to wait for the static instrument registry to
be hand-extended.

## Context

The VTI sector-mis-classification bug earlier in this session
(commit `cf30cfc`) was patched by adding 15 common US ETFs to the
static `INSTRUMENT_DEFINITIONS` dict in
`services/quant-engine/app/instruments/registry.py`. That's a
per-ticker patch — every NEW unknown ticker the user holds will
hit the same bug until someone hand-extends the registry.

This story adds a slow-path FMP-driven enrichment: at import time,
unknown symbols whose imported description is just the bare ticker
get their `description` (= FMP `companyName`) and `instrument_type`
(= "ETF" or "STOCK", from FMP `isEtf`) populated automatically.
The existing description-based `classify_imported_instrument`
fallback in `InstrumentRegistry` then resolves the sector
correctly without further code changes.

The static registry remains the fast path (no FMP call). FMP is
the slow path. The FMP cache layer makes repeated calls for the
same symbol free.

`MarketDataService.get_company_profile(symbol)` already exists at
`services/quant-engine/app/services/market_data.py:310` —
returns an FMP profile dict (`companyName`, `sector`, `isEtf`,
etc.) or `None`. No new client work needed.

This story focuses on the Freedom24 parser because that's where
the bug surfaces (Freedom24's `_parse_instruments` sets
`description=ticker` by design). IB and ESPP statements typically
include the full company name natively, so their parsers don't
currently exhibit the bug and are out of scope.

- `services/quant-engine/app/instruments/registry.py` —

  helper skips the FMP call. The existing
  `classify_imported_instrument` description fallback already
  handles these.
- [x] AC4 — Slow-path enrichment: for an unknown symbol with a
  trivial (bare-ticker-only or empty) description, the helper
  calls `market_data.get_company_profile(symbol)`. When FMP
  returns a non-None dict with a non-empty `companyName`, the
  returned instrument has `description = profile["companyName"]`
  (other fields preserved).
- [x] AC5 — `instrument_type` enrichment: when the FMP profile's
  `isEtf` flag is truthy, the returned instrument's
  `instrument_type` becomes `"ETF"`. When `isEtf` is falsy AND
  the imported `instrument_type` was empty/None, the returned
  instrument's `instrument_type` becomes `"STOCK"`. When the
  imported `instrument_type` was already a non-empty value, that
  value is preserved (the parser's explicit declaration wins).
- [x] AC6 — Fail-graceful: when FMP returns `None`, OR
  `get_company_profile` raises any exception, the helper returns
  the original `ImportedInstrument` unchanged for that symbol.
  Other symbols in the same snapshot are unaffected — partial
  enrichment is OK.
- [x] AC7 — `services/quant-engine/app/importers/freedom24.py`'s
  `import_statement(path)` calls `enrich_imported_instruments`
  on the assembled `ImportedPortfolioSnapshot` before returning.
  The enrichment call is wrapped in a try/except so a
  `MarketDataService` initialisation failure or any unexpected
  exception falls through to returning the un-enriched snapshot.
- [x] AC8 — Round-trip integration: an enriched instrument with

  `InstrumentRegistry.classify_imported_instrument` produces an

## Out of scope

- IB and ESPP parser enrichment. IB statements already
  populate richer descriptions natively; ESPP is hardcoded to
  MSFT (a known static-registry symbol). Adding enrichment
  there is a follow-up only if a real bug surfaces.
- Async / batch FMP calls. Sequential per-symbol is fine for
  v1 — the FMP cache layer makes repeated calls free, and
  the import flow is human-paced (not a hot loop). Batching
  would add code without measurable benefit.
- Sector overrides. The helper populates `description` and
  `instrument_type` only. The existing
  `classify_imported_instrument` in `InstrumentRegistry`
  does the description-keyword → sector inference. We do not
  bypass the registry's classification logic.
- Persisting enriched results to a local sector cache. The
  FMP client already caches its responses, so subsequent
  imports of the same symbol are free without extra
  persistence.
- Methodology change. No formula touched.
- Schema change. `ImportedInstrument` fields stay as-is; we
  just populate them more reliably.
- Contract doc update. `ImportedInstrument` isn't part of any
  user-facing contract doc (it's an internal import schema).
- `current-product-state.md` update. User experience improves
  but the underlying capability set is unchanged. Story
  author's discretion whether to add a one-line note.
- Retroactive enrichment of existing imported workspaces.
  The fix applies to new imports only.

## Notes / decisions

- **Why Freedom24-only.** The FMP enrichment helper is
  importer-agnostic; we deliberately wire it only into the
  Freedom24 parser because that's where the bug surfaces
  (Freedom24 sets `description=ticker` by design). IB and
  ESPP can adopt the helper later if they ever exhibit the
  same bug shape.
- **Why static registry stays the fast path.** Even with FMP
  enrichment available, the static `INSTRUMENT_DEFINITIONS`
  is faster (no I/O) and more deterministic (no FMP outage
  affects classification). Known symbols never round-trip
  through FMP. New symbols benefit from the slow path; once
  they prove to be commonly held, they get promoted to the
  static registry in a separate hand-edit.
- **Description-triviality heuristic.** "Bare ticker" =
  empty/None description, OR description equals the symbol
  after upper-casing, OR description has no whitespace AND
  no lowercase letters. This catches Freedom24's
  `description=ticker` case. A description like "Apple Inc"
  is non-trivial → we don't override it (FMP could shorten
  it and lose nothing useful, but the heuristic also saves
  an API call). Conservative — if a parser somewhere sets
  `description = "AAPL US"`, that's also skipped, but the
  existing classification doesn't care.
- **`instrument_type` precedence.** When the imported
  `instrument_type` already has a non-empty value (the
  parser made an explicit declaration), we keep it. We only
  populate `instrument_type` from FMP when the parser left
  it empty/None or set it to a non-ETF value while FMP says
  isEtf=True (in which case FMP wins — the parser was
  uninformed). This is intentionally asymmetric: FMP can
  upgrade STOCK→ETF but not downgrade ETF→STOCK.
- **Why a try/except wrapper at the import boundary.** A
  failed enrichment must not block the import. If FMP is
  down, the network is offline, or `MarketDataService` fails
  to construct (no API key, etc.), the import should still
  succeed with un-enriched instruments. Users get the same
  bug (some sectors → "Other") that existed before this
  story — no regression. Adding enrichment is a best-effort
  improvement, not a load-bearing dependency.
- **No new methodology.** This is an import-pipeline data
  quality fix, not an analytics change. No formula. No
  academic citation required.

  (overlay collision, drawdown smart-default, FMP
  enrichment) ship. The roadmap flips to "Completed Epic"
