# US-39.1: Direct-held ETF sector classification stops relying on keyword-substring matching

**Epic:** 39 — Direct-Held ETF Sector Classification
**PRD:** [`docs/product/prd/epic-39-direct-held-etf-sector-classification.md`](../prd/epic-39-direct-held-etf-sector-classification.md)
**Status:** Done
**Last updated:** 2026-08-24

**Filing note:** this draft was written against a work order that already
carried the epic title ("Epic 39 — Direct-Held ETF Sector Classification")
as a given, following the same Epic 37→38 precedent (a dedicated new epic
rather than reopening a closed one). That placement is confirmed at

## Story

As a **portfolio researcher**, I want a direct-held ETF that isn't in the
curated instrument registry (e.g. SBIO) to receive a real, identity-confirmed
sector classification derived from actual fund composition data, or an
honest "Unclassified" disclosure, instead of a silent match on whichever
handful of keywords happen to appear in the broker's free-text description —
and never a silently-wrong "Broad Market" default when no keyword hits — so
that the Exposure tab's sector breakdown reflects what I actually hold.

## Context

`InstrumentRegistry.classify_imported_instrument`'s ETF branch
(`services/quant-engine/app/instruments/registry.py:246-292`) is the one
sector-classification code path neither Epic 37 (the equity branch) nor Epic
38 (ETF look-through) touched. It is a keyword-substring matcher on the
broker's free-text description (`"BIOTECH"`, `"FINANCIAL"`, `"SEMIC"`, and
about ten others), and when none of its ~10 keywords hit, it silently
defaults `sector = "Broad Market"` — a claim about the fund's *intent*
(index-tracking, not sector-focused), asserted with no evidence behind it.

**Why `get_company_profile`'s `sector` field is not the fix.** Live-verified
2026-08-24 (`03-quant-research.md` § Live evidence log item 1) against six
ETFs spanning distinct themes — SBIO, SPY, XLF, GRID, QQQ, ICLN — FMP's
general profile `sector` field returned the identical pair
(`"Financial Services"` / `"Asset Management"`) for every single one. This is
FMP's fund-sponsor/vehicle classification (an ETF is itself an "asset
management" product), never a thematic answer, for any ETF. This confirms and
extends the finding both Epic 37's and Epic 38's PRDs already recorded as a
non-goal — do not reuse this field for ETFs.

**A different FMP endpoint answers the theme correctly.** A newly-found,
on-plan endpoint, `/stable/etf/sector-weightings` (legacy
`/api/v3/etf-sector-weightings/{symbol}`), returns each ETF's real sector
composition as a weighted breakdown. Live-verified against eight tickers
(`03-quant-research.md` § Live evidence log item 3): every known-sector-pure
fund (SBIO, XLF, XLV, IBB) resolves cleanly to its real theme at 98-100%
weight; genuinely diversified/multi-theme funds (SPY, GRID, ICLN) correctly
show a spread distribution instead of a false single-sector claim.
Corroborated by a second, independent provider — yfinance's
`Ticker.funds_data.sector_weightings` matches FMP's numbers closely on every
ticker tested (informational corroboration only; yfinance exposes no ISIN and
cannot itself serve as the identity gate).

**The SBIO ticker-collision case — proven live, the reason the identity gate
is not optional here.** `get_profile("SBIO")` resolves to a *different*
security: `isin: "US00162Q5936"`, `"ALPS Medical Breakthroughs ETF"` — a
US-listed fund. The statement's actual SBIO holding
(`docs/IB2026.csv`, `"INVESCO NASDAQ BIOTECH"`, `listing_exchange: LSEETF`,
ISIN `IE00BQ70R696`) is a different fund entirely that happens to share a
bare ticker. Without an identity gate, `/stable/etf/sector-weightings`
returns a plausible-looking "Healthcare 100%" result for the *wrong*
security — the two funds happen to agree on theme here by coincidence,
nothing guarantees that in general. Only the exchange-suffixed candidate
`SBIO.L` resolves to the statement's actual security (ISIN match confirmed
live); `SBIO` (bare) does not. This is the same collision class this
codebase's `app/core/symbols.py` `DFND`/`SEMI`/`CIBR` comments already
document and guard against for equities and other ETFs. SBIO currently has
**no** `SymbolResolutionRule` in `symbols.py` — this is new, not an existing
guard being extended.

**Resolution order (research brief § Formulas, mirrors
`equity_sector_resolution.py`'s shape — read that module directly before
implementing):**

1. Static registry lookup (unchanged): a curated `INSTRUMENT_DEFINITIONS`
   entry always wins.
2. Identity-gated dynamic lookup, opt-in (only attempted when `market_data`
   is supplied — same opt-in pattern the equity branch already uses):
   for each symbol candidate, confirm the candidate's FMP profile ISIN
   matches the statement's ISIN (same identity-gate mechanism as the equity
   branch, `instrument_identity.normalize_isin`); only on a match, read that
   candidate's `/stable/etf/sector-weightings` result; take the top-weighted
   sector bucket; accept it as a single-sector classification only if its
   share of total weight clears `DOMINANCE_THRESHOLD = 55%` (resolved by the
   human — see below); map it through the project's sector-taxonomy table.
3. Anything that does not clear every step above (no candidate's ISIN
   matches, no ISIN evidence on either side, an empty/zero-weight response,
   a below-threshold top share, an unmapped sector bucket, a lookup
   exception) resolves to no classification — never a fallback guess, and
   specifically never `"Broad Market"`.

**`DOMINANCE_THRESHOLD = 55%` — resolved.** Evidence table
(`03-quant-research.md` § Formulas), reframed against the chosen value: 55%
chosen because it captures GRID (58.4%) and QQQ (60.3%) with margin, and
cleanly excludes ICLN (41.4%) and SPY (37.4%) with margin, while the
unambiguous cases stay unambiguous on either side:

| Symbol | Top-sector share | Resolves to a single sector at 55%? |
|---|---|---|
| SBIO, XLV, IBB, XLF | 98-100% | Yes — unambiguous |
| QQQ | 60.3% | Yes — captured with margin; matches this fund's *existing* static curation ("Technology"), a useful calibration anchor |
| GRID | 58.4% | Yes — captured with margin |
| ICLN | 41.4% | No — cleanly excluded |
| SPY | 37.4% | No — cleanly excluded (already statically curated as "Broad Market", unaffected either way) |

**`category` is out of scope, unaffected — resolved.** This story resolves
`sector` only, via the existing `SECTOR_TAXONOMY_MAP`, consistent with how
equity classification (US-37.1) and ETF look-through classification
(US-38.1) already work. The existing keyword-based `category` derivation
already in `registry.py`'s ETF branch (Sector/Thematic/Broad Market/Bond/
Commodity ETF) stays completely untouched by this story — no new category
logic, no custom/thematic labeling, no dynamic tier for `category` at all.

**Do not repeat the keyword matcher's mistake.** A below-threshold dynamic
result must not default to `"Broad Market"` either, even though it is
tempting by analogy (SPY genuinely is diversified). `"Broad Market"` is a
claim about a fund's *intent* that a weight vector alone cannot establish —
GRID (58% Industrials) and ICLN (41%/30%/22% across three sectors) are both
diversified in the same numeric sense as SPY but are thematic funds, not
broad-market ones. The honest answer below threshold is "Unclassified",
matching this project's existing edge-case discipline.

New work this story requires, per the research brief's handoff (not
optional hardening — see § Open item: category and § Recommendation
summary):

- A new `SymbolResolutionRule` for `SBIO` in `app/core/symbols.py` (an
  `SBIO.L` candidate; deliberately no bare `"SBIO"` candidate, mirroring the
  `DFND`/`SEMI`/`CIBR` pattern already in that file).
- A new `MarketDataService`/`FmpClient` method reading
  `/stable/etf/sector-weightings` (the research brief proposes
  `get_etf_sector_weightings(symbol)` as a name, not a mandate) — no
  existing method calls this endpoint.
- A new `ClassificationSource` literal, distinct from `"fmp_identity_confirmed"`
  (the research brief proposes `"fmp_etf_sector_weighting_confirmed"`, not a
  mandate — the equity tier's literal resolves via a direct string mapping;
  this tier resolves via a structurally different mechanism, a weight-vector
  dominance rule, and collapsing both under one provenance label loses the
  traceability distinction guardrail 2 exists to preserve).

Implementer must also read: `services/quant-engine/app/instruments/equity_sector_resolution.py`
(the pattern this module's ETF counterpart mirrors — identity gate, fail-safe
`except Exception`, "never pass an unmapped string through raw" discipline);
`docs/product/stories/US-37.1-dynamic-equity-sector-classification.md` (same
identity-gate shape, same epic lineage); `docs/product/stories/US-38.1-etf-lookthrough-sector-classification.md`
(how "Unclassified never a guess" was phrased and tested for a sibling code
path); `03-quant-research.md` in full, especially § Live evidence log
(the raw data behind every claim above), § Formulas, with edge cases (the
exact resolution order as pseudocode, one row per edge case), and
§ Trust-class analysis.

## Acceptance criteria

- [x] AC1 — For a direct-held ETF symbol present in the static
  `INSTRUMENT_DEFINITIONS` registry, sector classification is unchanged and
  no dynamic lookup of any kind is attempted (`instruments/registry.py`'s ETF
  branch).
- [x] AC2 — For a direct-held ETF symbol not in the static registry, a
  dynamic sector lookup is attempted only when market data access is
  supplied to the classification call — mirroring the equity branch's
  existing opt-in gate — and is not attempted otherwise.
- [x] AC3 — A dynamically-resolved sector is used only when a symbol
  candidate's FMP profile ISIN and the statement's own ISIN are both present
  and match; this is checked against the correctly exchange-suffixed
  candidate, not only the bare ticker.
- [x] AC4 — For the SBIO case specifically: the bare `"SBIO"` candidate
  resolves to a different security on FMP than the statement's actual
  holding (confirmed live, research brief § Live evidence log item 3); this
  story ensures the identity gate rejects that wrong-security candidate, so
  no sector is ever sourced from it, and the correct exchange-suffixed
  candidate is the only one that can clear the gate for this symbol.
- [x] AC5 — When neither side of the identity check has ISIN evidence (the
  statement is missing an ISIN, or no candidate's FMP profile returns one),
  the dynamic lookup resolves to no classification.
- [x] AC6 — A dynamically-resolved classification is accepted as a single
  sector only when that sector's share of the fund's total reported weight
  meets or exceeds `DOMINANCE_THRESHOLD = 55%`; below 55%, the ETF resolves
  to no classification.
- [x] AC7 — A below-threshold or otherwise-unresolved dynamic result never
  defaults to `"Broad Market"` (or any other plausible-looking sector) — the
  outcome is the same "no classification" state as every other failure mode
  in this resolution order.
- [x] AC8 — A top-weighted sector bucket whose name is not present in the
  project's sector-taxonomy mapping table (e.g. a "Cash & Others" bucket) is
  treated as no classification — never passed through to the user as a new,
  unmapped sector value.
- [x] AC9 — An empty, missing, or zero-total-weight sector-weightings result
  for the identity-confirmed candidate resolves to no classification.
- [x] AC10 — If the dynamic lookup fails for any reason (timeout, error,
  rate limit, no coverage for the symbol), the import completes normally and
  the ETF falls through to no classification — a lookup failure never blocks
  or crashes an import.
- [x] AC11 — A direct-held ETF for which no source (static registry, or
  identity-confirmed dynamic lookup) resolves a sector is disclosed on the
  Exposure tab's sector breakdown under the same distinct "Unclassified"
  state the equity branch already uses (US-37.1) — never the literal
  `"Broad Market"` used as a stand-in for absence, and never silently
  dropped from the sector weight total.
- [x] AC12 — Direct-held ETFs whose sector already resolves today via the
  static registry, equities (the US-37.1 equity branch), and ETF
  look-through constituents (US-38.1) are unaffected by this story.

## Test plan

Backend (pytest), likely a new module mirroring
`test_equity_sector_resolution.py`'s shape (final location is the tech
lead's / backend-engineer's call), plus `test_instrument_registry.py`
coverage for the ETF branch's wiring:

- Static-registry fast path unaffected — a direct-held ETF symbol in
  `INSTRUMENT_DEFINITIONS` never triggers a dynamic lookup.
- Identity-match success case — a direct-held ETF with a statement ISIN
  matching the correct candidate's FMP profile ISIN, and a top sector share
  above threshold, resolves to the mapped taxonomy sector.
- **SBIO-collision-prevented case, specifically** — the bare-ticker
  candidate resolves to a different security's ISIN; the gate rejects it;
  only the correctly-suffixed candidate clears the gate and sources the
  classification.
- ISIN-mismatch case — a statement ISIN that disagrees with a candidate's
  FMP profile ISIN results in no classification, not the candidate's sector.
- No-ISIN-evidence case — either side missing an ISIN results in no
  classification.
- Dominance-threshold pass case — a top sector share at or above the 55%
  threshold resolves to that sector.
- Dominance-threshold fail case — a top sector share below the 55%
  threshold resolves to no classification, not `"Broad Market"`.
- Unmapped-sector-bucket case — a top sector string absent from the
  taxonomy mapping table results in no classification, not a raw
  pass-through.
- Empty-weights-response case — an empty or zero-total-weight
  sector-weightings result (including a nonexistent/non-ETF/uncovered
  symbol) results in no classification.
- Lookup-exception case — an exception from the dynamic lookup results in no
  classification and does not propagate.
- Aggregation coverage — a direct-held ETF with no resolved sector appears
  in the Exposure-tab sector breakdown under the "Unclassified" state, with
  its weight included in the total (not dropped, not folded into any named
  sector including "Broad Market").
- Regression — static-registry ETFs, equity-branch classifications, and
  look-through constituent classifications remain unchanged (no behavioural
  change outside the direct-held ETF, non-static branch).

Frontend (vitest): none anticipated by default — the Exposure tab's sector
rendering is already data-driven off whatever bucket labels the engine
returns (same reasoning US-37.1 and US-38.1 recorded for their own stories).
If the design pass decides the new dynamic-tier state needs its own visual
treatment, a frontend ticket should be added at that point.

Regression / guardrail:

- No-fabrication regression: a direct-held ETF with no resolved
  classification is never assigned a sector string standing in for absence
  (neither `"Broad Market"` nor a plausible-looking-but-unconfirmed sector).
- `python scripts/run_all_tests.py` green. Goldens diff inspected: if SBIO
  or any other direct-held ETF in the bound statement's own fixtures
  reclassifies as a result of this fix, that diff is the legitimate
  flow-through of this fix and should be committed.

## Notes / decisions

- **`DOMINANCE_THRESHOLD = 55%` — resolved by the human.** See Context §
  `DOMINANCE_THRESHOLD = 55% — resolved` for the evidence table framed
  against the chosen value. No AC or ticket in this story is written to
  "hold regardless of the exact threshold" — all reference 55% directly.
- **`category` scoped out entirely — resolved by the human.** This story
  resolves `sector` only, via the existing `SECTOR_TAXONOMY_MAP`. The
  existing keyword-based `category` derivation in `registry.py`'s ETF
  branch is untouched — no ticket in this story implements or modifies any
  `category` logic.
- **Why this story does not ticket frontend work.** The Exposure tab's
  sector cards render whatever bucket labels the engine returns, with no
  special-casing observed for any particular sector string. As drafted, the
  fix is entirely backend; the existing generic rendering picks up the new
  "Unclassified" outcomes with no frontend code change required. If the
  design pass decides the new dynamic-tier state needs its own visual
  treatment, a frontend ticket should be added at that point.
- **Naming caution carried forward, not mandated.** The research brief
  recommends against reusing the equity branch's `"fmp_identity_confirmed"`
  literal for this tier — the two tiers resolve via structurally different
  mechanisms (a direct string mapping vs. a weight-vector dominance rule)
  and collapsing them loses a traceability distinction guardrail 2 exists to
  preserve. This is a recommendation for the design pass, not a locked
  contract (mirrors US-37.1's own Open decision #1 precedent for the same
  kind of naming caution).
- **Why the identity-gate mechanism is reused, not reimplemented.** Same
  correctness requirement US-37.1 already established for equities: a
  second, divergent ISIN-comparison implementation is exactly the class of
  defect this project's tech-debt findings repeatedly flag. The SBIO case
  proves live that this requirement transfers unchanged to ETFs.
