# US-23.1: Detection tooling + tech-debt register + removal protocol

**Epic:** Epic 23 — Dead-Code Cleanup & Codebase Review
**PRD:** [`epic-23-dead-code-cleanup-and-review.md`](../prd/epic-23-dead-code-cleanup-and-review.md)
**Status:** Done
**Last updated:** 2026-06-12

## Story

As a **developer of this project**, I want dev-only dead-code detection tooling
and a single tech-debt register with a written removal protocol, so that every
later cleanup story in this epic is tool-assisted and consistent — and dead code
is caught going forward instead of re-accumulating.

## Context

There is no dead-code tooling today (no ruff/vulture for Python; no
knip/ts-prune/eslint for TS) and `tsconfig` lacks `noUnusedLocals`/
`noUnusedParameters`, so detection is manual and misses things. This keystone
story stands up the detection floor the rest of Epic 23 relies on, plus the
`docs/tech-debt-register.md` doc (where US-23.2–23.7 record hardcodes/
anti-patterns) and the **removal protocol** (the PRD's "confirmed dead"
checklist) so deletions stay safe. Tooling is dev-only; no runtime dependency.

Implementer must read:
- `docs/product/prd/epic-23-dead-code-cleanup-and-review.md` — the safety
  protocol and category split (delete dead vs. catalog smells).
- `services/quant-engine/requirements.txt` + `scripts/run_all_tests.py` — where
  Python dev tooling and the canonical runner live.
- `apps/desktop/package.json` + `tsconfig*.json` — where TS tooling + compiler
  flags live.

## Out of scope

- **Acting on the baseline findings** — that is US-23.2–23.7 (this story only
  produces the detectors + the register, not the deletions).
- **Gating the build on zero dead-code findings** — that is the epic's tail,
  **US-23.8**, which can only go green once US-23.2–23.7 have cleaned the
  baseline. This story produces the detectors + register; US-23.8 enforces them.
- **CI wiring** — there is no CI in this repo; the tooling is local/dev-only.
- **Reformatting / full lint adoption** — only the *unused* rules are enabled,
  not a style ruleset.

## Notes / decisions

- **Why vulture + ruff (not one):** ruff's `F`-rules catch unused
  imports/locals/redefinitions fast and deterministically; vulture catches
  whole-program unused *functions/classes/attributes* that ruff does not. They
  are complementary; both are dev-only and fast.
- **Why an allowlist is mandatory:** the project has heavy dynamic usage that
  static tools flag as false positives — pytest fixtures, Pydantic
  `field_validator`s, FastAPI route handlers, `schema_version`-keyed persistence
  sanitizers. The allowlist (with a reason per entry) is part of the deliverable
  so later stories trust the signal.
- No financial formula; no methodology change.
