# US-20.2: History range normalization

**Epic:** Epic 20 — Market-Data Cache Efficiency & Control
**PRD:** [`epic-20-market-data-cache-efficiency.md`](../prd/epic-20-market-data-cache-efficiency.md)
**Status:** Done
**Last updated:** 2026-06-11

## Story

As a **portfolio researcher**, I want each symbol's price history fetched over a
single normalized superset date-range and sliced to satisfy each engine's
specific window, so that the many overlapping range requests an analysis makes
(attribution `display+window`, correlation `lookback`, drift windows, provenance
30d, dashboard history, …) collapse onto **one shared FMP cache key per symbol
per span** instead of one call per distinct `(from, to)` — cutting the FMP
overuse that is the dominant inefficiency in the cache.

## Context

Today `MarketDataService.get_historical_prices(symbol, from, to)` passes the
caller's exact `(from, to)` straight to `FmpClient.get_historical_price_light`,
whose cache key is `{path, {symbol, from, to}}`. Because every engine computes
its own lookback, the same symbol's bars are fetched repeatedly under slightly
different ranges — each a distinct key, each a distinct FMP call (PRD problem
#1, "the dominant source of FMP overuse"). This story inserts a
**range-normalization seam** inside `MarketDataService`: the requested window is
widened to a canonical, deterministic superset range (quantized to calendar-year
boundaries), that one canonical range is fetched and cached, and the returned
rows are sliced back to the caller's exact `(from, to)`. Identical output, far
fewer FMP calls. US-20.1's `GET /cache/stats` is the instrument that lets us
*see* the reduction.

This is purely a caching/efficiency change: **no new market data, no change to
provider priority (FMP→Yahoo), trust semantics, provenance, or `last_fetch_meta`
shape** (Epic 18 owns those; PRD non-goals). No financial formula is touched —
the bars an engine receives for a given `(from, to)` are byte-for-byte what it
gets today.

Implementer must read:
- `app/services/market_data.py` — `get_historical_prices` (the FMP-candidate +
  yfinance-fallback loops at ~263–305), `get_direct_verified_benchmark_history`
  (~310–334), `_sanitize_price_rows`, `get_historical_prices_for_symbols`.
- `app/clients/fmp.py` — `get_historical_price_light` / `_get` (cache key is
  `{path, params}` with `params={symbol, from, to}`).
- `docs/architecture/testing-architecture.md` — the frozen-goldens note

  `MarketDataService`, so this change does not touch goldens; engine tests mock

  `test_market_data.py` against a mocked `FmpClient`.

## Acceptance criteria

- [x] AC1 — For a given symbol, two requests whose `(from, to)` fall within the
  same canonical span pass the **identical canonical `(from, to)`** to
  `FmpClient.get_historical_price_light` — i.e. they share one cache key, so the
  real `JsonFileCache` serves the second from cache and only one underlying FMP
  network fetch occurs. Verified by asserting identical client args across the
  two requests (and, with a real tmp-dir cache, a single network fetch).
- [x] AC2 — A normalized request returns **byte-identical rows** to what a direct
  un-normalized `(from, to)` fetch would return: the canonical range is sliced to
  `from <= date <= to`, preserving row order and contents. No bar outside the
  requested window leaks into the result.
- [x] AC3 — The canonical range is a **pure, deterministic function of the
  requested `(from, to)`** (calendar-year quantization: `canonical_from` = Jan 1
  of `from`'s year, `canonical_to` = Dec 31 of `to`'s year) — no wall-clock
  dependency, so behaviour is reproducible across machines and test runs.
- [x] AC4 — Fail-closed unchanged: an empty/negative-cached canonical fetch, or a
  window with no bars, yields `[]` (never fabricated bars); the FMP-candidate →
  yfinance-fallback order and the proxy-fallback behaviour are preserved.
- [x] AC5 — `last_fetch_meta` for every path (`type`, `resolved_symbol`,
  `cached`, `vendor`, and the verified-benchmark fields) is **unchanged** in
  shape and values — no trust/provenance regression. (US-21.5's superset
  assertions in `test_market_data.py` stay green.)
- [x] AC6 — The verified-benchmark direct path
  (`get_direct_verified_benchmark_history`, SPY/QQQ) uses the same normalization,
  so the repeatedly-fetched benchmark also collapses to one canonical call per
  span.
- [x] AC7 — Because overlapping windows now collapse to one canonical cache key
  per `(symbol, span)`, the number of distinct `history`-namespace cache entries
  written for a multi-window analysis is **strictly lower** than the number of
  distinct `(symbol, from, to)` engine requests (the call-reduction this story
  exists for; observable via `GET /cache/stats` / cache-dir entry count). Full
  backend + frontend suites stay green.

## Out of scope

- **In-memory memo layer + parallel multi-symbol fetch** — that is US-20.3
  (the latency win); this story is the FMP-call-count reduction only.
- **Superset-aware cross-span reuse** (slicing a cached 5-year canonical range to
  satisfy a later 30-day request without any fetch) — a possible US-20.3/future
  enhancement; year-quantization gives same-span sharing without cache
  enumeration.
- **Single max-anchor strategy** (always fetch `[today − MAX_LOOKBACK, today]`):
  maximizes reuse but introduces wall-clock nondeterminism and unbounded
  over-fetch for short windows — deliberately rejected in favour of the
  deterministic year-quantization rule.
- **Any change to TTL policy, provider priority, trust/provenance, or
  `last_fetch_meta` shape** (PRD non-goals; Epic 18 owns provenance).
- **ETF holdings / profile / fundamentals caching** — different access pattern;
  not part of the overlapping-range problem.

## Notes / decisions

- **Why calendar-year quantization (not month or max-anchor):** it is the
  simplest rule that is (a) a *pure function of the request* — no `today`, so
  deterministic and unit-testable; (b) collapses every request whose window
  falls in the same year-span onto one cache key (the common case: many engines
  reading recent history ending near the import date); and (c) bounds over-fetch
  to at most ~one extra year on each side. Month quantization shares fewer
  requests; a `today`-anchored max range shares the most but is nondeterministic
  and over-fetches. Year-quantization is the right balance for the
  call-reduction goal of this story.
- **Correctness is slicing, not approximation:** the canonical range is always a
  *superset* of the requested window, so slicing to `from<=date<=to` returns
  exactly the bars a direct fetch would. Adjusted-close drift is a function of
  *when* you fetch, not of the query range, so a wider query returns the same
  adjusted values for the overlapping dates within a single fetch.
- **No goldens / engine-test impact:** `FrozenMarketData` (US-21.4) and the
  conftest engine mocks replace `MarketDataService` wholesale, so normalization
  is only reachable in `test_market_data.py`; this keeps the change low-blast-radius.
- No new financial formula; no academic citation. Methodology unchanged.
