## Story

As a **developer or agent responsible for this project's dependency hygiene**, I
want each of the six outstanding dependency advisories assessed and recorded —
reachability, minimum safe version, and golden / analytic impact — **without
changing any version**, so that the remediation that follows is scoped against
fact instead of guesswork.

## Context

US-36.2 built the scheduled `dependency-audit.yml` workflow (weekly `pip-audit` +
`npm audit`) and **deliberately deferred acting on anything it finds** — "acting
on any vulnerability the scan finds ... is a follow-up, not part of this slice"
(US-36.2 § Out of scope). That first real run surfaced six advisories:

Backend (`services/quant-engine/requirements.txt`, pinned exact):
- `starlette==0.48.0`
- `pypdf==6.9.1`
- `python-multipart==0.0.20`
- `pydantic-settings==2.13.1`
- `python-dotenv==1.1.1`

Frontend (transitive, dev / build-time, low severity):
- `@babel/core`

Backend versions are pinned exact **because the suite's route-introspection and
golden tests are sensitive to FastAPI / Pydantic internals** (`requirements.txt`
header; US-36.2 context). Three of the five backend advisories — `starlette`,
`pydantic-settings`, `python-dotenv` — sit directly on that sensitive path.
Scoping a bump before knowing whether it moves a golden is the "fix before the
cause is named" failure the findings-first pattern exists to prevent. So this
story assesses; it changes nothing.

**Offline constraint.** Live `pip-audit` / `npm audit` could not be re-run when
this story was drafted (`01-delivery-brief.md` § risks). The six-advisory list is
carried from US-36.2 § Out of scope, the `2026-08-27-next-epic-or-story` delivery
brief, and the roadmap open-items bullet — all three agree, none re-verified
against a current vulnerability database. The assessment must state where its
advisory data came from and flag any advisory it cannot confirm against a source,
rather than assuming the carried list is current and complete.

**Precedent.** Epic 36 (built the scan, deferred the fix) and Epic 21 (test /
architecture hardening). Findings are recorded as `F-1..F-n` and folded into the
epic PRD at close-out, per the Epic 32 / Epic 36 findings-list convention.

Implementer must read:
- `docs/product/stories/US-36.2-dependency-vulnerability-scan.md` — § Out of scope
  for the exact advisory set and the goldens-sensitivity rationale.
- `.github/workflows/dependency-audit.yml` and `scripts/audit_dependencies.py` —
  the live scan definition; confirm the advisory set against a current run (or the
  workflow's most recent run output) at implementation time.
- `services/quant-engine/requirements.txt` — the pinned set and the "why pinned

## Test plan

This is an audit. There is no new test code; the "test" is the assessment method,
and it must be reproducible from what the document records.

Assessment method (record it in the document):

- **Advisory-data lookup.** Under the offline constraint, source each advisory's
  id / severity / affected-version range from the carried US-36.2
  design-verification output, cross-checked against any offline advisory-database
  mirror and the packages' own release notes / changelogs. Mark anything
  unconfirmed. When network is available, a live
  `python scripts/audit_dependencies.py` (or the `dependency-audit.yml` workflow)
  is the confirming source.
- **Reachability / import-graph check.** For each backend package, trace whether
  `services/quant-engine/app/` exercises the vulnerable API — e.g.
  `python-multipart` / `starlette` request-parsing on the import routes, `pypdf`
  in the broker-PDF importer under `app/importers/`, `pydantic-settings` /
  `python-dotenv` in settings loading under `app/core/`. Record the call sites
  found (or their absence).
- **Trial-bump observation.** In a throwaway virtualenv (never the committed one),
  bump each candidate to its AC4 version and run the golden, route-introspection
  and methodology suites; record any golden diff or analytic-output change.
  Discard the environment and the bump — the committed manifests stay
  byte-identical (AC9).

Regression / guardrail:

- `python scripts/run_all_tests.py` green against the unchanged repo.
- Backend goldens and `apps/desktop/src/**/dashboardGoldens.ts` byte-identical —
  nothing in this story touches analytics or schema.
- No methodology or contract doc changes — this story establishes no formula and
  no field.

## Notes / decisions

- **Why findings-first.** Backend deps are pinned exact because the golden and
  route-introspection tests are sensitive to FastAPI / Pydantic internals;
  `starlette`, `pydantic-settings` and `python-dotenv` sit on that path. Assessing
  reachability and golden impact before scoping a bump is the point of the
  pattern.
- **Why the frontend advisory is its own ticket.** `@babel/core` is transitive,
  low-severity, dev / build-time — likely a lockfile-only bump with no runtime
  surface. Keeping it off the backend ticket's critical path lets it land
  independently.
- **Offline sourcing.** The six-advisory list agrees across three prior artifacts
  but was not re-verified against a live database when this story was drafted; AC6
  forces the document to be explicit about that.
- **Precedent.** Epic 36 built the scan and deferred the fix; Epic 21 is the
  hardening sibling. Findings fold into the PRD as `F-n` at close-out per Epic 32
  / Epic 36.
