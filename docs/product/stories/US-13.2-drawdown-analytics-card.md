# US-13.2: Drawdown Analytics card

**Epic:** 13 — Risk Analytics Tab
**PRD:** [`epic-13-risk-analytics-tab.md`](../prd/epic-13-risk-analytics-tab.md)
**Status:** Done
**Last updated:** 2026-06-01

## Story

As a **portfolio researcher**, I want a Drawdown Analytics card on the Risk
tab that shows me the underwater curve of my synthetic portfolio plus the
top-5 historical drawdown episodes (peak / trough / recovery dates,
magnitude, duration, underwater days), so that I can pre-decide a risk
budget anchored in how bad past drawdowns actually got — and how long
recovery took — rather than reasoning abstractly about volatility.

## Context

US-13.1 (Done) added the Risk tab with one card (`StressScenariosCard`).
This story adds a second card directly below it in the same
`.risk-shell-stack` flex column. The underlying drawdown computation
(`_build_drawdown_from_return_index`) already exists in
`services/quant-engine/app/analytics/risk.py:1219` but is only consumed
inside the diagnostics pipeline — never surfaced as a chart, and the
episode-identification algorithm documented in
`docs/finance/financial-methodology.md` §Drawdown episode identification
is not yet implemented in code. This story closes that gap.

The Risk tab now ships with two cards by the end of this story; US-13.3
(VaR / distribution) adds the third.

## Acceptance criteria

  `current_drawdown_pct(underwater_series)`,

## Notes / decisions

- **Methodology already complete.** §Wealth Index and Drawdown
  (line 114) + §Drawdown episode identification (line 129) were
  appended during the Epic 13 foundation pass with the full algorithm
  + Magdon-Ismail & Atiya (2004) + Goldberg & Mahmoud (2017)
  citations. No methodology ticket needed in this story.
- **Pure-analytics module is testable in isolation.** Six fast
  fixture-based tests verify the episode-identification algorithm
  without touching `MarketDataService` — same separation pattern
  that `analytics/correlation.py` follows (scalar functions tested
  directly, engine tested separately).
- **Lookback cap rationale.** The "max" window fetches 3000
  calendar days (~8.2 years). Past that, factor stability concerns
  outweigh the value of more data, and FMP cache misses become
  common. The constant `_MAX_LOOKBACK_CALENDAR_DAYS = 3000` is
  module-level with a comment so the value is greppable and
  documented at the implementation site.
- **Trust contract.** All drawdown outputs are
  synthetic-history trust class (current holdings × historical
  prices, never broker-truth). The wrapper `trust` field is
  `'synthetic'` on happy path, `'unavailable'` on every failure
  mode; never partial / degraded.
- **Component pattern.** Self-fetching with internal window state
  (closest existing precedent: `FactorAttributionCard.tsx`).
  `RiskPanel` does not own the drawdown state — refreshing the
  Risk tab does not require panel re-renders for window changes,
  matching the StressScenariosCard pattern from US-13.1.
- **Test mock pattern for the RiskPanel two-card test.** Use URL-
  routed `vi.fn().mockImplementation` (matching on
  `/engines/stress/run` vs `/engines/drawdown/run` in the request
  URL), not `mockResolvedValueOnce` chains — the chain pattern
  breaks fragile when card order matters. See `installFetchMock`
  pattern in the test fixtures.
- **No backend formula additions.** The analytics module
  composes existing helpers (`_build_drawdown_from_return_index`)
  plus the new episode walker — every formula traces to a
  methodology section already in place.
