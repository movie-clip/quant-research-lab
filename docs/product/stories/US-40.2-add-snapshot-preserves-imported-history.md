## Story

As a **portfolio researcher**, I want adding a new statement to an existing
portfolio (rather than replacing it outright) to keep the reproducibility and
history data I would have kept had I chosen replace, so that which import
mode I picked never silently decides whether my portfolio's history is still
there tomorrow.

## Context

Today, `processImportedFiles`'s `add_snapshot` branch (`App.tsx:767-795`)
passes `importedHistorySnapshot: null` to `saveImportedSnapshotNode`
(`App.tsx:789`), while the `replace` branch on the very same function passes
`nextAnalysis.snapshot` (`App.tsx:801`) — the real, just-imported analyze-
upload response. The result: a researcher who chooses "Add statement" instead
of "Replace" gets a node whose `historySource.importedHistorySnapshot` is
always `null`, discarding the reproducibility/replay data the replace path
correctly keeps. This is a genuine, previously-known gap — it was explicitly
scoped out of two prior technical plans (2026-08-24 run's `02-` and
`03-technical-plan`), each time because the fix requires **client-side
recombination of two `PortfolioOverview`-shaped objects** (the existing
snapshot's and the newly imported one's) that was not designed in either
pass.

**What "preserves history" means here (value statement, not a mechanism).**
`add_snapshot` should behave like `replace` from the researcher's point of
view: choosing to add a statement rather than replace the portfolio should
never be the reason reproducibility data silently disappears. This story does
not prescribe how the two `PortfolioOverview`-shaped payloads are combined —
that is exactly the design question the two prior technical plans correctly
declined to answer without a dedicated pass, and it stays tech-lead DESIGN's
job here too.

**Sequencing note (informational, not a hard dependency).** Per the delivery
brief's own sequencing (`02-delivery-brief.md` § Sequence), US-40.1 is
expected to land first. It has no formal code dependency on this story (no
shared function, per `01-scout.md` § Blast-radius / conflict notes), but it
does establish "what does a frozen snapshot's own metadata correctly look
like" for `run_metadata`, which the recombination design below may want to be
consistent with, since a `PortfolioOverview` object being merged here carries
its own `run_metadata`.

Implementer must also read: `apps/desktop/src/app/App.tsx:767-801`
(`processImportedFiles`'s `add_snapshot` and `replace` branches, side by
side); `apps/desktop/src/app/portfolioWorkspaceStorage.ts:301-334`
(`saveImportedSnapshotNode`, the persistence call both branches feed);
`apps/desktop/src/features/portfolio/workspaceTypes.ts`'s
`ImportedHistorySource` union (the three-way `imported_replay` /
`history_context` / `none` shape a design pass will need to reconcile
between the two combining snapshots).

## Acceptance criteria

- [x] AC1 — Using "Add statement" (`add_snapshot` mode) to layer a new import
  onto an existing snapshot results in a node whose history/reproducibility
  data is not silently discarded — a researcher who adds a statement retains
  what they would have retained had they chosen "Replace" instead.
- [x] AC2 — After an add_snapshot import, replay/history-derived views (e.g.
  the Dashboard's history-backed cards) that read the resulting node's
  history source reflect the combination of the prior snapshot's history and
  the newly imported statement's history — not just the newly imported
  statement in isolation, and not silently falling back to the pre-existing
  snapshot's history alone.
- [x] AC3 — If the two snapshots' history data cannot be cleanly combined
  (e.g. conflicting or incompatible history sources), the resulting node
  discloses the degradation to the researcher rather than silently dropping
  one side, silently picking one side without disclosure, or fabricating a
  merged value that doesn't correspond to either input.
- [x] AC4 — The `replace`-mode import path's behavior is unchanged by this
  story — its history data continues to be preserved exactly as it is today.

## Test plan

Frontend (vitest), most likely extending `App.test.tsx` or wherever
`processImportedFiles`'s import-mode branching is currently covered (final
module is the tech lead's / frontend-engineer's call):

- add_snapshot preserves history — the resulting node's
  `historySource.importedHistorySnapshot` (or whatever shape the design pass
  settles on) is non-null and derived from the combination of both snapshots,
  not the `null` it is today.
- replace-mode regression — the existing replace-path behavior (history
  preserved from the just-imported statement) is unchanged.
- Degraded-combination case — a fixture pair whose history sources cannot be
  cleanly combined produces a disclosed degradation, not a silent drop or a
  fabricated merge (AC3).
- Sequential-add regression — adding a second statement on top of a node that
  itself already came from a prior add_snapshot (a chain, not just one
  add on top of the original base) continues to preserve history through the
  chain, not just one level.

Regression / guardrail:

- No-fabrication regression: a combined history node never presents merged
  data as if it came from a single import when the two sources actually
  conflict (AC3).
- `python scripts/run_all_tests.py` green.
