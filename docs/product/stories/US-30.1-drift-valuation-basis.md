# US-30.1: Fix the drift valuation basis — honest anchor, fail-closed TWR, truthful note

**Epic:** Epic 30 — Exposure Improvements
**PRD:** [`epic-30-exposure-improvements.md`](../prd/epic-30-exposure-improvements.md)
**Status:** Done
**Last updated:** 2026-07-08

## Story

As a **portfolio researcher**, I want the vs-Market drift cards and chart to
show my portfolio's actual return versus the benchmark, so that a glance at
the Exposure tab tells me the truth — never a −6226% fabricated by dividing
real market moves by a broken denominator.

## Context

PRD findings F-1/F-2 (verified 2026-07-08, reproduced exactly against the
IB2026.csv portfolio + SPY). The drift request path
(`DriftEngineRequest` → `build_imported_snapshot_from_request`) carries
positions + cash balances but **no `statement_totals` and no ledger**.
`PortfolioStateEngine.build_daily_states` anchors
`base_cash = starting_nav − opening_positions_value`
(`engine/portfolio_state.py:52,124`); with `starting_nav = None → 0.0`, cash
reconstructs as ≈ **−$62.6k** (the request's real `cash_balances` are
ignored), day-one `total_portfolio_value` is exactly $0.00, and
`_time_weighted_daily_return` divides real ~$62k market moves by ±$1k noise —
daily "returns" of −336%/+1763% compound into the reported −6226.32%. The
result reaches the screen labeled `trust="synthetic"` with the note
"Broker-ledger replay: compounded time-weighted return" — false on a path
with no ledger to replay.

Two fixes, layered:

1. **Honest basis (primary).** With no ledger there are no external flows, so
   the TWR machinery has nothing to neutralize — the drift engine's window
   return and indexed series switch to the **market-value chain of current
   holdings** (`total_market_value`), which is the synthetic-history
   convention every other Exposure/Risk engine already uses and exactly what
   the existing `Synthetic` badge claims. The TWR-with-flows machinery is
   retained **only** when the snapshot carries ledger entries (the US-27.8
   deposit-neutrality contract stays pinned). Secondarily,
   `PortfolioStateEngine` stops fabricating cash: when
   `statement_totals.starting_nav` is absent, `base_cash` anchors from the
   snapshot's own `cash_balances` (base-currency sum; non-base cash follows
   the existing US-27.8 FX-fallback disclosure) instead of
   `0 − opening_value`.
2. **Fail-closed chain (defense in depth).** A computed daily return
   ≤ −100% is impossible for a long-only portfolio and means the valuation
   inputs are broken — the window must fail closed (`trust="unavailable"`,
   explanatory note), never compound a sign-flipped `growth` into a
   plausible-looking number.

## Notes / decisions

- **Why market-value chain, not "TWR with reconstructed cash":** with zero
  ledger entries there are no external flows, so TWR over any constant-cash
  portfolio value reduces to the value chain itself; including a constant
  cash lump only dilutes the displayed return without adding information,
  and the synthetic convention (current holdings × historical prices,
  §Synthetic History) is what every sibling engine (correlation,
  attribution, stress, drawdown, distribution) already measures and what the
  `Synthetic` badge already claims. No new formula — this re-uses the
  documented wealth-index convention; no new citation required.
- **Fail-closed bound:** ≤ −100% daily is the impossibility bound for
  long-only portfolios (value cannot go below zero); the guard is
  deliberately NOT a clamp — clamping would fabricate. Unavailable + note.
- The F-1 fixture shape for tests: positions + cash_balances,
  `statement_totals=None`, `ledger_entries=[]` — exactly what
  `build_imported_snapshot_from_request` produces today.
