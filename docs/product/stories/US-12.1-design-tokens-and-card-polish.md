# US-12.1: Design tokens + apply to the four Exposure cards

**Epic:** 12 — UI Polish & Design System
**PRD:** [`epic-12-ui-polish-design-system.md`](../prd/epic-12-ui-polish-design-system.md)
**Status:** Done
**Last updated:** 2026-05-28

## Story

As a **portfolio researcher**, I want the Exposure tab's five new feature
cards (drift panel + indexed return chart, rolling correlation chart, factor
attribution card, multi-benchmark correlation table) to share a single set
of design tokens for color, spacing, and typography — and I want the rolling
correlation chart's text overlap and axis alignment fixed in the same pass —
so that the surface stops looking like five different features bolted
together and becomes a coherent research workbench.

## Context

Epics 9 and 11 shipped four feature cards (five files counting
`IndexedReturnChart` separately from `DriftBenchmarkPanel`). Each was built
in isolation; each hand-rolls hex colors, font sizes, spacings, and the
"Synthetic" trust badge. The rolling correlation chart additionally has a
known polish bug: dual-axis Y labels (`yAxisId="correlation"` left,
`yAxisId="beta"` right) collide with the rotated axis name labels when the
container is below ~700 px wide.

This story is the foundation of Epic 12. It introduces design tokens (CSS
variables in `apps/desktop/src/app/styles.css`, the implementer's
recommended choice unless they have a strong reason for the alternative TS
module approach — see Notes) and refactors the five cards to consume them.
The token refactor is paired with the polish fix on the rolling correlation
chart so the user sees visible improvement on day one — not just an
under-the-hood rename.

No new components are extracted here — those land in US-12.2. No backend,
no analytics, no schema changes.

Implementer must read:

- `apps/desktop/src/app/styles.css` — existing global styles + any current
  CSS variable usage (to match conventions)
- The five card files listed under Tickets — to inventory every literal
  color / spacing / font value that needs a token
- `docs/product/prd/epic-12-ui-polish-design-system.md` — for token category
  list and the success-signal definitions

## Notes / decisions

- **CSS variables vs typed TS module**: the implementer should default to
  CSS variables in `styles.css` (`:root { --color-text-primary: #...; }`),
  consumed in components as `style={{ color: 'var(--color-text-primary)' }}`.
  Rationale: lighter (no new module), no rebuild needed on token change,
  runtime themeable (US-12.4 or beyond could add a theme switcher with
  zero refactor), plays naturally with the existing `styles.css`.
  Trade-off accepted: TS doesn't type-check token names; a typo lands as
  an inherited / default style. The audit test (AC9) covers the worst
  failure mode (hardcoded hex) which is far more common than typo'd token
  names.
- **No academic citation needed** — UI design story, no formula. The
  `quant-research` skill is not relevant here.
- **Why the polish fix is in this story** (T-12.1.3) rather than US-12.3:
  the user explicitly flagged "chart doesn't look production ready,
  alignment looks off, text is overlapping" when commissioning Epic 12.
  Bundling the fix with the tokens delivers visible improvement on the
  first ship and avoids the appearance of the system getting "worse"
  during the token sweep.
- **Audit test is a regression check, not a lint rule**: this project
  doesn't have ESLint custom rules. The audit test fills that gap. If
  the audit becomes too noisy, future work can graduate it to an ESLint
  custom rule — out of scope for this story.
- **Escape-hatch comment convention**:
  `// design-system: escape-hatch: <one-line reason>` immediately above
  the offending literal. The audit test tolerates one such hatch per
  literal. Reasonable hatches: vendor-required exact values (e.g. a
  specific brand color for a logo), unsupported CSS-variable contexts.
  Unreasonable hatches: "didn't feel like making a token". Review the
  hatches at story close-out.
