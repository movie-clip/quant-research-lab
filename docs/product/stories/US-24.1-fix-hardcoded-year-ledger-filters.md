# US-24.1: Fix the hardcoded calendar-year ledger filters (latent bugs)

**Epic:** Epic 24 — Codebase Improvement
**PRD:** [`epic-24-codebase-improvement.md`](../prd/epic-24-codebase-improvement.md)
**Status:** Done
**Last updated:** 2026-06-19

## Story

As a **portfolio researcher**, I want the monthly activity series and the
withholding-tax reconciliation to cover **my statement's actual period**, not a
hardcoded year, so that importing a 2026 (or any non-2025) statement shows real
activity and a correct tax reconciliation instead of an empty/zeroed result.

## Context

Two pure-analytics functions hardcode the calendar year `2025` (catalogued in
Epic 23 / US-23.2 as the only High-severity latent bugs in
[`docs/tech-debt-register.md`](../../tech-debt-register.md) → Epic 24 backlog
row US-24.1):

- `app/analytics/activity.py` `build_activity_series` (line ~24):
  `if entry.date.year != 2025: continue` — **silently drops every ledger entry
  not dated 2025**, so a 2026 statement yields an empty monthly activity series.
- `app/analytics/reconciliation.py` `_negative_withholding_total` (line ~24):
  `... and candidate.date.year == 2025` — the withholding-tax reconciliation
  total only ever sums 2025 entries, so a 2026 statement's withholding check
  reconciles against `0`.

The year filter is an **anomaly**: every sibling reconciliation actual in
`build_reconciliation_summary` (dividends, fees, interest, deposits) sums the
ledger with **no** year filter, and `build_activity_series` already buckets by
`%Y-%m`, so the month grouping handles any span. The snapshot itself already
scopes the ledger to the imported statement(s). Removing the hardcoded-year
filters is therefore both the **consistent** and the **correct** fix.

Implementer must read:
- `app/analytics/activity.py` + `app/analytics/reconciliation.py` (the two filters).
- `app/domain/ledger.py` `snapshot_to_ledger` — confirms the ledger is already
  scoped to the snapshot's statement(s).
- `docs/finance/financial-methodology.md` — the reconciliation / activity
  sections, to document the period-scoping rule (no hardcoded year).

## Notes / decisions

- **Why removal (not "derive the year 2025→statement-year"):** the snapshot's
  ledger is already scoped to the imported statement(s) by
  `snapshot_to_ledger`, and the sibling reconciliation actuals (dividends, fees,
  interest, deposits) already sum the ledger with no year filter. Removing the
  year filter makes the two outliers consistent with that, fixes 2026+, and is a
  no-op for any single-year (e.g. 2025) statement — so the goldens hold. If, in
  review, removal is found to change 2025 output (it should not), fall back to
  deriving the year(s) from the statement period rather than re-introducing a
  literal — but never silently drop all entries.
- **No new formula; no academic citation needed** — this corrects a scoping bug,
  it does not introduce a new metric.
- **Behaviour-aware fix (Epic 24 discipline):** unlike Epic 23's deletions, this
  changes output for non-2025 statements by design; the 2025 goldens are the
  behaviour-neutral anchor.
