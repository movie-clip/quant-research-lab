## Story

As a **portfolio researcher**, I want the app to only ever show me a trust
signal that describes the same moment as the numbers it sits beside — so that
when I reopen a persisted snapshot days after importing it, nothing on screen
implies the snapshot's classification was just recomputed against today's
market when it was actually frozen at import, and nothing in the codebase is
one careless read away from making that mistake again.

## Context

Two places today silently misrepresent frozen data as current, both the same
bug class the 2026-08-24 run's Finding 1 already fixed once for a different
field (`getBenchmarkTrust`, `CR-1-frontend.md`):

1. **No freeze-date signal in the snapshot picker.** The snapshot picker
   labels an imported/base node just the literal string `"base"`
   (`variantLabels.ts:4,10,23`, rendered via `App.tsx:876-877`) — no date, no
   timestamp, nothing distinguishing a snapshot imported this morning from one
   imported three months ago. A researcher switching between snapshots has no
   way to tell, from the label alone, how stale a given one is. The date this
   story needs already exists engine-side and does not require a schema
   change: `ExposureRunReproducibilityMetadata.input_imported_at` /
   `.snapshot_as_of_date` (`exposure_engine.py:152-162`) are already computed
   per snapshot, just never threaded to the picker.

2. **`run_metadata.source_status`/`.confidence` are always live, never
   frozen, and sit beside fields that are.** Per the quant research brief
   (`03-quant-research.md` § Field census, § Consumer census — binding on this
   story), `run_metadata.source_status.lookthrough_resolution`,
   `run_metadata.source_status.benchmark_holdings`, and `run_metadata.confidence`
   (`exposure_engine.py:79-91`, assembled fresh on every engine call from
   `_build_exposure_source_status` at `:131-149`) are structurally the same
   coupling Finding 1 exploited: they live on the same response object as the
   6 fields `ImportedExposureOverride` already correctly freezes at import
   (`availability`, `lookthrough`, `market_overlap`, `current_state_concentration`,
   etc. — `docs/contracts/exposure-fields.md:37`), but are excluded from that
   freeze, so they always reflect *this render's* live classification even
   when shown alongside a frozen snapshot.

**Reachability is different from Finding 1 (binding context, not a reason to
skip this).** The research brief's exhaustive grep found **zero** current
frontend or backend consumers of these 3 fields for trust display — this
residual is dormant, not live and reachable the way Finding 1 was
(`03-quant-research.md` § Consumer census, § Same bug class?). That
classifies this half as MATERIAL/preventive, not CRITICAL/urgent — but the
trap is real: a future card reaching for `run_metadata.source_status` to add
a badge is exactly how Finding 1 happened the first time.

**The required fix direction for the trust-classification half (quant
research brief, binding on this story's ACs and on tech-lead DESIGN).** Per
`03-quant-research.md` § Fix direction, the recommended approach is **not** to
extend `ImportedExposureOverride`'s freeze mechanism to cover these 3 fields.
They are strictly redundant re-derivations of `availability`'s own
classification (§ Duplication finding) — there is nothing left to preserve
that isn't already frozen elsewhere — and a nested nested-nested (`run_metadata`
sub-object) nested merge would reproduce the exact split-vintage-object risk
one layer down that this story exists to close, not extend
(`03-quant-research.md` § Fix direction, point 4). The fix is: retire these 3
fields as a trust source, permanently, everywhere — a contract-doc statement
plus a regression test, not a new freeze path. If tech-lead DESIGN weighs
this differently (e.g. wants `run_metadata` internally self-consistent as a
documented invariant regardless of consumer behavior), the nested-merge risk
named above must be called out explicitly in that design, not treated as a
routine type extension (`03-quant-research.md` § risks).

**No backend schema change is implied.** The three fields are already
self-consistent within one engine call; the defect this story closes is a
consumption-discipline gap (a future consumer reading a live field next to
frozen ones), not a computation error.

**Candidate simplification, not required by this story.** Independent of the
freeze/staleness question, the research brief found `_build_exposure_source_status`
and `_build_exposure_availability` (`exposure_engine.py:131-149`, `:165-215`)
separately re-implement the identical three-way classification logic over the
same inputs, and `run_metadata.confidence` is a pure recombination of two
fields `availability` already carries (`03-quant-research.md` §
Duplication finding). This is a real duplication smell, but fixing it is not
required to close the trust-signal defect. Tech-lead DESIGN's call whether to
ticket it inside this story as a simplification, or leave it as a noted
opportunity for a future pass.

## Acceptance criteria

**(a) Freeze-date signal in the snapshot picker**

- [x] AC1 — The snapshot picker's option label for a persisted imported/base
  snapshot node discloses the date that snapshot's underlying data was
  captured, not just the bare `"base"` string it shows today
  (`variantLabels.ts`, rendered via `App.tsx`'s snapshot picker).
- [x] AC2 — A variant node built on top of an imported base continues to
  disclose the base's import/capture date somewhere in its picker label — the
  date is not silently dropped once a variant is layered on top.
- [x] AC3 — When no import/capture date exists for a node (e.g. an
  in-progress working draft with no persisted import behind it), the picker
  label renders exactly as it does today — no placeholder date, no fabricated
  or blank date string standing in for absence.

**(b) `run_metadata.source_status`/`.confidence` retired as a trust source**

- [x] AC4 — `docs/contracts/exposure-fields.md` states, alongside the
  existing frozen-fields disclosure (line 37), that
  `run_metadata.source_status.lookthrough_resolution`,
  `run_metadata.source_status.benchmark_holdings`, and `run_metadata.confidence`
  are always live/per-render values, are redundant re-derivations of
  `availability`'s own classification, and must never be read as the trust
  basis for a snapshot whose `availability`/look-through/benchmark-overlap
  fields are frozen at import.
- [x] AC5 — No component under `apps/desktop/src/features/portfolio` reads
  `run_metadata.source_status.*` or `run_metadata.confidence` to compute or
  display any trust/badge/status value — enforced by a permanent regression
  test, mirroring the shape of the already-shipped `BenchmarkPositioningCard`
  fix, not a one-time grep.
- [x] AC6 — Every trust badge a researcher sees on a reopened, persisted
  imported snapshot continues to be sourced from the already-frozen
  `availability` / `current_state_concentration` / `market_overlap` fields
  exactly as before this story — this story changes documentation and
  consumption discipline around `run_metadata.source_status`/`.confidence`,
  it does not change any value a researcher currently sees.
