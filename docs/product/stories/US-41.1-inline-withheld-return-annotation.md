# US-41.1: Explain a withheld-return gap where it appears on the Performance & Benchmark chart

**Epic:** 41 — Documentation & Roadmap Accuracy Reconciliation
**PRD:** none yet — see `## Open decisions`
**Status:** Backlog
**Last updated:** 2026-08-26

## Story

As a **portfolio researcher**, I want the exact date where the Performance &
Benchmark line breaks to tell me why, right there on the chart, so that I do
not have to leave the chart to find the reason in `ReplayDisclosuresCard` or
the card's own summary note.

## Context

Today the gap is disclosed twice — `ReplayDisclosuresCard`'s prose note and
`PerformanceBenchmarkCard.tsx`'s own summary line ("N days excluded... see
Replay Disclosures") — but neither disclosure sits *at* the point in the
chart where a researcher actually encounters the break. This story closes
that specific reading gap. It does not change what is disclosed, or add a
new disclosure — only where an existing one is reachable from.

**Grounding.** `03-quant-research.md` (this run) establishes, against the
live IB2026 fixture and independent recomputation, not just a read of the
code:

- Per-date classification needs no cross-date context — every needed signal
  lives on the single `DailyPortfolioState` for that date (§ Classification
  branches).
- `replay_disclosures()`'s run-level reason string is written with two
  branches (`reconciliation_adjustment`, `unbacked_cash_flow`) but only one
  is live under current semantics (`unbacked_cash_flow` materiality,
  US-34.8) — the other never fires today (§ Classification branches).
- `portfolio_return_pct` can be `null` for **three** distinct causes, only
  one of which is a per-date, state-carried fact the others are a run-level
  scalar and an adjacent-pair comparison (§ Scope of what the field
  explains). This governs the AC framing below directly.

## Acceptance criteria

- [ ] AC1 — **Every point whose date is in `withheld_return_dates` gets an
  inline reason naming that date's specific cause**, visible at or from that
  point on the chart, without the researcher needing to open Replay
  Disclosures or scroll to the card's summary note. (Narrowed framing per
  `03-quant-research.md` § Scope of what the field explains — see AC2 for
  why this is not "every null point.")

- [ ] AC2 — **A point whose `portfolio_return_pct` is null for a reason
  other than state-level withholding gets no inline reason at all** — no
  cause is fabricated for whole-series basis suppression or a
  zero-denominator gap, both of which are run-level or adjacent-pair facts,
  not something a single date can honestly explain (guardrail 4;
  `03-quant-research.md` § Scope of what the field explains, causes 1–2 vs.
  cause 3). On the current IB2026 fixture every null point happens to be a
  withheld-state point, so this AC is invisible today — the contract must
  hold regardless of that coincidence.

- [ ] AC3 — **A non-withheld date carries no inline-reason value at all** —
  never an empty string, never a "no reason" placeholder. Absence is
  absence.

- [ ] AC4 — **The backend surfaces the per-date reason as
  `PerformancePoint.withheld_reason: str | None`**, computed via a shared
  classifier so `replay_disclosures()`'s existing run-level string and this
  new per-point field read one classification, not two independently
  maintained ones (`03-quant-research.md` § Field proposal). This is a
  constraint on the implementation the research carried forward for
  correctness, not a full contract — nullability semantics beyond "null iff
  not withheld" (exact TS prop shape, exact component wiring) are the tech
  lead's design-pass call.

- [ ] AC5 — **The run-level disclosures are unaffected.**
  `withheld_return_dates`, `withheld_return_reason`, the
  `ReplayDisclosuresCard` note and `PerformanceBenchmarkCard`'s existing
  summary line keep their current meaning, computation and wording — this
  field is additive only (`03-quant-research.md` § Additive-only
  confirmation).

- [ ] AC6 — **The inline reason states the specific cause in the same
  register as the existing disclosures** (e.g. names the unbacked-cash-flow
  mechanism the way the run-level note already does), not a generic "data
  withheld" placeholder — the point of this story is specificity at the
  point of use.

## Notes / decisions

- **Why a backend field, not client-side re-derivation.** The human approved
  the thin-backend-field approach over re-implementing
  `replay_disclosures()`'s classification logic a second time in
  TypeScript, per this run's work order. `03-quant-research.md` grounds why:
  a client-side classifier would need to reproduce the same
  materiality-adjusted `unbacked_cash_flow` rule TypeScript-side, with no
  shared source of truth going forward — the prior chart-audit run's own
  Finding 2 (a dead duplicate formula, deleted for exactly this drift risk)
  is the concrete precedent this approach avoids repeating.
- **Why the AC framing is narrower than "every null point gets a reason."**
  `portfolio_return_pct` can be null for three distinct causes, and only one
  of them (state-level withholding) is a fact a single date can honestly
  carry. An AC that promised an explanation for every null point would be
  correct on the current IB2026 fixture only by coincidence, and would
  become a fabricated attribution on a future statement where basis
  suppression or a zero-denominator gap produces a null point that is not a
  withheld-state point.
