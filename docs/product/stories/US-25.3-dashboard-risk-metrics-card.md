# US-25.3: Risk metrics card (volatility, drawdown, concentration)

**Epic:** Epic 25 — Dashboard Performance & Risk Summary
**PRD:** [`epic-25-dashboard-performance-risk-summary.md`](../prd/epic-25-dashboard-performance-risk-summary.md)
**Status:** Done
**Last updated:** 2026-07-04

## Story

As a **portfolio researcher**, I want **to see portfolio volatility,
drawdown, and concentration on the Dashboard tab**, so that **I get a risk
snapshot alongside performance without switching to the Risk tab**.

## Context

`DiagnosticsResult` (`volatility_summary`, `drawdown_summary`,
`risk_concentration_summary`) is already fetched by `App.tsx`
(`diagnosticsAnalysis` state, populated by `runDiagnosticsEngine` /
`runImportedDiagnosticsEngine`) and already powers `RollingFactorLoadingsCard`
via the `exposureResult`/`factorModel` composition — but `diagnosticsAnalysis`
itself is never passed to `DashboardPanel`, and no card reads
`volatility_summary` / `drawdown_summary` / `risk_concentration_summary`.

**Deliberately does not use `DashboardHistoryResult.max_drawdown_pct`.** That
field lives behind the dashboard-history investor-economics withholding
policy (`docs/contracts/dashboard-fields.md`: "`max_drawdown_pct` and other
non-allowlisted investor-economics outputs must stay `null`/hidden" even when
TWR/benchmark/excess scalars are admitted). `DiagnosticsResult.drawdown_summary`
is a separate computation path with its own `section_trust`
(`risk_contribution_path`) and is not part of that withholding family — using
it here means the card can show real numbers on days the dashboard-history
scalar would be withheld, provided diagnostics' own trust level supports it.

Read before implementing:
- `docs/finance/financial-methodology.md` §Volatility and Relative Risk,
  §Wealth Index and Drawdown, §Risk Contribution and Concentration (note: the
  concentration section currently has no formulas — US-25.4 fixes that; do
  not block this story on it, but do not invent a formula here either — render
  the values, cite the section, and let US-25.4 backfill the math)
- `services/quant-engine/app/schemas/diagnostics.py`:
  `DiagnosticsRiskConcentrationSummary` (`factor_hhi`, `position_hhi`,
  `top_1_factor_risk_share`, `top_3_factor_risk_share`,
  `top_1_position_risk_share`, `top_5_position_risk_share`)
- `apps/desktop/src/app/App.tsx` — `diagnosticsAnalysis` state already exists;
  this story threads it into `DashboardPanel` as a new prop, mirroring how
  `exposureResult` and `factorModel` are already threaded

## Acceptance criteria

- [x] AC1 — When `diagnosticsAnalysis` is present, the card shows portfolio
      volatility, benchmark volatility, downside volatility, and tracking
      error from `volatility_summary`, each `n/a` when its individual field is
      `null`.
- [x] AC2 — The card shows current and max drawdown from
      `drawdown_summary` (diagnostics path, not dashboard-history), each
      `n/a` when `null`.
- [x] AC3 — The card shows factor HHI, position HHI, and the top-1/top-3
      (factor) / top-1/top-5 (position) risk-share figures from
      `risk_concentration_summary`, each `n/a` when `null`.
- [x] AC4 — The card's trust badge reflects
      `diagnosticsAnalysis.run_metadata.section_trust.risk_contribution_path`
      (`verified_adjusted_close` / `degraded_unverified_return_basis` /
      `unavailable`) — never a generic "Synthetic" label disconnected from
      this specific section-trust field.
- [x] AC5 — When `diagnosticsAnalysis` is absent or
      `availability.historical_sections_available = false`, the card renders
      a single EmptyState, not partially-populated `n/a` rows.
- [x] AC6 — This card never reads `DashboardHistoryResult.max_drawdown_pct`
      — a code-review-visible fact (single diagnostics-only data source for
      this card), not just a documented rule.

## Test plan

Frontend (vitest):
- `DashboardPanel.test.tsx` — **5 new tests**: renders volatility/tracking-
  error fields with `n/a` for null; renders drawdown fields from diagnostics
  (asserted against a fixture where `dashboardHistory.max_drawdown_pct` is
  deliberately different, to prove the diagnostics value — not the withheld
  one — is what renders); renders HHI + risk-share fields; trust badge follows
  `section_trust.risk_contribution_path` across its three states; single
  EmptyState when `diagnosticsAnalysis` absent or unavailable.

Regression / guardrail:
- Existing diagnostics-consuming tests (`RollingFactorLoadingsCard.test.tsx`)
  unaffected — this story only adds a new consumer of already-fetched state,
  it does not change `runDiagnosticsEngine`/`runImportedDiagnosticsEngine`.
- `dashboardGoldens.ts` IB2026/FF2026 goldens unaffected (no backend change).

## Out of scope

- No new backend field, engine, or route — every field here is already
  computed by the existing diagnostics engine.
- No attempt to reconcile or explain why diagnostics drawdown and
  dashboard-history drawdown can differ in value — that is expected (different
  truth-class/withholding paths) and is exactly why this story deliberately
  picks the diagnostics path; a mismatch is not a bug to fix here.

## Notes / decisions

- Concentration (HHI, top-N risk share) has no formula in
  `financial-methodology.md` today — only prose. This story renders the
  already-computed values as-is; US-25.4 is responsible for backfilling the
  formula section (with an HHI citation — e.g. Hirschman 1964 / Herfindahl
  1950, standard concentration-index precedent) so the guardrail
  ("methodology traceability") is satisfied by epic close, not by this
  individual story.
- Defensive-guard fix found by the full suite (`run_all_tests.py`), not by a
  story-plan test: `App.test.tsx` exercises a real scenario where
  `diagnosticsAnalysis` is non-null and `availability.historical_sections_available`
  is `true`, but the individual `volatility_summary`/`drawdown_summary`/
  `risk_concentration_summary` sub-objects are absent — the card crashed on
  first render. Fixed by treating a missing sub-object as unavailable (fail
  closed) rather than trusting `availability` alone; added a dedicated
  regression test for this exact shape. This is the kind of gap `verify-story`
  running the canonical suite (not just the story's own new tests) exists to
  catch.
