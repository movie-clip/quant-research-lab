# US-13.1: Risk tab + Stress Scenarios card

**Epic:** 13 — Risk Analytics Tab
**PRD:** [`epic-13-risk-analytics-tab.md`](../prd/epic-13-risk-analytics-tab.md)
**Status:** Done
**Last updated:** 2026-06-01

## Story

As a **portfolio researcher**, I want a third top-level tab labeled **Risk**
that opens to a **Stress Scenarios** card showing each predefined scenario's
projected portfolio impact, so that I can pre-decide a risk budget for events
like a broad market sell-off, a rates-down rally, or an inflation
reacceleration — without leaving the desktop app or asking the engine an
ad-hoc question.

## Context

Today the app has two tabs (Dashboard + Exposure). The stress-scenarios
computation already exists in
`services/quant-engine/app/analytics/risk.py:1401`
(`build_stress_scenarios(model)`) and runs inside the diagnostics pipeline,
but the result is never surfaced on the UI — the researcher has no way to see
"what does the Broad Market Selloff scenario imply for my portfolio." This
story adds the Risk tab and the first card, wiring the existing analytic
through a dedicated route and a Epic-12-compliant card component.

This is the first story of Epic 13 (3-card tab); subsequent stories add
Drawdown (US-13.2) and VaR / Distribution (US-13.3) cards to the same tab.
Tab navigation plumbing therefore lands here so the first ship is "Risk
tab exists and works for one card."

## Notes / decisions

- **Schema reuse, not extension.** The pre-existing
  `StressScenarioResult` schema (reconciliation.py:517) already has
  `estimated_return_pct: float | None` and `status: Literal["ok",
  "unavailable"]` — meaning the original implementer already accounted
  for the "factor model empty" path. This story therefore changes no
  per-scenario field. Only the *response wrapper* (`StressEngineResponse`)
  is new, and only it carries the engine-level `trust` field. The
  diagnostics engine already emits unavailability via its
  `_build_unavailable_stress_scenarios(...)` helper
  (diagnostics_engine.py:308) — the new stress engine produces the same
  shape so consumers are interchangeable.
- **Why a dedicated route rather than reuse diagnostics.** Diagnostics
  returns a 30+ field payload; for the Risk tab we want the minimum
  surface (single response with just the scenarios), both for clarity
  and so that the card's `useEffect` fetch is cheap and traceable.
  Reconciliation test (third backend test) pins the contract that the
  two paths cannot diverge.
- **No new formula.** §Stress Scenarios is already in
  `financial-methodology.md` (line 311) with the formula
  `estimated_scenario_return = sum(current_factor_loading_i * shock_i)`.
  Academic precedent (Litterman & Winkelmann 1998; Connor, Goldberg &
  Korajczyk 2010) is in the Research Brief used to author Epic 13's PRD
  — will be added to the methodology section by US-13.5 close-out, not
  here.
- **Tab plumbing lands in this story** (not a separate US-13.0) so the
  first ship is "Risk tab exists and works." Subsequent stories (13.2,
  13.3) add cards to a tab that already exists, simplifying their
  scope.
- **Self-fetching card pattern** (RiskPanel manages its own fetch via
  useEffect on `[snapshot]`) matches what ExposurePanel and its children
  do — keeps App.tsx state lean and avoids replaying the
  `analyzeExposureSnapshot` vs `analyzeRestoredSnapshot` divergence that
  bit the drift fetch on restore.
- **No fabrication, fail-closed**: when the factor model is empty, the
  card renders an EmptyState with explicit text. It does NOT render zero
  scenario rows, NOT render placeholder pcts, NOT silently hide the card.
- **ui-polish skill auto-invoked** on T-13.1.5 (card) and T-13.1.6
  (panel + tab) per the build-story cycle. Audit test
  (`designSystem.audit.test.ts`) is a regression gate.
