# US-14.2: DrawdownAnalyticsCard smart-default window fallback

**Epic:** 14 — Post-Epic-13 Bug Sweep
**PRD:** [`epic-14-post-epic-13-bug-sweep.md`](../prd/epic-14-post-epic-13-bug-sweep.md)
**Status:** Done
**Last updated:** 2026-06-01

## Story

As a **portfolio researcher**, I want the Drawdown Analytics card to
automatically fall back to a shorter window (756d → 252d → Max) when
its default 1260d window has insufficient FMP history to render,
so that the card shows me useful drawdown data on the first
snapshot load instead of an "unavailable" empty state I have to
manually click around to escape.

## Context

`apps/desktop/src/features/portfolio/DrawdownAnalyticsCard.tsx`
defaults to a 1260d (5-year) window (line ~46:
`const DEFAULT_WINDOW: WindowOption = 1260`). When the user's
portfolio has positions whose FMP price history is shorter than 5
years, the engine returns `trust='unavailable'` and the card
renders an EmptyState — even though a 756d / 252d / Max window
might return rich data. Today the user has to click each window
in turn until they find one that works.

US-13.2's close-out explicitly flagged this as a deferred concern;
US-14 PRD picks it up.

The fix is fetch-orchestration only: when the initial fetch comes
back `trust='unavailable'` AND the user hasn't manually picked a
window, auto-retry with the next-shorter window. Backend unchanged;
the engine already returns `trust='unavailable'` correctly when it
has < 20 daily observations or no market data.

- `apps/desktop/src/features/portfolio/DrawdownAnalyticsCard.test.tsx`

## Acceptance criteria

- [x] AC1 — When `snapshot` becomes non-null AND the user has NOT
  manually selected a window, the card fetches with window=1260
  first. If the response is `trust='synthetic'`, render the data
  and stop (no extra fetches). Net delta on the happy path: 1
  fetch (matches current behaviour).
- [x] AC2 — When `snapshot` becomes non-null AND the user has NOT
  manually selected a window AND the 1260 fetch returns
  `trust='unavailable'`, the card automatically retries with
  window=756. If that returns `trust='synthetic'`, render its
  data. Selected window in the WindowSelector updates to reflect
  the window that actually rendered (so the user can see which
  one succeeded).
- [x] AC3 — Cascade order is strict: 1260 → 756 → 252 → `null`
  (Max). Each step only runs if the previous one returned
  `trust='unavailable'`. Cascade stops on the first
  `trust='synthetic'` response.
- [x] AC4 — When ALL four windows return `trust='unavailable'`,
  the card renders EmptyState with the LAST attempted window
  (Max) selected — so the user can manually click around if
  desired. No fabrication; no fallback to a stale prior
  successful response.
- [x] AC5 — When the user clicks any WindowSelector button,
  the card fetches with that exact window AND disables
  auto-fallback for the lifetime of the current snapshot.
  Whatever the engine returns for that specific window is
  rendered — even if `trust='unavailable'`, no cascade runs.
  The user's explicit choice always wins.
- [x] AC6 — When the user changes the snapshot (e.g. swaps to a
  different imported workspace), the auto-fallback override
  resets — the new snapshot's first fetch starts from 1260
  again and re-enables the cascade.
- [x] AC7 — When a fetch in the cascade fails with a network
  error (not `trust='unavailable'` but an actual exception /
  non-2xx response), the cascade STOPS and the card shows the
  ErrorState. The failure isn't window-specific so we don't try
  shorter windows. (The user can manually retry by clicking a
  window.)
- [x] AC8 — While the cascade is running, the card shows
  LoadingState ("Computing drawdown analytics…") continuously.
  Intermediate `trust='unavailable'` responses are NOT briefly
  flashed as EmptyState mid-cascade. The final render is the
  first synthetic result OR the final EmptyState — never an
  intermediate state.
- [x] AC9 — A `cancelled` flag still aborts the cascade if the
  effect re-runs (e.g. snapshot changes, user clicks a window).
  No stale fetches write to component state after cancellation.
  No race conditions where two cascades' results interleave.
- [x] AC10 — All previously Done tests stay green: 310 backend +
  187 frontend. Net delta: 0 backend, +4 frontend.
  `python scripts/run_all_tests.py` green; `cd apps/desktop &&
  npx tsc --noEmit` clean. `designSystem.audit.test.ts` 5/5
  green (untouched).

  matters.

  swaps (AC6 explicitly resets it). Persisting per-snapshot
  preferences is a different feature.
- No retroactive fix for existing imported workspaces — this is
  a UX fix that flows naturally on every snapshot reload.

## Notes / decisions

- **Cascade vs. parallel fetch**. Sequential cascade is the
  right pattern for v1: it minimizes backend load on the happy
  path (most users will have ≥ 5 years of history and the 1260
  call succeeds on the first try). Parallel fetch (fire 4 calls
  in parallel, pick longest with data) is faster on the unhappy
  path but wastes 3 calls on the happy path. Trade-off favors
  cascade since "unhappy path" is rare and the latency
  difference is small (~200ms per cached FMP fetch).
- **The user-override semantic**. Once the user clicks a
  window, we respect that even if it returns `unavailable`.
  This is intentional — the user expressed intent, and silently
  reverting to a different window would feel patronizing. The
  EmptyState message ("At least 20 trading days…") is the
  appropriate feedback; the user can change windows again or
  accept the result.
- **Snapshot-change resets override**. When the user swaps to a
  different workspace, the previous override should NOT carry
  over — the new portfolio's history characteristics may be
  different and the cascade should re-run. Implementation: a
  separate `useEffect([snapshot])` that resets the override
  flag, OR the main effect detecting snapshot identity change.
  The simpler pattern is the dedicated reset effect.
- **Cancellation discipline matters more here**. With a single
  fetch per effect run, the existing `cancelled` flag suffices.
  With a multi-fetch cascade, the cancellation check must be
  inside the loop (between each fetch) — otherwise a snapshot
  change mid-cascade leaves a stale cascade running to
  completion against a stale snapshot reference, and writes
  results to a now-defunct render.
- **Loading state continuity** (AC8) is what makes the
  cascade feel like one operation rather than a flicker
  sequence. The implementation must not transition through
  `state='done'` with the unavailable response mid-cascade;
  it should remain in `state='loading'` until the cascade
  resolves to either synthetic data or exhausts.
- **No methodology change.** The drawdown formula in
  `financial-methodology.md` §Wealth Index and Drawdown +
  §Drawdown episode identification is untouched. No academic
  citation needed.
- **Optional future polish**: surface a small inline indicator
  ("Showing 756d — 1260d unavailable") when the cascade
  successfully fell back. Not required for v1 — the
  WindowSelector's active state already shows which window is
  rendering, and the user can compare against their
  expectation if curious.
