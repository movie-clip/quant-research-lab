## Story

As an **engineer debugging cache behaviour** via `MarketDataService`'s
`last_fetch_meta` / `get_last_fetch_meta`, I want the `cached` flag to report
what actually happened on each call, for every method that reports one, and I
want the formula that decides "is this a cache hit" to live in exactly one
place, so that I can trust this diagnostic when reasoning about FMP call
volume, rate limits, and cache effectiveness instead of quietly distrusting
it the way `get_company_profile`'s callers had to before US-37.2.

## Context

US-37.2 (T-37.2.2) fixed this same bug for exactly one method,
`MarketDataService.get_company_profile` — its `last_fetch_meta[...]["cached"]`
now reflects a real per-call hit/miss instead of a hardcoded `True`. US-37.2's
own "Out of scope" section named this as leaving "4 other methods" unfixed,
but that count was wrong on two counts, corrected by this run's delivery
brief after re-reading `market_data.py` directly
(`02-delivery-brief.md` § Stories (Story B)): there is no `get_quote` method
(the real name is `get_latest_quotes`), and the list omitted
`get_direct_verified_benchmark_history` entirely. The real, corrected scope
is **five methods, six hardcoded call sites**, every one of which currently
sets `"cached": True` unconditionally on a successful call, regardless of
whether that call was actually served from the on-disk cache or required a
live fetch:

- `get_latest_quotes` (`services/market_data.py`, one call site)
- `get_historical_prices` (two call sites — the FMP-branch success path, and
  the yfinance-fallback success path)
- `get_direct_verified_benchmark_history` (one call site)
- `get_etf_holdings` (one call site)
- `get_etf_holdings_for_date` (one call site, in its non-history-cache branch)

Separately, and independently fixable, `get_company_profile`'s own fix
(T-37.2.2) introduced a second problem the research that grounds this story
already named as the right shape to close: `market_data.py`'s
`_profile_will_be_served_from_cache()` helper answers "will this be a cache
hit" by **re-deriving its own copy** of the cache-key formula
(`cache_identifier = json.dumps({"path": "profile", "params": {"symbol": ...}}, sort_keys=True)`)
rather than calling into the one formula `fmp.py`'s `_get()` actually uses to
build the key it looks up (`clients/fmp.py:184-187`,
`cache_identifier = json.dumps({"path": path, "params": params}, sort_keys=True)`).
The two are hand-kept in sync today by construction, not by a shared
function — if `fmp.py`'s call shape for a profile request ever changes (a
new param, a renamed one), `market_data.py`'s copy would silently stop
agreeing with it, and `_profile_will_be_served_from_cache` would start
reporting a false answer with nothing to catch it.

**Value framing.** This is diagnostic-internal — an engineer reading
`last_fetch_meta`, not a researcher reading the Exposure/Risk/Dashboard tabs.
There is no end-user-visible outcome in this story. It is filed as a story
rather than routed to the tech-debt register because it is closer to *fixing
a diagnostic that actively misreports* than to a refactor with no behavioural
change (matching how US-37.2 itself framed the identical `get_company_profile`
fix) — but the delivery brief flags this as a closer INVEST call than
US-38.1's, and the human should weigh "value" here as diagnostic honesty for
the people maintaining this system, consistent with guardrail 4's
"never fabricate," applied to an internal signal rather than a UI number.

Implementer must also read: `docs/product/stories/US-37.2-sector-classification-followups.md`
(the story T-37.2.2 shipped under, same bug shape, same file); the docstring
on `_profile_will_be_served_from_cache`
(`services/quant-engine/app/services/market_data.py:460-483`), which already
names the narrow edge case this fix does not need to solve (a reported miss
followed by a live request that itself fails and falls back to stale cached
data — pre-existing, out of scope, see § Out of scope).

## Acceptance criteria

- [x] AC1 — `get_latest_quotes`'s `cached` value under
  `last_fetch_meta[symbol]` reports `True` only for a call whose quote
  response was actually served from the cache, and `False` for a call that
  required a live fetch.
- [x] AC2 — `get_historical_prices`'s `cached` value reports the true
  per-call hit/miss state on both of its success paths — the primary (FMP)
  branch and the yfinance-fallback branch — not a hardcoded value on either.
- [x] AC3 — `get_direct_verified_benchmark_history`'s `cached` value reports
  the true per-call hit/miss state.
- [x] AC4 — `get_etf_holdings`'s `cached` value reports the true per-call
  hit/miss state.
- [x] AC5 — `get_etf_holdings_for_date`'s `cached` value reports the true
  per-call hit/miss state for the branch that reaches a live/cached FMP
  fetch (its holdings-history-snapshot branch, which is a distinct, already
  differently-labeled data source, is unaffected by this story).
- [x] AC6 — Calling any one of the five methods above twice for the same
  symbol/inputs within the cache's TTL reports the first call's `cached`
  value as `False` (or whatever the true miss/hit state of that specific call
  was) and the second call's as `True` — the two calls are distinguished, not
  reported identically.
- [x] AC7 — The cache-key formula used to answer "is this call a hit" is
  expressed once, in `fmp.py`, and `market_data.py`'s pre-check helper (the
  mechanism `get_company_profile` already uses, extended to the methods in
  AC1-AC5) derives its answer from that one formula rather than maintaining
  its own independent copy of it.
- [x] AC8 — `get_company_profile`'s existing correct behaviour (T-37.2.2) is
  unchanged in outcome after AC7's refactor — its `cached` flag still reports
  the true per-call hit/miss state, now sourced from the single formula.

## Test plan

Backend (pytest), `test_market_data.py` (the module US-37.2 added
`get_company_profile` coverage to):

- One cache-miss-then-cache-hit pair per method in AC1-AC5 — first call
  reports `cached: False`, a second call for the same symbol/inputs within
  TTL reports `cached: True`. Mirrors the shape of `get_company_profile`'s
  existing AC3/AC4 test from US-37.2.
- `get_historical_prices`'s two branches (FMP success, yfinance-fallback
  success) each get their own hit/miss pair, since they are two separate
  call sites, not a shared one.
- Regression — `get_company_profile`'s existing cache-flag test(s) from
  US-37.2 stay green after the cache-key-formula consolidation (AC7/AC8),
  proving the refactor is behaviour-preserving for the method it started on.
- A test asserting `market_data.py`'s helper and `fmp.py`'s own key-building
  path agree by construction (e.g. asserting they are literally the same
  function/formula, not just producing matching output on today's inputs) —
  the whole point of AC7 is to make a future drift structurally unreachable,
  not merely re-pass today's fixture.

Regression / guardrail:

- No existing test asserts the current (wrong) hardcoded `cached: True` for
  any of the five methods specifically — worth re-confirming at
  implementation time, mirroring US-37.2's own note on this.
- `python scripts/run_all_tests.py` green, including the dead-code gate (a
  cache-key-formula consolidation that leaves the old duplicated logic behind
  unused would trip vulture/knip).

## Out of scope

- **Any change to what gets cached, or for how long (TTL, persistence).**
  This is a diagnostic-accuracy fix only, reporting what already happens —
  mirroring T-37.2.2's own scope boundary and the delivery brief's explicit
  framing.
- **The narrow edge case named in `_profile_will_be_served_from_cache`'s own
  docstring**: a pre-check reporting a miss, followed by a live request that
  itself fails and falls back to serving stale cached data — the response is
  in fact cache-served even though the pre-check reported `False`. Not
  resolvable without a return-side signal from `fmp.py`'s `_get()`, which
  this story does not add. Pre-existing, unaffected by this story either way.
- **Persisting the resolved classification, or any other US-37.1/US-37.2
  caching recommendation.** Unrelated — that thread concerns what the sector
  resolver caches, not this story's cache-*flag* accuracy.
- **A frontend ticket.** `last_fetch_meta` is not rendered on any tab; this
  story has no UI surface.
