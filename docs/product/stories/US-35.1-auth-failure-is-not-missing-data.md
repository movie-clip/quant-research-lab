# US-35.1: Stop returning an auth failure as if it were missing data

**Epic:** Epic 35 — Market-Data Failure Honesty
**PRD:** [`epic-35-market-data-cache-resilience.md`](../prd/epic-35-market-data-cache-resilience.md)
**Status:** Done (2026-08-19)
**Last updated:** 2026-08-19

## Story

As a **portfolio researcher**, I want a misconfigured market-data key to tell me
so, rather than showing me an empty Dashboard, so that I can tell the difference
between *"the market has no data for you"* and *"this machine could not ask"*.

## Context

PRD finding **F-1**, verified empirically on 2026-08-19 with a deliberately
invalid key.

`FmpClient._get` negative-caches `{401, 402, 403, 404}` as `[]`
(`app/clients/fmp.py:190`), then immediately re-reads that entry with
`allow_stale=True` and returns it — so the `httpx.HTTPStatusError` is swallowed,
not raised:

```
FMP negative cache [history] {'symbol': 'AAPL', …} status=401
FMP stale cache fallback [history] {'symbol': 'AAPL', …}
RESULT: returned []          <-- no exception
second call: []              <-- served from the negative cache
```

With `fmp_history_cache_ttl_seconds = 86400`, one failed run poisons every
symbol it touched for a day, and fixing the key does not help until the TTL
expires or the cache is cleared by hand.

Every engine downstream then behaves *correctly* on the empty input and degrades
to `unavailable`. The trust ladder tells the truth about the data it was handed.
Nothing says the key is wrong. This is a fail-closed path reached for the wrong
reason — the same shape as US-34.9's first implementation, which blanked the
benchmark by dropping every row and produced a symptom indistinguishable from
"this benchmark has no data".

Implementer must read: `app/clients/fmp.py` (`_get`, the negative-cache and
stale-fallback branches); `app/services/market_data.py` (**every** call site
wraps the client in `except Exception: return []` — see the note below);
`app/core/cache.py`; the Epic 35 PRD.

### The constraint that shapes this story

`MarketDataService` catches `Exception` broadly at **eight** call sites and
returns `[]` / `None`. Raising in the client alone changes nothing observable.

Those catches are **correct and must stay**: one delisted or unresolvable symbol
must not fail a whole-portfolio fetch, and the symbol-resolution pipeline
deliberately tries several candidates and expects most to fail. The distinction
this story introduces is therefore not "swallow vs raise" but:

| Failure | Scope | Behaviour |
|---|---|---|
| 404, unresolvable symbol, delisted | **this symbol** | keep degrading to `[]` — unchanged |
| 401, or no API key configured | **every symbol** | propagate; it is not a fact about any symbol |

A caller-configuration failure cannot be represented as an absence of data,
because it is not an absence of data.

## Acceptance criteria

- [x] AC1 — **A 401 raises instead of returning `[]`.** `FmpClient._get`
  propagates a dedicated error for an authentication failure rather than
  converting it to an empty result.

- [x] AC2 — **A 401 is never written to the cache.** No negative entry is
  created for it, so fixing the key and re-running works immediately —
  no manual cache clear, no 24-hour wait.

- [x] AC3 — **404 is unchanged.** A genuinely unknown symbol still
  negative-caches and still returns `[]`, so the retry-storm protection that
  behaviour exists for is intact.

- [x] AC4 — **The error survives `MarketDataService`.** The auth error
  propagates through the service's `except Exception` call sites instead of
  being flattened to `[]`, while every *other* exception at those sites still
  degrades exactly as it does today.

- [x] AC5 — **A per-symbol failure still degrades.** A portfolio containing one
  unresolvable symbol alongside good ones still returns data for the good ones —
  this story must not turn one bad symbol into a whole-request failure.

- [x] AC6 — **The message names the cause.** The surfaced error says the market
  data credential is missing or rejected, and which it was. A researcher reading
  it must not have to guess whether their portfolio or their config is at fault.

- [~] AC7 — ~~**An unset key is treated the same way as a rejected one.**~~
  **WRONG — reverted 2026-08-19.** Shipping it turned every route into a 400 in
  CI, which runs deliberately **keyless**: the suite is network-free, so engines
  are expected to reach the client, get nothing, and degrade to `unavailable`.
  Running without a key is a **supported mode**, not a misconfiguration. An unset
  key keeps raising the plain `ValueError` that `MarketDataService` swallows;
  only a *rejected* key (401) raises `MarketDataAuthError`. A test now guards
  against re-unifying them.

- [x] AC8 — **402/403 keep their current behaviour, deliberately.** They are
  entitlement answers about a *symbol* on this plan — the UCITS listings FMP
  does not serve return 402 on every run and fall through to the yfinance
  fallback, which is working as intended. Changing them is out of scope and the
  story says so rather than leaving it ambiguous.

- [x] AC9 — **Behaviour-neutral on a healthy run.** No production behaviour
  changes when the key is valid: `dashboardGoldens.ts` byte-identical, full
  suite + tsc + dead-code gate green.

## Out of scope

- **402 and 403.** See AC8 — they are entitlement answers about a symbol, the
  UCITS path depends on the current behaviour, and changing them would need its
  own evidence about which are transient. Named here so the implementer does not
  "tidy" them in passing.
- **Removing negative caching.** It stays for 404, which is what it is for.
- **Retry, backoff, or rate-limit handling.** A 429 is a real gap and is not
  this story.
- **How the API surfaces the error to the UI.** This story makes the failure
  reach the service boundary honestly; deciding whether a route returns 503 with
  a detail message, and how the Dashboard renders that, is a separate slice.
- **The other two Epic 35 findings** — the unclearable `history_yf` namespace
  (US-35.2) and the silently degrading golden capture (US-35.3).

## Notes / decisions

- **No formula, no methodology, no trust-class change.** This story does not
  touch analytics; no academic citation applies. The trust ladder is unchanged —
  the point is that an engine should not be *handed* an empty series that means
  "misconfigured".
- **Why a dedicated exception rather than a sentinel return.** Every call site
  already treats "falsy result" as "no data". A sentinel would have to be
  checked at eight places that currently cannot distinguish it; an exception
  type is checkable in one `except` clause per site and cannot be ignored by
  accident.
- **Why the broad catches are kept.** They are load-bearing for symbol
  resolution, which tries `VUAA.L` → `VUAA` → a US proxy and expects failures.
  Removing them would convert normal resolution misses into hard errors — the
  opposite of this story's intent.
- **The 24-hour TTL is the multiplier, not the bug.** Even a correct negative
  cache would be uncomfortable at 86400s; the reason it matters here is that the
  entry should never have been written. Re-tuning the TTL is not part of this
  story and would not fix it.

## Outcome (2026-08-19)

**Verified against the live API, not just mocked.** With a deliberately invalid
key, `MarketDataAuthError` now raises with a message naming the cause, and the
cache directory is left **empty** — so a corrected key works on the very next
call. Before, the same call returned `[]` and wrote a negative entry good for 24
hours.

**The two-layer constraint was the substance of the story.** Fixing the client
alone would have changed nothing observable: `MarketDataService` catches
`Exception` at **six** call sites (the story estimated eight) and would have
flattened the raised error straight back into `[]`. Each catch now re-raises
`MarketDataAuthError` and swallows everything else exactly as before. Both
directions are tested — an auth error propagates out of `get_historical_prices`,
and a `RuntimeError` at the same call site still degrades to `[]`.

**402 was left alone deliberately, and pinned.** It is an entitlement answer
about a symbol on this plan: the UCITS listings return it on every run and
depend on falling through to the yfinance fallback. Two tests exist purely to
stop a later reader folding 402 in with 401 on the assumption that both are
"auth" failures — `test_a_plan_entitlement_response_keeps_its_negative_cache`
and `test_a_plan_entitlement_402_still_falls_through_to_yfinance`.

**Count correction:** the story said "eight `except Exception` call sites"; there
are six. Recorded rather than quietly corrected, since the number was used to
argue the story's shape.

Behaviour-neutral on a healthy run: `dashboardGoldens.ts` byte-identical, 760
backend (+9) + 331 frontend green, tsc + dead-code gate clean.

## Correction (2026-08-19) — AC7 was wrong and shipped red

**I merged this with a failing CI run.** `gh pr merge` does not block on failing
checks without branch protection, and I did not check the result before merging.
`main` was red for roughly ten minutes.

**The defect was real, not a test artifact.** AC7 reasoned that "no key" and
"rejected key" are the same failure class. They are not:

- A **rejected** key (401) means the caller tried to authenticate and was
  refused — a genuine misconfiguration, and the case this story exists for.
- **No** key at all is a **supported mode**. The test suite is network-free by
  design and CI has no key, so every engine is expected to reach the client, get
  nothing back, and degrade to `unavailable`. Raising there converted that into
  a 400 on every route — `test_drift_engine.py` and friends went from 200 to 400.

The unset-key guard is reverted to its original `ValueError`, which
`MarketDataService` swallows on the way to `[]`.
`test_an_unset_key_is_not_treated_as_a_rejected_one` now asserts explicitly that
it is **not** a `MarketDataAuthError`, so the two cannot be re-unified by someone
who notices they look alike.

**What I should have done:** run the suite the way CI runs it — keyless — before
merging. Doing that now (`.env` moved aside) reproduces the failure exactly and
then confirms the fix: 760 backend + 331 frontend green with no key present.

The core of the story is unaffected: a 401 still raises, is still never cached,
and a corrected key still works on the next call.
