# US-24.5: Decouple broker statement sections from the domain (and fix the two silent misclassifications it caused)

**Epic:** Epic 24 — Codebase Improvement
**PRD:** [`epic-24-codebase-improvement.md`](../prd/epic-24-codebase-improvement.md)
**Status:** Done
**Last updated:** 2026-08-09

## Story

As a **portfolio researcher**, I want my Freedom24 trades and my ESPP payroll
contributions to be recognised as trades and contributions, so that the proof
system reports what my statement actually shows instead of reporting them as
unclassified cash movements of unknown origin.

## Context

Tech-debt register row **US-24.5**. Re-validated against the code on
2026-08-09 per Epic 24 discipline, and the row's severity is **understated**:
the coupling is not latent debt, it is already producing wrong output on two of
the three supported brokers.

`domain/ledger.py` derives `broker_evidence` and `cash_movement_classification`
by matching `source_section` against **hardcoded broker display strings**
(`:63-93`) — `"Trades"`, `"Deposits & Withdrawals"`, `"Dividends"`,
`"Interest"`, `"Fees"`, `"Withholding Tax"`, and a handful of aliases. Any
importer whose statement calls a section something else falls through to
`"unknown"`, silently.

### Findings (reproduced against the committed fixtures, network-free)

**F-1 (High) — every Freedom24 trade is unclassified.** `freedom24.py:270`
emits `source_section="Transactions"`; the domain requires exactly `"Trades"`.
On `FF2026.pdf`, **3 of 8 ledger entries** — every BUY and SELL — classify as
`"unknown"` instead of `"internal_trading_flow"`:

```text
FF2026.pdf: unknown 3 (SELL 2, BUY 1) — all source_section="Transactions"
```

**F-2 (High) — every ESPP contribution and purchase is unclassified.**
`espp.py:159,171` emits `source_section="Employee Stock Purchase Summary"` for
both the payroll DEPOSIT and the BUY. On `ESPP2026.pdf`:

```text
DEPOSIT  Employee Stock Purchase Summary  -> unknown   (want external_capital_flow)
BUY      Employee Stock Purchase Summary  -> unknown   (want internal_trading_flow)
```

The DEPOSIT case is the worst of the two: `external_capital_flow` is precisely
how the proof system recognises investor contributions
(`portfolio_proof.py:803-805`), and with a zero count it reports
`status="not_observed"` — so an ESPP portfolio's payroll contribution is
**invisible to the proof system** while the statement states it plainly.

**Examined and found correct:** IB2026.csv classifies all 204 entries with zero
`unknown` (the IBKR labels are the ones the domain was written against), which
is why this survived — the primary fixture never exercised the defect. The
register's **second item is stale**: `LedgerEntryType` already exists as a
shared `Literal` in `app/schemas/imports.py:9` and is imported by the domain
and both IBKR importers, so there is no pseudo-enum left to extract.

### Why the fix is a section-role registry

`source_section` is **provenance** — it should keep saying what the statement
actually said, so an importer must not be forced to relabel "Transactions" as
"Trades" to satisfy a downstream matcher. The coupling to remove is the
domain's assumption that it knows every broker's vocabulary. A single
registry mapping *known section label → semantic role* gives one place that
holds the vocabulary, and lets a guard test assert that every label any
importer emits resolves — so the next broker fails loudly at test time instead
of silently classifying `unknown` in production.

Implementer must read: `app/domain/ledger.py:60-115`;
`app/schemas/imports.py:9` (`LedgerEntryType`);
`app/services/portfolio_proof.py:780-815` (the consumer);
`app/importers/{interactive_brokers,interactive_brokers_csv,freedom24,espp}.py`
(every `source_section=` site); the register row US-24.5.

- [x] AC1 — A **single shared registry** maps each known broker section label to
  a semantic role (trade / external transfer / dividend / interest / fee /
  tax). `broker_evidence` and `cash_movement_classification` consult the role;
  no broker display string is matched inline in `domain/ledger.py`.
- [x] AC2 — **F-1 fixed:** every Freedom24 BUY/SELL classifies as
  `internal_trading_flow` and carries `broker_trade_ledger_line` evidence.
  `FF2026.pdf` has **zero** `unknown` entries.
- [x] AC3 — **F-2 fixed:** the ESPP payroll DEPOSIT classifies as
  `external_capital_flow` with `broker_transfer_section_line` evidence, and the
  ESPP BUY as `internal_trading_flow`. `ESPP2026.pdf` has **zero** `unknown`
  entries, and the proof system's external-capital-flow witness reports
  `broker_proven` rather than `not_observed`.
- [x] AC4 — **IBKR is byte-identical.** All 204 `IB2026.csv` entries keep their
  existing classification and evidence, and the PDF path is unchanged — this
  story must not move the primary fixture's numbers.
- [x] AC5 — **`source_section` still records what the statement said.** No
  importer is changed to emit a different broker's label; provenance is
  preserved (`"Transactions"` stays `"Transactions"`).
- [x] AC6 — **`unknown` still means genuinely unrecognised**, not "typo". It
  remains reachable and is still surfaced by the proof witnesses; the fix does
  not paper over unclassifiable entries by defaulting them to a role.
- [x] AC7 — **A new broker cannot silently regress this.** A test asserts that
  every `source_section` value any importer emits resolves to a registered
  role, so an unregistered label fails the suite rather than degrading output
  in production.
- [x] AC8 — `dashboardGoldens.ts` is byte-identical (the goldens are generated
  from IB2026, which AC4 pins as unchanged); no schema or methodology formula
  changes.

## Out of scope

- **Adding a semantic-role field to `ImportedLedgerEntry`.** That is the fuller
  decoupling (importers declare the role directly), but it is a schema change
  touching persisted snapshots and every importer. The registry fixes both
  defects and removes the string coupling without it; recorded as a possible
  follow-up.
- **Re-labelling any importer's `source_section`** (AC5 — provenance).
- **Changing what the proof system does with a classification.** This story
  makes the classification correct; the admission policy built on it is
  unchanged.
- **The ESPP/Freedom24 parsers themselves** — hardened in US-24.4 / US-24.8 and
  not revisited here.

## Notes / decisions

- **Severity correction, recorded here:** the register rated this **Med** as
  pure coupling debt. It is a **High** correctness defect on two of three
  brokers, found only because this story re-validated the row against the
  fixtures before refactoring. The Epic 24 discipline ("validate the row
  first") is what surfaced it.
- **Why `"Employee Stock Purchase Summary"` maps to two roles.** The same ESPP
  section produces both the payroll DEPOSIT and the BUY, so the role cannot be
  a pure function of the label — it is resolved together with `entry_type`,
  exactly as the existing IBKR aliases already are (`"Income Summary"` and
  `"Cash deposits/ withdrawals"` each serve several entry types today).
- **Why not just add `"Transactions"` to the existing inline sets.** That fixes
  today's two symptoms and leaves the structure that caused them: the fourth
  broker will hit it again, silently. AC7's coverage guard is the actual
  deliverable — it converts a silent production degradation into a failing test.
- No new formula, so no academic citation is required. The affected semantics
  (external capital flow vs internal trading flow) already sit in
  §Portfolio Return Methodology and the portfolio-proof material.
