# US-12.4: `ui-polish` skill + Epic 12 close-out

**Epic:** 12 — UI Polish & Design System
**PRD:** [`epic-12-ui-polish-design-system.md`](../prd/epic-12-ui-polish-design-system.md)
**Status:** Done
**Last updated:** 2026-05-29

## Story

As a **portfolio researcher**, I want any agent that builds the next analytics
card to produce a result that visually matches the four Exposure cards from
Epics 9/11 without me having to ask for a polish pass — by reading a single
project skill (`ui-polish`) that codifies the design tokens, primitives,
chart defaults, and accessibility baseline established in US-12.1–12.3 —
so that visual consistency is enforced by agent workflow, not by post-hoc
review.

## Context

US-12.1 introduced design tokens. US-12.2 extracted primitive components.
US-12.3 added shared chart defaults + an accessibility baseline. The
material is in place, the audit tests pin the contract — but the
*knowledge* of how to use it lives only in implicit code patterns. The
next agent that runs `build-story` on a new analytics story will not
know that `<CardShell>` exists unless someone tells it.

This story closes that gap with two artifacts:

1. **`ui-polish` skill** (`.claude/skills/ui-polish/SKILL.md`) — the 8th
   project skill. Teaches any agent the design system by example, with
   copy-paste-ready patterns and an anti-pattern list. Build-story can
   then auto-delegate the UI slice of a ticket to this skill the same way
   it currently delegates the test slice to `write-tests`.

2. **`docs/contracts/ui-design-system.md`** — long-lived contract doc.
   Tables of tokens, primitives, audit checks. The reference any future
   UI story consults (and that `update-docs` consults when reconciling a
   UI change).

Plus the standard close-out (roadmap, README, current-product-state,
CLAUDE.md, story status). After this story ships, Epic 12 is fully
closed.

No backend changes. No code changes (apart from one small edit to the
`build-story` skill to mention `ui-polish` as the auto-delegation target
for UI work). No tests change.

Implementer must read:

- The 7 existing project skills (`.claude/skills/*/SKILL.md`) — to match
  the established skill format, frontmatter style, "cycle" reference, and
  "Definition of Done" section pattern
- `apps/desktop/src/app/styles.css` `:root` block — to inventory the
  60+ tokens for the skill's "tokens" section
- `apps/desktop/src/app/primitives/` (8 files: TrustBadge, WindowSelector,
  EmptyState, LoadingState, ErrorState, CardShell, ChartShell,
  chartDefaults) — to inventory primitives with exact prop signatures
- `apps/desktop/src/test/designSystem.audit.test.ts` — for the 5 audit
  tests to document under "Audit-enforced contracts"
- `docs/contracts/correlation-fields.md` — style reference for the new
  ui-design-system contract doc

## Notes / decisions

- **Why a skill, not just a doc** — the contract doc (AC4) is a
  reference; the skill (AC1+AC2) is *invokable* by the cycle. When
  build-story hits the UI slice of a ticket, it should be able to
  delegate to `ui-polish` for guidance the same way it delegates the
  test slice to `write-tests`. AC9 closes that loop in the build-story
  skill text.
- **No academic citation needed** — pure UI / docs story.
- **Skill length target**: 250–350 lines. The existing project skills
  span ~150 (build-story, lean) to ~400 (fmp-data, reference-heavy).
  ui-polish is closer to the reference end — lots of token/primitive
  inventory.
- **The "canonical card pattern" code block** is the highest-value
  section. Implementer should aim for a complete, type-checking,
  copy-pasteable example (~30–40 lines of TSX) showing
  CardShell → TrustBadge → WindowSelector → ChartShell → axis defaults →
  state primitives. Treat it like the README's quick-start.
- **AC3 path-existence** is manual at this story. A future "skill-audit"
  story could grep all `.claude/skills/*/SKILL.md` for file paths that
  no longer exist on disk and flag them — useful insurance but
  out-of-scope here.
- **Migration note in the contract doc** isn't a TODO — it's a
  *deliberate* statement of what the design system covers and what it
  doesn't. If someone tries to add a Dashboard-tab feature later, the
  contract doc tells them: design system applies, but the Dashboard
  tab hasn't been migrated yet, so expect inconsistency until a future
  story migrates it.
- **The 8th skill slot**: ui-polish makes 8 project skills total
  (build-story, write-story, write-tests, verify-story, update-docs,
  quant-research, fmp-data, ui-polish). The "cycle" diagram remains
  6 skills (research → plan → implement → cover → QA → sync); fmp-data
  and ui-polish are reference skills called *from within* the cycle,
  not steps in the cycle. CLAUDE.md should reflect this distinction.
