# US-24.8: Harden the IBKR importer parsing (fail-safe)

**Epic:** Epic 24 — Codebase Improvement
**PRD:** [`epic-24-codebase-improvement.md`](../prd/epic-24-codebase-improvement.md)
**Status:** Done
**Last updated:** 2026-07-04

## Story

As a **portfolio researcher**, I want **a malformed line in an Interactive
Brokers statement to degrade to a partial import rather than crash the whole
import**, so that **a small layout drift in next year's statement doesn't
block me from importing at all**.

## Context

`docs/tech-debt-register.md` (US-24.4 row) flags this as a deferred
follow-up: "the same fail-safe pattern for `interactive_brokers.py` /
`espp.py` remain deferred follow-ups." US-24.4 made the Freedom24 importer
fail-safe (skip a malformed record, continue parsing) because it walked
fixed line offsets and any unexpected content raised
`IndexError`/`ValueError` straight out of `import_statement`.

**Investigation corrected this story's original two-importer scope down to
one.** Both `interactive_brokers.py` and `espp.py` are regex-`match()` +
`if not match: continue`-guarded for "is this a record at all" (unlike
Freedom24's raw positional-offset walk), which is inherently more fail-safe.
The remaining risk is narrower: a regex can match a record shape while still
capturing a numeric/date group that fails the subsequent
`float()`/`datetime.strptime()` conversion, and that conversion has no
guard — crashing the whole import. Whether this is *reachable* depends on
how permissive each importer's regex groups are:

- **`interactive_brokers.py` — reachable, fixed here.** Its statement-totals
  patterns use `[\d,.-]+` (permits multiple dots/hyphens, e.g. a corrupted
  `"1.2.3"` token still matches the shape but fails `float()`), and its
  period-end-date regex allows any `\d{1,2}`/free-form month text that can
  fail `datetime.strptime` even though it matches the shape (e.g. an invalid
  calendar day or a garbled month name).
- **`espp.py` — investigated, found not reachable, left unchanged.** Every
  numeric group in `espp.py` uses the strict shape `[\d,]+\.\d+` (or
  `-?[\d,]+\.\d+`), which by construction contains exactly one decimal point
  and only digits/commas elsewhere — after `_normalize_number`'s
  comma-strip, this is *always* a valid `float()` input. There is no
  reachable "regex matched, but the number was invalid" case in `espp.py`
  today. (Confirmed by attempting to construct exactly this failure in a
  test — every crafted "malformed" input either failed to match the regex at
  all, which the existing `if not match: return []`/`raise ValueError`
  already handles correctly, or matched and parsed successfully.) Adding a
  try/except around calls that cannot raise would be unjustified complexity
  for a scenario that cannot happen — the same principle behind not adding
  speculative error handling. `espp.py`'s existing hard-fail on "structure
  doesn't match at all" (e.g. `_parse_stock_position`'s
  `raise ValueError("Could not parse ESPP stock holdings section")`) remains
  the correct behavior — this importer is scoped to one specific statement
  shape (hardcoded `MICROSOFT CORP`/`MSFT`), so "the structure is
  fundamentally different" is the honest failure mode, not "one field was
  malformed."

Read before implementing:
- `docs/finance/financial-methodology.md` "Importer resilience rule" (added

- `services/quant-engine/app/importers/freedom24.py` — the reference

- `services/quant-engine/app/importers/interactive_brokers.py`

## Acceptance criteria

- [x] AC1 — A single malformed numeric field in an IBKR statement's summary
      section (`_parse_statement_totals`) degrades that one field to `None`
      and the import continues, rather than raising and aborting the whole
      import.
- [x] AC2 — A malformed IBKR statement period string that matches the
      period regex but fails `datetime.strptime` degrades `as_of_date` to the
      existing `date(2025, 12, 31)` fallback rather than raising — i.e.
      `_parse_period_end_date` never lets a `ValueError` escape.
- [x] AC3 — A single malformed record (bad numeric or calendar-invalid date
      group) in the IBKR trades, dividends/withholding-tax/interest/fees, or
      deposits-and-withdrawals sections is skipped and parsing continues,
      rather than raising and aborting the whole import.
- [x] AC4 — Valid, well-formed IBKR statements produce byte-identical output
      to today (behaviour-neutral for the golden-master fixtures — `IB2026.pdf`
      unchanged).
- [x] AC5 — `financial-methodology.md`'s "Importer resilience rule" is
      updated to cover both hardened importers (Freedom24, IBKR), and to
      record that `espp.py` was investigated and found not to need the same
      change (its regex groups cannot produce a matched-but-unparseable
      numeric value).

## Notes / decisions

- The original story premise assumed both `interactive_brokers.py` and
  `espp.py` needed the identical fix. Implementation disproved half of that:
  `espp.py`'s numeric regex groups (`[\d,]+\.\d+`) cannot capture a value
  `float()` will reject, so the "malformed field degrades gracefully" fix
  has no reachable failure to guard against there. This was caught by trying
  to write the ESPP test cases first and finding every constructed
  "malformed" input either failed to match (already handled) or parsed fine
  — the same "verify before building on a premise" discipline applied
  elsewhere in this session (Epic 25's Modified-Dietz correction).
- No academic citation needed — this is import-robustness engineering, not a
  financial formula change.
